# เทียบเคียง OpenAI dots กับ MyAI (SPADA L5) และ Team Agent (OneManOS SetBox)

- **รหัสเอกสาร: SPD-ANL-001** · ร่าง 2026-09-30 · เป็นการวิเคราะห์เชิงสถาปัตยกรรม ไม่ใช่ผลทดสอบ
- ระดับความมั่นใจ: เนื้อหาฝั่ง dots มาจากข้อความที่ผู้ใช้แนบ (ซึ่งอ้าง OpenAI) และการค้นเว็บยืนยันเฉพาะแกนหลัก · ฝั่ง SPADA/SetBox มาจากการอ่าน ADR และเอกสารใน repo ไม่ได้รันระบบ
- เอกสารนี้ **ไม่ใช่เอกสารสำหรับส่งนักลงทุน** ข้ออ้างเปรียบเทียบใดๆ ต้องผ่านการทดสอบก่อนนำไปใช้ในสไลด์

## 1. สิ่งที่ยืนยันได้และยังยืนยันไม่ได้เกี่ยวกับ dots

| ข้อความ | สถานะ |
|---|---|
| dots เป็น always-on agent ใน ChatGPT ใช้ GPT-6 Astra มี cloud computer และ browser ของตัวเอง เชื่อม 4,000+ แอป เริ่มเปิดตัว 29 ก.ย. 2569 (Pro นอก EEA/สวิส/สหราชอาณาจักร และ Business Premium; beta สำหรับ Enterprise/Edu/Healthcare) | **ยืนยันจากผลค้นเว็บหลายแหล่ง** |
| local computer access (ปิดเป็นค่าเริ่มต้น), custom rules 4 แบบ, scheduled tasks, subagents, memory จากแอปที่เชื่อม, reset ลบ memory และ task, disconnect ไม่ลบข้อมูลที่เคยดึง | **ยังไม่ได้ตรวจกับเอกสารต้นทาง** (มาจากข้อความที่แนบ) |
| dots ยังโทรหาผู้ใช้เองไม่ได้ | **ขัดแย้ง**: หัวข้อข่าวแหล่งหนึ่งในผลค้นเขียนว่า dots "calls and writes for you" ต้องตรวจเอกสาร OpenAI ก่อนอ้าง |

## 2. ต้องแยกให้ชัดว่าเทียบกับอะไร

ผู้ใช้เอ่ยถึงสองสิ่งที่ ADR 0016 แยกกันโดยเจตนา:

| | MyAI | Team Agent |
|---|---|---|
| ที่อยู่ | ชั้น 5 ของ SPADA (อยู่ใน SPADA) | บน OneManOS SetBox (อยู่นอก SPADA ตาม ADR 0014) |
| การรัน | on-device, ภายใต้ Constitutional | บนกล่องของกิจการ ทีมเดียวหลายบทบาทได้ |
| ตัวตน | `did:spada:agent:*` สงวนไว้สำหรับ MyAI | **ไม่มี DID ของตัวเอง** ทำในนามเจ้าของ (client_id + device DID + ลายเซ็นเจ้าของ) |
| อิสระ | D2.1: อิสระเฉพาะ operation ที่ย้อนกลับได้ | human-in-the-loop เป็น UX ชั้นแรก หลักฐานที่ SPADA เชื่อคือ actor assertion ที่เจ้าของลงนาม (ผูก payloadDigest) |
| สถานะ | `myai-inference-service`, `ai-host-gateway` มีในโค้ด · doc 189 (พ.ค.–มิ.ย.) ให้คะแนน MyAI 60/100 | WO-N1 (agent key) ต้องตั้ง N00-K ก่อนทำต่อ · dual review ต้องผ่าน acceptance ก่อนอ้าง |

คำตอบต่อคำถาม "ทีม AI ของ SetBox" จึงหมายถึง **Team Agent** ซึ่งตามสถาปัตยกรรมตอนนี้ไม่ใช่ MyAI

## 3. เทียบตามแบบ 8 ชั้น

| ชั้น | dots | MyAI + Team Agent วันนี้ (ตามเอกสาร) | ผลเทียบ |
|---|---|---|---|
| 1 เป้าหมาย/ความรับผิดชอบ | รับ "responsibility" ต่อเนื่อง | Team Agent ช่วยงานตามคำสั่งและใบงาน ยังไม่มีวัตถุ "ความรับผิดชอบ" เป็นข้อกำหนด | **dots นำ** |
| 2 การให้เหตุผล | GPT-6 Astra (โมเดลระดับหน้าฉาก) | ขึ้นกับโมเดลที่เลือก ยังไม่พบข้อมูลว่าใช้โมเดลใดและวัดผลอย่างไร | **น่าจะต่ำกว่าหากใช้โมเดลท้องถิ่นขนาดเล็ก** ต้องวัด |
| 3 ความจำ | memory ของ ChatGPT + แอปที่เชื่อม ควบคุมโดยผู้ให้บริการ | ความจำอยู่ใน OneVault/PersonSpace เจ้าของถือ ตัดตามสิทธิ์ (OPOF) | **SPADA/SetBox นำเรื่องความเป็นเจ้าของ** dots นำเรื่องความสะดวก |
| 4 การทำงานต่อเนื่อง | scheduler, background work, subagents | local workflow เดินต่อเมื่ออินเทอร์เน็ตขาด (ตามมาตรฐาน 108/095) แต่ยังไม่พบ scheduler/trigger แบบเชิงรุกเป็นมาตรฐาน | **dots นำ**; SetBox ได้เปรียบเรื่องทำงานออฟไลน์ |
| 5 คอมพิวเตอร์ | cloud computer + local (เมื่ออนุญาต) | SetBox คือคอมพิวเตอร์ของกิจการเอง | **SetBox นำเรื่องอธิปไตยการรัน** |
| 6 เครื่องมือ/แอป | 4,000+ connector, browser, Codex | connector น้อยกว่ามาก ต้องสร้างเอง | **dots นำมาก** |
| 7 การควบคุมโดยมนุษย์ | custom rules 4 ระดับ | actor assertion ลงนามผูกเนื้อหา (payloadDigest, nonce) พิสูจน์ได้ฝั่ง server | **SPADA นำเรื่องความน่าเชื่อถือของหลักฐาน** dots นำเรื่อง UX |
| 8 การสื่อสาร | ChatGPT, Slack, email, text | ผ่านแอป/ช่องทางของ SetBox และ notification-service | dots นำ |

**สรุปการเทียบ**: ยังไม่ "ใกล้เคียง" ในเรื่องความสามารถของตัวเอเจนต์ (ชั้น 1, 2, 4, 6, 8) แต่ "ต่างกันในทิศทางที่ SPADA ได้เปรียบ" ในเรื่องเจ้าของข้อมูล การรันที่เจ้าของคุม และหลักฐานที่ตรวจสอบได้ (ชั้น 3, 5, 7)

## 4. ความต่างเชิงหลักการที่ควรใช้เป็นจุดยืน

| คำถาม | dots | SPADA/SetBox |
|---|---|---|
| ใครเป็นเจ้าของ agent และ memory | ผู้ให้บริการแพลตฟอร์ม (ผู้ใช้ reset ได้) | เจ้าของตัวตน/กิจการ |
| การรันอยู่ที่ไหน | คลาวด์ผู้ให้บริการ (local เป็นทางเลือก) | กล่องของกิจการ (cloud เป็นทางเลือก) |
| ตัวตนของเอเจนต์ | เอเจนต์มี identity ในแพลตฟอร์ม | เอเจนต์ไม่มี identity ของตัวเอง ทุกอย่างเป็นลายเซ็นของเจ้าของ |
| หลักฐานการอนุมัติ | บันทึกในแพลตฟอร์ม | ลายเซ็นผูกเนื้อหา ตรวจซ้ำได้ นอกแพลตฟอร์ม |
| ข้อมูลที่เรียนรู้แล้วหลังถอดแอป | ต้อง reset ทั้ง dot | ออกแบบให้ผูกกับเจ้าของรายเรื่อง (ต้องพิสูจน์ด้วยการทดสอบ) |

## 5. แนวทางปรับใช้และทำให้ดีกว่า

**หลักการ: อย่าแข่งเรื่องความฉลาดของโมเดลหรือจำนวน connector ให้แข่งเรื่อง "เอเจนต์ที่เจ้าของคุมและพิสูจน์ได้"**

1. **เพิ่มวัตถุ `Responsibility` เป็นข้อกำหนด** เก็บใน OneVault: เป้าหมาย, ขอบเขตข้อมูล, ตารางเวลาและ trigger, ระดับอิสระ (Assistant/Agent/Steward), เงื่อนไขส่งต่อมนุษย์, เจ้าของ และวันหมดอายุ ให้ Team Agent ทำงานจากวัตถุนี้ ไม่ใช่จาก prompt เดี่ยว
2. **กำหนดระดับอิสระตามความย้อนกลับได้** สอดคล้อง D2.1: Steward ได้เฉพาะงานย้อนกลับได้ (ร่างเอกสาร ค้นข้อมูล จัดคิว) งานที่ย้อนกลับไม่ได้ (จ่ายเงิน ส่งสัญญา แชร์ข้อมูลออกนอกกิจการ) ต้องมี actor assertion ของเจ้าของเสมอ
3. **ทำ policy engine 4 ทางแบบ dots แต่เพิ่มหลักฐาน**: ทำได้เลย / ทำได้ถ้าอนุมัติล่วงหน้า / ถามก่อน / ส่งต่อมนุษย์ โดยสองข้อหลังผลิตลายเซ็น ผูก `payloadDigest` และเก็บใน OneVault
4. **เพิ่ม scheduler และ trigger เชิงเหตุการณ์** ให้ Team Agent (เวลา, เอกสารใหม่ใน OneVault, สถานะใบสั่งเปลี่ยน) เป็นช่องว่างตรงๆ เทียบกับ dots
5. **ใช้มาตรฐาน connector แทนการสร้างทีละตัว** (เช่น MCP) แล้วคัดเฉพาะ connector ของงานที่ลูกค้าเป้าหมายใช้จริง 10–20 ตัว ไม่ไล่ตัวเลขหลักพัน
6. **นโยบายเลือกโมเดลแบบผสม**: งานข้อมูลอ่อนไหวใช้โมเดลท้องถิ่น งานทั่วไปเรียกโมเดลภายนอกผ่าน `ai-host-gateway` โดยกรองข้อมูล (redaction), บันทึกว่าส่งอะไรออก และให้เจ้าของปิดได้ ต้องวัดคุณภาพจริงก่อนตัดสินว่าโมเดลท้องถิ่นพอหรือไม่
7. **ขั้นตรวจผลบังคับ (verify)**: ผลงานเอเจนต์ผ่านการตรวจโดยเอเจนต์ตัวที่สองหรือมนุษย์ตามความเสี่ยง (ตรงกับแนวคิด dual review ที่ต้องผ่าน acceptance)
8. **ออกแบบการลบและ reset ให้ดีกว่า**: ข้อมูลที่เอเจนต์สรุปหรือจำ ต้องผูกกับแหล่งและเจ้าของ เมื่อเจ้าของถอนสิทธิ์ ต้องลบสรุปที่มาจากแหล่งนั้นได้ นี่คือจุดที่ dots ยอมรับว่าต้อง reset ทั้งตัว
9. **กันการโจมตีแบบ prompt injection** (doc 335 T5): แยก instruction กับ data (กฎเหล็กข้อ 9 ที่ยัง Proposed) ควรเร่งให้ Lead ตัดสินก่อนให้ Steward อ่านอีเมลหรือเว็บภายนอก

## 6. แผนพิสูจน์ (ก่อนอ้างว่า "ใกล้เคียง" หรือ "ดีกว่า")

| ขั้น | งาน | เกณฑ์ผ่าน |
|---|---|---|
| A | เลือกงานจริง 10 งานจากกรณีน้องอิงอร (ตอบอีเมล เตรียมใบเสนอราคา สรุปสต็อก ปิดบัญชีประจำวัน ฯลฯ) | ได้รับความยินยอมและไม่มีข้อมูลลับหลุด |
| B | ให้ Team Agent, dots (ถ้ามีสิทธิ์ทดสอบ) และคนทำงานเดียวกัน 10 งาน | เทียบ: ความถูกต้อง เวลา จำนวนครั้งที่ต้องขอคนช่วย ต้นทุน |
| C | ทดสอบการควบคุม: สั่งงานที่ต้องถามก่อน 20 กรณี รวมกรณีล่อ prompt injection | เอเจนต์ไม่ข้ามด่านในทุกกรณี |
| D | ทดสอบ reset/ถอนสิทธิ์ | ข้อมูลที่ถอนสิทธิ์ไม่ปรากฏในผลงานใหม่ |
| E | บันทึกผลใน SPD-INV-002 (ทะเบียนข้ออ้าง) | ข้ออ้างใดที่ผ่านจึงนำไปใช้ในสไลด์ได้ |

## 7. ข้อเสนอสำหรับการนำเสนอวันที่ 3 ตุลาคม

- ใช้ dots เป็นหลักฐานว่าทิศทาง "เอเจนต์ที่รับผิดชอบงานต่อเนื่อง" เป็นจริงแล้วในตลาด ไม่ใช่ว่าเรา "เหมือนหรือดีกว่า"
- ข้อความที่พูดได้อย่างปลอดภัย: "dots คือเอเจนต์บนคลาวด์ของผู้ให้บริการ ส่วนแนวทางของเราคือทีมเอเจนต์ที่กิจการเป็นเจ้าของและทุกการอนุมัติมีหลักฐานลายเซ็นของเจ้าของ"
- ห้ามอ้างว่าเทียบเท่าหรือดีกว่าในด้านความสามารถ จนกว่าขั้น A–E จะเสร็จ

## 8. คำถามที่ต้องให้ Lead ตัดสิน

1. ให้เพิ่ม `Responsibility` object เป็น ADR/ข้อกำหนดของ OneManOS (นอก SPADA) หรือไม่
2. อนุญาตให้ Team Agent เรียกโมเดลภายนอกหรือไม่ และเงื่อนไขข้อมูลที่ห้ามออก
3. ตัดสิน doc 335 ข้อ 9 (แยก instruction/data) ให้เป็นกฎเหล็กก่อนเปิด Steward
4. เลือกกรณีทดสอบขั้น A และผู้รับผิดชอบ
