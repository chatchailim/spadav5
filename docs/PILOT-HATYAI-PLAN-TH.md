# แผนนำร่อง SPADA Node/Network + OneManOS SetBox ในเมืองหาดใหญ่ (Smart City ประเทศไทย)

**รหัสเอกสาร:** SPD-PLN-001 · **สถานะ:** ร่างเพื่อทบทวน v0.1 (ยังไม่ผ่านที่ปรึกษากฎหมาย ยังไม่มีพันธมิตรในพื้นที่ยืนยัน) · **วันที่:** 2026-10-02
**อ้างอิง:** SPD-CUR-001 (สถานะปัจจุบัน), ADR 0005, 0008, 0014, 0015, 0017, 0020, 0022, 0023, 0024 (Proposed), 0025 (Proposed), PROP-0003 (consent ledger), PROP-0009 (offline/mesh), SPD-MED-004/005/007/008

> **ข้อควรรู้ก่อนอ่าน:** repo นี้ไม่มีข้อมูลเฉพาะพื้นที่หาดใหญ่ เอกสารนี้ออกแบบจากสถาปัตยกรรมของโครงการ ข้อเท็จจริงเรื่องหน่วยงาน กฎหมาย งบประมาณ และสภาพพื้นที่ต้องตรวจกับแหล่งจริงก่อนใช้ ส่วนที่ยังไม่ทราบเขียนเป็น **[●]** ไม่มีการกำหนดตัวเลขลงทุนหรือผลตอบแทนในเอกสารนี้ และไม่ใช่คำปรึกษากฎหมาย

---

## 1. วัตถุประสงค์และขอบเขต

**วัตถุประสงค์:** พิสูจน์ว่า SPADA Node/Network และ SetBox สร้างประโยชน์ที่วัดได้ให้ประชาชนและหน่วยงานท้องถิ่นในหาดใหญ่ โดยข้อมูลยังเป็นของเจ้าของ ภายในเวลา 12 เดือน และด้วยความเสี่ยงที่ควบคุมได้

**อยู่ในขอบเขต:** Community Node หนึ่งแห่ง, SetBox สำหรับองค์กรนำร่อง, ตัวตน/consent ของสมาชิกนำร่อง, Use Case 1–2 ที่เลือกในข้อ 4
**อยู่นอกขอบเขต:** การแทนที่ระบบ Smart City เดิมของเมือง, การเก็บข้อมูลประชาชนโดยไม่มี consent, ระบบเตือนภัยทางการ (ต้องยังเป็นหน้าที่ของหน่วยงานที่มีอำนาจตามกฎหมาย), การเปิดค่า `APPLIANCE` ก่อน device attestation จบ (ADR 0017)

**ขอบเขตทางสถาปัตยกรรมที่ต้องรักษา (ADR 0014–0016):** OneManOS, OneVault, SetBox, Human Gate, Team Agent อยู่นอก SPADA Node/Network SPADA ให้ตัวตน, consent และหลักฐาน ห้ามเอกสารสื่อสารกับเมืองทำให้เข้าใจว่า SPADA เป็นเจ้าของข้อมูล

## 2. หลักการนำร่อง

1. **เสริม ไม่แทน** ระบบที่เมืองมีอยู่ เราเป็นชั้นตัวตนและ consent ที่ประชาชนควบคุมเอง
2. **เริ่มเล็ก วัดผล แล้วค่อยขยาย** ทุกระยะมีเกณฑ์ผ่าน/หยุด (Gate) ที่เขียนไว้ล่วงหน้า
3. **ข้อมูลเป็นของเจ้าของ** หนึ่งคนหนึ่งแฟ้ม (OPOF) เปิดให้ผู้รับเฉพาะวัตถุประสงค์และช่วงเวลา เพิกถอนได้ มีบันทึกการเข้าถึง
4. **ความจริงก่อนคำสัญญา** สื่อสารเฉพาะสิ่งที่พิสูจน์ได้ ณ วันนั้น
5. **มนุษย์ตัดสินในเรื่องสำคัญ** ใช้ Human Gate และ A/B/C delegation tier ตามที่โครงการกำหนด
6. **ออกได้เสมอ** สมาชิกขอสำเนาและออกจากโครงการได้โดยไม่ถูกลงโทษ (PROP-0010)

### 4.1 ตัวเลือก

## 5. สถาปัตยกรรมนำร่อง

```
ประชาชน/สมาชิก ── MyAI/แอป ── SPADA Node หาดใหญ่ (Community Node, ADR 0005)
                                   │  DID, consent, BookChain (Identity/Trusted/Service/EWallet/AI Books)
                                   │  OIDC: id.spada.network (ADR 0023)
              ┌────────────────────┴───────────────┐
        SetBox ของบริษัทนำร่อง (Use Case A)    [ระยะ 2] SetBox ผู้ประสานงาน/เทศบาล (Use Case B)
        OneVault รหัสท้องถิ่น → ผูก DID ภายหลัง (ADR 0022)
```

| องค์ประกอบ | การตัดสินใจนำร่อง | หมายเหตุ |
|---|---|---|
| Node | Community Node หาดใหญ่ 1 แห่ง ดูแลโดยคณะกรรมการชุมชน | ADR 0005 safeguards รอ community ratification ต้องผ่านก่อนเปิดจริง |
| การระบุที่อยู่ Node | ใช้ DID เป็น canonical, ภูมิภาคเป็น attribute | ADR 0008 |
| SetBox | 3–5 เครื่องในระยะที่ 1 | ติดตั้งตาม ADR 0017 รับรองรุ่นด้วย EK certificate (ADR 0020) ห้ามเปิด `APPLIANCE` จน attestation จบ |
| ตัวตนสมาชิก | DID ผ่าน OIDC ของ SPADA | การรับรองตัวตนจริงจากภาครัฐ: ดู U4 |
| Consent | PROP-0003 consent ledger, grantee เป็น discriminated union (ADR 0018) | consent รายวัตถุประสงค์ รายช่วงเวลา เพิกถอนได้ |
| ความทนทาน | ออกแบบโหมดออฟไลน์/mesh สำหรับภาวะน้ำท่วม (PROP-0009) | Use Case B เท่านั้น ยังเป็น Proposal |
| TrustScore | **ไม่ใช้ gate ตัวเลขในนำร่อง** จนกว่า ADR 0024 ได้ข้อสรุป | หลีกเลี่ยงสัญญาที่ผูกกับค่ายังไม่ตัดสิน |
| ฮาร์ดแวร์ KeySign | ใช้เฉพาะรุ่นที่ Lead ตัดสินแล้ว | อย่านำ ESP32-C3 ไปแสดงต่อนักลงทุนจนกว่าจะตัดสิน (SPD-MED-007) |

## 6. แผนตามระยะ

### ระยะ 0 — เตรียมความพร้อม (เดือนที่ 1–2)

| งาน | ผลลัพธ์ | เกณฑ์เสร็จ |
|---|---|---|
| ตั้งทีมนำร่องและผู้รับผิดชอบหลัก | ผู้นำโครงการ, ผู้ประสานพื้นที่, ผู้ดูแลระบบ, DPO | ลงชื่อรับบทบาทแล้ว |
| ตรวจ U1–U5 | บันทึกคำตอบพร้อมแหล่งอ้างอิง | ทุกข้อมีคำตอบหรือมีเหตุผลที่ข้าม |
| จ้างที่ปรึกษากฎหมายและทำ DPIA | รายงาน DPIA และข้อกำหนด PDPA | ผ่านการตรวจโดยบุคคลที่มีคุณวุฒิ |
| คัดเลือกพันธมิตร Use Case A (2–3 ราย) | บริษัท/สำนักงานที่ยินดีเข้าร่วม | หนังสือแสดงเจตจำนงจาก ≥ 2 ราย |
| ตั้งคณะกรรมการชุมชนและร่างกติกา Node | กติกา ratification ตาม ADR 0005 | ผ่านการประชุมชุมชนและบันทึกมติ |
| ขออนุญาตและชี้แจง "น้องอิงอร" และผู้ถูกอ้างถึงในสื่อ | หลักฐานการอนุญาต | ลายลักษณ์อักษร |

**Gate 0:** มีคำตอบ U2/U3 เป็นลายลักษณ์อักษร + DPIA ผ่าน + คณะกรรมการชุมชนตั้งแล้ว ไม่ผ่านข้อใดให้หยุด ไม่เริ่มระยะ 1

### ระยะ 1 — นำร่อง Use Case A (เดือนที่ 2–5)

| สัปดาห์ | กิจกรรม |
|---|---|
| 1–3 | เตรียมและทดสอบฮาร์ดแวร์ (WO-HWQ-001), ติดตั้ง SetBox 3–5 เครื่อง, ตรวจ attestation |
| 3–5 | ลงทะเบียนสมาชิกนำร่อง 30–100 ราย, อบรมผู้ใช้, ทดสอบ consent/เพิกถอนกับข้อมูลทดสอบ |
| 5–14 | ใช้งานจริงด้วยข้อมูลขอบเขตจำกัด, ประชุมทบทวนรายสัปดาห์, บันทึกเหตุการณ์ผิดปกติ |
| 14–16 | สรุปผลและประเมินกับคณะกรรมการ |

**Gate 1 (เกณฑ์ผ่านเสนอ ต้องปรับตามจริงก่อนใช้):**
- ไม่มีเหตุการณ์ข้อมูลรั่วไหลระดับรุนแรงตลอดช่วง
- ผู้ใช้อย่างน้อย [●]% ทำงานหลักสำเร็จโดยไม่ต้องช่วยเหลือ
- ลดเวลา/ข้อผิดพลาดเทียบฐานก่อนนำร่องอย่างน้อย [●]% (ฐานต้องวัดก่อนเริ่ม)
- การเพิกถอน consent มีผลภายในเวลาที่กำหนด [●] ในการทดสอบทุกครั้ง
- ผู้ใช้อย่างน้อย [●]% ยินดีใช้ต่อ

### ระยะ 2 — เตรียมและทดลอง Use Case B (เดือนที่ 5–10)

เริ่มเมื่อผ่าน Gate 1 และมีหน่วยงานที่มีอำนาจตกลงร่วมแล้วเท่านั้น

1. ทำข้อตกลงบทบาท: ระบบของเราเป็น "ทะเบียนความช่วยเหลือโดยสมัครใจ" ไม่ใช่ระบบเตือนภัยทางการ และไม่รับประกันการช่วยเหลือ
2. ออกแบบ consent เฉพาะช่วงเหตุ: ปกติผู้ประสานงานเห็นเพียงจำนวนรวม เมื่อเหตุการณ์ประกาศโดยหน่วยงานที่มีอำนาจ จึงเปิดข้อมูลรายบุคคลตามขอบเขตและมีบันทึกการเข้าถึงทุกครั้ง
3. ซ้อมสถานการณ์จำลอง (tabletop) อย่างน้อย 1 ครั้ง และทดสอบโหมดออฟไลน์/mesh (PROP-0009)
4. กำหนดผู้ประสานงานที่ผ่านการรับรอง อบรม และมีสัญญารักษาความลับ
5. ผู้ที่ไม่ตอบกลับหรือไม่มีสัญญาณต้องไม่ถูกตีความว่าปลอดภัย

**Gate 2:** ที่ปรึกษากฎหมายรับรองโครงสร้างความรับผิด + ผ่านการซ้อม + หน่วยงานที่มีอำนาจลงนามเป็นลายลักษณ์อักษร ไม่ครบให้ทำเป็นเอกสารต้นแบบเท่านั้น ไม่เปิดใช้จริง

### ระยะ 3 — ขยายและถ่ายโอนการดูแล (เดือนที่ 10–12 เป็นต้นไป)

- รายงานผลสาธารณะตามข้อ 9
- ตัดสินใจร่วมกับคณะกรรมการ: ขยายพื้นที่/Use Case ใหม่, ปรับกติกา, หรือหยุด
- ถ่ายโอนการดูแล Node จากทีมโครงการสู่ชุมชนตาม ADR 0005 ตามกติกาที่ ratify แล้ว

## 7. ข้อมูล ความเป็นส่วนตัว และ PDPA (เช็กลิสต์)

ต้องให้ที่ปรึกษากฎหมายและ DPO ยืนยันทุกข้อก่อนเริ่มระยะ 1

- [ ] ระบุบทบาท data controller / joint controller / processor ของ ทีมโครงการ, Node, บริษัทนำร่อง, หน่วยงานรัฐ
- [ ] ระบุฐานทางกฎหมายรายกิจกรรม (ความยินยอมโดยชัดแจ้ง, ภารกิจสาธารณะ, ประโยชน์สำคัญต่อชีวิต) และเงื่อนไขพิเศษของข้อมูลอ่อนไหว (สุขภาพ)
- [ ] ประกาศความเป็นส่วนตัวภาษาไทยที่อ่านเข้าใจง่าย มีวัตถุประสงค์ ระยะเวลาเก็บ ผู้รับข้อมูล สิทธิของเจ้าของข้อมูล
- [ ] กลไกใช้สิทธิ: ขอดู/ขอสำเนา/แก้ไข/ลบ/ถอนความยินยอม พร้อมเวลาตอบสนองตามกฎหมาย
- [ ] นโยบายเด็กและผู้ไม่มีความสามารถทำนิติกรรม (ผู้แทนโดยชอบธรรม)
- [ ] การโอนข้อมูลข้ามพรมแดน (ถ้ามี โฮสต์หรือผู้ให้บริการต่างประเทศ)
- [ ] ขั้นตอนแจ้งเหตุละเมิดข้อมูลภายในเวลาที่กฎหมายกำหนดและแผนสื่อสาร
- [ ] การเก็บข้อมูลขั้นต่ำ: ไม่เก็บพิกัดละเอียดหรือสถานะสุขภาพในระยะ 1
- [ ] ข้อมูลทดสอบต้องเป็นข้อมูลสังเคราะห์จนกว่า DPIA ผ่าน
- [ ] BookChain เป็น append-only: ออกแบบให้เก็บเฉพาะ hash/หลักฐาน ไม่ใส่ข้อมูลส่วนบุคคลดิบในบันทึกที่ลบไม่ได้ เพื่อไม่ขัดสิทธิในการลบ (ต้องให้ผู้ออกแบบ ADR 0006 ยืนยัน)

## 10. การกำกับดูแลและบทบาท (RACI เบื้องต้น)

R = ผู้ลงมือ, A = ผู้รับผิดชอบสุดท้าย, C = ปรึกษา, I = รับทราบ

| งาน | Lead | ผู้นำนำร่อง | ผู้ประสานพื้นที่ | วิศวกร/ผู้ดูแลระบบ | กฎหมาย/DPO | คณะกรรมการชุมชน |
|---|---|---|---|---|---|---|
| ตัดสิน Use Case และ Gate | A | R | C | C | C | C |
| ติดตั้งและดูแล SetBox/Node | I | A | I | R | C | I |
| ลงทะเบียนและอบรมสมาชิก | I | A | R | C | C | I |
| PDPA/DPIA และสัญญา | A | R | I | C | R | I |
| เหตุการณ์ละเมิดข้อมูล | A | R | C | R | R | I |
| ratify กติกา Node | C | C | C | I | C | A |
| รายงานผลสาธารณะ | A | R | C | C | C | C |

การตัดสินใจที่เป็นของ Lead (ไม่ใช่ Claude หรือ agent อื่น): ลงนาม MOU/สัญญา, เปิดข้อมูลจริง, เปิด Use Case B, ใช้งบ

## 12. การสื่อสาร

## 14. การตัดสินใจที่ต้องการจาก Lead

1. อนุมัติให้เริ่มระยะ 0 และจัดสรรผู้รับผิดชอบ
2. ยืนยัน Use Case A เป็นก้าวแรก (หรือเลือกอย่างอื่นด้วยเหตุผล)
3. ยืนยันว่าไม่ลงนามสัญญาก่อนมีคำตอบทางกฎหมาย
4. สถานะ ADR 0024/0025 และชิปของ KeySign: ตัดสินได้เมื่อใด
5. งบเริ่มต้นสำหรับระยะ 0 และผู้ที่จะเป็นที่ปรึกษากฎหมาย
