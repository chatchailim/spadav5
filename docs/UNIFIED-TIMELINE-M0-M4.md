## 1. เป้าหมายเดียวและตัวชี้วัด

**เป้าหมาย:** สมาชิกเป็นเจ้าของตัวตน ข้อมูล และ AI ของตน และได้มูลค่าสุทธิเป็นบวก โดยระบบพิสูจน์ได้ ไม่ใช่เพียงสัญญา (SPD-RDM-001 §1, SPD-ECO-001 §1)

ตัวชี้วัดหลัก (ไม่ใช้จำนวน node/ธุรกรรม/ผู้ใช้รวม): สัดส่วนสมาชิกที่มูลค่าสุทธิเป็นบวก · เวลาส่งออกและกู้คืนข้อมูลเมื่อเลิกใช้ · ความหน่วงเพิกถอน consent · ธุรกรรมฉ้อโกงที่ถูกหยุด · จำนวนข้อมูลข้ามเจ้าของ (เป้าหมาย 0)

## 2. ภาพมาตรฐาน (ตาม ADR 0014/0016 และ SPD-ANL-003 §5)

```text
           เจ้าของ (Human)
        ┌──────┴──────────────┐
        │                     │
   ┌────▼─────┐        ┌──────▼──────────────────────────┐
   │  MyAI    │        │ OneManOS SetBox (นอก SPADA)      │
   │ (SPADA   │        │  Team Agent ─ MCP ─ OneVault     │
   │  ชั้น 5) │        │  (ทำในนามเจ้าของ ไม่มี DID)       │
   └────┬─────┘        └──────┬──────────────────────────┘
        │  ตัวตน/สิทธิ์/หลักฐาน (OIDC, actor assertion ลายเซ็นเจ้าของ)
        └──────────────┬──────┘
                ┌──────▼───────┐
                │ SPADA Node / │
                │ Network      │
                └──────────────┘
```

MyAI และ Team Agent เป็นผู้ช่วยของเจ้าของคนเดียวกันคนละส่วน เชื่อมกันผ่านเจ้าของและสิทธิ์ ไม่ใช่ผ่านสายบังคับบัญชา

**ข้อสังเกตจากการเทียบต้นฉบับ (รอ Lead ตัดสินว่าจะแก้ที่ใด):**

1. **M4 ไม่ได้นิยามไว้** ทางเลือก: (ก) เพิ่มนิยาม M4 ใน `milestones.md` หรือ (ข) ติดป้าย WO-J ใหม่เป็น M3 (R2) · **คำตัดสิน (2026-10-01, ตามอำนาจที่ Lead มอบใน SPD-DEC-005 รอบ 3): เลือก (ข)** เพราะเนื้องาน (federation + mTLS) เป็นเงื่อนไขของเกณฑ์ M3 อยู่แล้ว และไม่เพิ่มมาตรวัดใหม่ · ข้อความแก้สำหรับผู้ดูแลอยู่ที่ [PATCH-M4-relabel-WO-J](decisions/PATCH-M4-relabel-WO-J.md) · **ยังไม่มีผลใน monorepo** (ผมอ่านอย่างเดียว) จนกว่าผู้ดูแลนำไปใช้ · ในเอกสารนี้ถือว่า WO-J อยู่ใน M3 (R2) และแถว "(M4)" ในตารางหมายถึงเฟสหลัง M3 ของข้อเสนอนี้เท่านั้น
2. **เกณฑ์ M2 แคบกว่าแผนธุรกิจ:** M2 วัดที่ "ชุมชนนำร่องรับสมาชิก + 5/8 บริการ" ไม่ได้วัดว่ามีลูกค้าจ่ายเงินหรือปิด P1 ของ SetBox ดังนั้น **E1 และเงื่อนไขปลดงวด 2 เป็นเงื่อนไขเสริมของแผนธุรกิจที่ต้องผ่านคู่กับ M2 ไม่ใช่ส่วนหนึ่งของคำนิยาม M2** การจับคู่ในตารางหมายถึงทำในช่วงเดียวกัน ไม่ได้หมายความว่าเป็นเกณฑ์เดียวกัน
3. **ผู้ใช้จริง ≥ 10 ราย** (เงื่อนไขปลดงวด 2) กับ **"5 จาก 8 บริการพื้นฐาน"** (M2) เป็นคนละมาตรวัด ควรกำหนดนิยามของ "ผู้ใช้จริง" ในสัญญาให้สอดคล้องกับชุมชนนำร่องของ M2 เพื่อไม่ให้วัดสองครั้ง
4. **เกณฑ์ตรวจรับเฉพาะของ M2/M3 ที่อยู่ในใบงาน** (เช่น "ต้องปิด P1/GAP-04/05 ก่อนขายจริง") มาจาก ADR ใบงาน และผลตรวจ ไม่ได้อยู่ใน `milestones.md` ดูเส้นทางวิกฤตในข้อ 5

**การอ่านตาราง:** เดือนในคอลัมน์เงินทุนนับจากวันโอนงวด 1 (ไม่ใช่วันที่ปฏิทิน) แกน M คือแกนผลิตภัณฑ์ ทั้งสองเส้นต้องผ่านเงื่อนไขทางเทคนิคชุดเดียวกันก่อนขายจริง จึงลดงานซ้ำซ้อนได้

## 6. เส้นทาง Team Agent (F0–F4) และกฎถาวร

เฟสและเกณฑ์ตามข้อ 4 ของ SPD-ANL-002 (ไม่แก้) · **กฎถาวรที่ Lead อนุมัติ (SPD-DEC-005 ข้อ 6):**

1. ไม่เปิดการเขียนหรืออนุมัติอัตโนมัติของเอเจนต์ จนกว่าเส้นทาง UI/CLI → อุปกรณ์เจ้าของ → actor assertion ที่ SPADA ยอมรับจะมีหลักฐานครบ (A6) และ human gate พิสูจน์ตัวตน ไม่ใช่ตรวจรูปแบบชื่อบัญชีเท่านั้น
2. "อิสระภายในวงเงิน" ใช้ได้เฉพาะ operation ที่ **ย้อนกลับได้จริง** (D2.1) งานอื่นต้องมีลายเซ็นเจ้าของผูกเนื้อหา
3. Team Agent ไม่มี DID ของตัวเอง ทำในนามเจ้าของ (ADR 0016) ห้ามยกฟังก์ชันของ Team Agent เข้ามาไว้ใน SPADA
4. Event/Decision เป็นชนิดใหม่ของ OneVault ต้องไม่กระทบ Fact v0 (POO-WO-002) และสัญญา C2 (fact hash) ต้องผ่านใบงานและ ADR ฝั่ง OneManOS
5. ไม่บอกลูกค้าหรือนักลงทุนว่า "ทำเหมือน dots" จนกว่าผ่านแผนพิสูจน์ใน SPD-ANL-001 ข้อ 6
