## บริบท

ADR 0020 กำหนดว่าเครื่องจะติดตั้ง SetBox ได้ต่อเมื่อรุ่นนั้นผ่านการรับรองและอยู่ในทะเบียนฮาร์ดแวร์ โดยเกณฑ์คือ EK certificate ไม่ใช่ชนิด TPM ADR นี้เขียนจากมุมที่ SPADA ออกสิทธิ์ติดตั้งและตัดสิน `deviceAssurance` (ADR 0017)

แต่ตามที่ Lead ระบุ **มีความเป็นไปได้ทั้งสองแบบ** และมีเหตุผลต่างกัน:

- **Track S**: ติดตั้ง OneManOS SetBox แบบ **ไม่เชื่อม SPADA** (ตามที่ README ของ SetBox ออกแบบ: ทำงานบนเครื่องเดียว ไม่ต้องต่ออินเทอร์เน็ต ไม่มี dependency ภายนอก)
- **Track C**: ติดตั้งแบบ **เชื่อม SPADA** ผ่าน `ProvisioningClaim`, api-gateway, WorkSpace (ADR 0017, doc 340)

ADR 0014 ตัดสินว่า OneManOS/OneVault/SetBox อยู่นอก SPADA ดังนั้นถ้าให้ Attestation Policy Steward ของ SPADA ตัดสินเครื่อง Track S ทุกเครื่อง จะเป็นการให้ SPADA กำกับสิ่งที่อยู่นอกขอบเขตของตนและเพิ่มภาระเกินจำเป็น ในทางกลับกัน หากไม่มีเกณฑ์ฮาร์ดแวร์เลยใน Track S ก็เสี่ยงต่อข้อมูลลูกค้าและอาจต้องเปลี่ยนเครื่องเมื่อลูกค้าต้องการเชื่อม SPADA ภายหลัง

## เหตุผลที่ต้องมีเกณฑ์ฮาร์ดแวร์ ต่างกันตามเส้นทาง

| | Track S (ไม่เชื่อม SPADA) | Track C (เชื่อม SPADA) |
|---|---|---|
| ใครได้รับผลกระทบถ้าเครื่องถูกแก้ไขแฝงหรือ TPM ปลอม | เจ้าของกิจการรายนั้น (ข้อมูลบัญชี ภาษี เงินเดือน) | สมาชิกอื่นและ node ที่ไว้วางใจ device record และ attestation |
| ทำไมต้องมี TPM จริง | เก็บผูกกุญแจเข้ารหัสดิสก์/ความลับของระบบกับเครื่อง ตรวจการแก้ไขระดับบูต | เป็นราก attestation ของอุปกรณ์ที่ SPADA ตัดสิน `deviceAssurance` |
| ทำไมปฏิเสธ vTPM | ไม่ให้ความคุ้มครองฮาร์ดแวร์จริง | ไม่มีรากฮาร์ดแวร์เลย (ADR 0020) |
| EK certificate | ไม่จำเป็นต่อการทำงาน | จำเป็นต่อ `APPLIANCE` (ปัจจุบันยังบล็อก) |
| ผู้มีอำนาจกำกับ | ฝั่ง OneManOS | SPADA (Attestation Policy Steward) |
| ผลของความล้มเหลว | จำกัดในกิจการเดียว แต่กระทบชื่อเสียงและสัญญากับลูกค้า | อาจกระทบความไว้วางใจของเครือข่าย |

## ข้อเสนอการตัดสินใจ

1. **เกณฑ์ฮาร์ดแวร์ฐานเดียว สองเส้นทางกำกับ**: ทุกรุ่นที่ขายในชื่อ SetBox ต้องผ่านเกณฑ์ฐาน **HB** = ระดับ 🟡 NATIVE-ELIGIBLE ของ ADR 0020 §2 คือ TPM 2.0 บนฮาร์ดแวร์จริง (vTPM ปฏิเสธ), Secure Boot เปิดและอยู่ใน user mode, PCR bank SHA-256 ครบ, อ่าน event log ได้, ปิดช่องดีบักถาวรได้ · เหตุผลที่ใช้ฐานเดียว: เครื่อง Track S จะเชื่อม SPADA ภายหลังได้โดยไม่ต้องเปลี่ยนเครื่อง
2. **Track C = ADR 0020 เต็มรูปแบบ ไม่เปลี่ยน**: ต้องอยู่ในทะเบียน (doc 344) ห้ามข้อยกเว้น ผู้กำกับคือ Attestation Policy Steward
3. **Track S = กำกับโดยฝั่ง OneManOS**: ผู้กำกับคือ Technical Owner ของ SetBox Factory WorkSpace (NextWaver.Net ตาม doc 340 §10) ใช้ขั้นตอนวัดและสคริปต์ชุดเดียวกับ Track C แต่การรับรองบันทึกเป็น "ผ่าน HB" และ **SPADA ไม่อ่านและไม่รับรอง** (สอดคล้อง doc 340 §11 และ ADR 0014) **เก็บเป็นทะเบียนแยกจากของ SPADA (doc 344)** ตามทิศทางของ Lead (ดูหัวข้อทะเบียนสองฝั่งและขั้นตอนรวมด้านล่าง)
4. **เงื่อนไขเพิ่มเฉพาะ Track S** (จากผลตรวจความพร้อม SetBox 2026-09-06 ที่ยังเป็น CONDITIONAL): ตรวจ signature/manifest แบบ fail-closed เมื่อติดตั้ง, เปิดการเข้ารหัสดิสก์ทั้งลูกและเก็บ recovery key ที่ลูกค้าถือ, บังคับ preflight ก่อนส่งมอบ, ผ่านตรวจ H1–H7 และซ้อมกู้คืน backup จริงก่อนส่งมอบ
5. **สัญญาและการสื่อสารกับลูกค้า**: Track S ต้องระบุชัดว่า "ไม่ได้รับ `deviceAssurance` หรือการรับรองใดจาก SPADA" และการเชื่อม SPADA ภายหลังต้องผ่านการรับรองรุ่นตามทะเบียนและ provision ด้วย `ProvisioningClaim` ใหม่ (ADR 0017 §7.3–7.4)
6. **ห้ามใช้ชื่อหรือแนวคิด `T1/T2/T4-S` ใน SPADA** เหมือนเดิม (doc 340 §11) และ "Track S/C" ในเอกสารนี้ **เป็นคำเชิงจัดซื้อ/ปฏิบัติการ** ไม่ใช่คำใน schema หรือ API ของ SPADA

## ทะเบียนสองฝั่งและการรวมภายหลัง

**สองชุดแยกกัน:**

| ทะเบียน | เจ้าของ | อยู่ที่ | ขอบเขต |
|---|---|---|---|
| **ทะเบียนฮาร์ดแวร์ฝั่ง SPADA** (Track C) | Attestation Policy Steward | `spada-monorepo` doc 344 (มีอยู่แล้ว ว่างเปล่า) | เครื่องที่จะเชื่อม SPADA · เกณฑ์ ADR 0020 เต็ม |
| **ทะเบียนฮาร์ดแวร์แบบเดี่ยว** (Track S) | ผู้ลงนาม Track S (ตอนนี้: ฉัตรชัย) | ฝั่ง OneManOS (`onemanos-setbox` หรือที่ Lead กำหนด) แม่แบบร่าง: [HARDWARE-REGISTRY-STANDALONE-TEMPLATE](../procurement/HARDWARE-REGISTRY-STANDALONE-TEMPLATE.md) | เครื่องที่ขายโดยไม่เชื่อม SPADA · เกณฑ์ฐาน HB |

ทั้งสองชุดเป็น **append-only** (ถอนรุ่น = เพิ่มรายการใหม่ ห้ามลบ) และใช้ขั้นตอนวัดชุดเดียวกัน (doc 344 §3) ต่างกันที่ผู้ลงนามและสิทธิ์ที่ได้

**รวมกันเมื่อไร (เงื่อนไขที่แนะนำตามทิศทางของ Lead):**

1. ลูกค้า/กิจการเจ้าของเครื่องได้ **ลงทะเบียนเป็นสมาชิกใน SPADA Node/Network** (มี DID ตัวตนของบุคคลหรือองค์กรตามระบบจริง) และ **ต้องการเชื่อมเครื่องเข้า SPADA**
2. รุ่นและเวอร์ชัน BIOS/TPM firmware ของเครื่องนั้นต้องผ่านการวัดตามเกณฑ์ ADR 0020 ที่ระดับอย่างน้อย NATIVE-ELIGIBLE โดยผู้ลงนามฝั่ง SPADA (Attestation Policy Steward) **วัดหรือทบทวน evidence ของเครื่องจริงนั้น** ไม่คัดลอกผลจากทะเบียนฝั่งเดียวโดยไม่ตรวจ (ถ้า evidence เดิมยังตรงกับ BIOS และ TPM firmware เดียวกัน ให้ทบทวน evidence hash แทนการวัดใหม่ได้ ตามดุลยพินิจ Steward)
3. เพิ่มรายการในทะเบียนฝั่ง SPADA เป็นรายการใหม่ที่อ้างรายการเดิมของทะเบียนแบบเดี่ยว (ไม่ย้ายหรือลบของเดิม)
4. provision ด้วย `ProvisioningClaim` ใหม่ (ADR 0017 §7.3–7.4) เพราะไม่มี host attestation เดิมให้โอน
5. หลังรวมแล้ว เครื่องนั้นอยู่ภายใต้กติกา Track C ทุกข้อ (BIOS เปลี่ยน = รับรองใหม่, เพิกถอนโดย Approver ของ WorkSpace เจ้าของกล่อง)

**"รวม" ในความหมายนี้ = เครื่องรายตัวย้ายเข้าทะเบียน Track C ได้เมื่อผ่านเงื่อนไข ไม่ได้แปลว่าผสมสองทะเบียนเป็นไฟล์เดียวทั้งหมด** ถ้า Lead ต้องการผสมสองทะเบียนเป็นชุดเดียวในอนาคต ให้ทำเป็นการตัดสินใจแยกเมื่อเครือข่ายมีหลาย node แล้ว เพราะต้องกำหนดสายอำนาจใหม่

**เครื่องที่ลูกค้ามีอยู่แล้ว (Track S อนุมัติทีละกรณี):**

| ขั้น | ต้องทำ |
|---|---|
| 1 | ลูกค้าส่งรุ่น/serial/BIOS ให้ตรวจก่อนตกลงสัญญา |
| 2 | วัดเครื่องจริง 10 ข้อ (doc 344 §3) ห้ามอนุมัติจากคำบอกเล่าหรือเอกสาร |
| 3 | ระดับต้องไม่ต่ำกว่า HB (NATIVE-ELIGIBLE) ไม่เช่นนั้นปฏิเสธ (ทางเลือก: ลูกค้าเปลี่ยนเครื่อง) |
| 4 | ผู้ลงนาม Track S บันทึกรายการเดี่ยวในทะเบียนแบบเดี่ยว พร้อมเหตุผลและ hash ของ evidence |
| 5 | ล้างเครื่องและติดตั้งระบบใหม่จาก image ที่เซ็นแล้ว ล็อก BIOS ตามเวอร์ชันที่วัด |
| 6 | ลูกค้าลงนามรับทราบว่าเป็นเครื่องของลูกค้าเอง ไม่ใช่ล็อตที่ผู้ให้บริการรับรองทั้งรุ่น และรับทราบข้อจำกัด Track S (ไม่ได้รับการรับรองจาก SPADA) |
| 7 | การอนุมัติเป็นรายกรณี ไม่ขยายผลเป็นรุ่นอื่นโดยอัตโนมัติ |

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **ก. (เสนอ) เกณฑ์ฐานเดียว สองเส้นทางกำกับ** | ไม่ต้องเปลี่ยนเครื่องเมื่ออัปเกรด, รักษาขอบเขต ADR 0014, ต้นทุนรับรองรอบเดียว | ต้องมีผู้ลงนามสองสาย และต้องคุมการสื่อสารสัญญาให้ชัด |
| ข. ให้ ADR 0020 ครอบคลุมทุกเครื่อง | ง่าย มีที่เดียว | ขัดขอบเขต ADR 0014 ขยายภาระ Steward ของ SPADA ไปกับลูกค้าที่ไม่เชื่อม SPADA |
| ค. ไม่มีเกณฑ์ใน Track S | ถูกและเร็ว | เสี่ยงข้อมูลลูกค้า เครื่องเชื่อม SPADA ภายหลังไม่ได้ ต้องเปลี่ยนเครื่อง ขัดหลัก "ข้อมูลเป็นของกิจการ" ของ SetBox |
| ง. เกณฑ์ Track S ต่ำกว่า HB (เช่น ไม่ต้องมี TPM) | ตลาดเครื่องกว้างและถูกกว่า | ต้องไม่อ้างการป้องกันระดับบูต และอัปเกรดไป Track C ไม่ได้ (ต้องเปลี่ยนเครื่อง) |

## ผลที่ตามมา

**ข้อดี**: กติกาเดียวเห็นง่าย ไม่ล็อกเครื่องลูกค้า และรักษาขอบเขต SPADA/OneManOS
**ข้อเสีย/ต้นทุน**: ต้องกำหนดผู้ลงนามฝั่ง Track S ต้องมีสคริปต์รับรองฮาร์ดแวร์ (doc 344 ระบุว่ายังไม่มี ต้องมี WO) และทะเบียนยังว่างจึงยังไม่มีรุ่นใดขายได้ตามกติกาไม่ว่า Track ใด
**ความเสี่ยง**: ลูกค้าเข้าใจผิดว่า Track S ได้รับการรับรองจาก SPADA (ลดด้วยสัญญาและข้อความบนเอกสารส่งมอบ) · การใช้ทะเบียนร่วมอาจทำให้ผู้ลงนามสับสนถ้าไม่ระบุสายอำนาจชัดเจน

## ข้อกำหนดเรื่องเครื่องที่ลูกค้ามีอยู่แล้ว

ADR 0020 ห้าม "เครื่องที่ลูกค้ามีอยู่แล้ว" โดยไม่มีข้อยกเว้น (Track C) สำหรับ Track S ผมเสนอให้ **ใช้กฎเดียวกันเป็นค่าเริ่มต้น** แต่เปิดทางให้ Lead อนุมัติทีละกรณี เมื่อรุ่นและ BIOS ผ่านการวัดตามเกณฑ์ HB จริงและบันทึกผลแล้ว (ไม่ใช่รับรองจากเอกสาร) ถ้า Lead ต้องการความเข้มเท่ากันทั้งสองเส้นทาง ให้ตัดข้อนี้ออก

## เกณฑ์ตรวจรับของการตัดสินใจนี้

- ระบุผู้ลงนามของแต่ละ Track ในเอกสารกำกับ (ชื่อจริง)
- ทะเบียนฮาร์ดแวร์มีคอลัมน์ "Track ที่เหมาะสม" และยังเป็น append-only
- สัญญามาตรฐานของ Track S มีข้อความไม่อ้างการรับรองจาก SPADA
- มี WO สคริปต์รับรองฮาร์ดแวร์ที่ใช้ได้ทั้งสองเส้นทาง
