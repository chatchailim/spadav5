## ข้อ 1: ถามผู้ขายเรื่อง dTPM/fTPM (ค้างมา 10–11 รอบ)

**ข้อเท็จจริง**: ADR 0020 ตัดสินแล้วว่าเกณฑ์คือ **EK certificate ไม่ใช่ชนิดของ TPM** · ห้ามรับมอบใบเสนอราคาก่อนได้คำตอบเป็นลายลักษณ์อักษร (D11) · vTPM ถูกปฏิเสธเสมอ · ทะเบียนฮาร์ดแวร์ (doc 344) ยังว่าง

**ข้อสังเกตที่ช่วยลดความกดดัน**: ถ้าเครื่องเป็น fTPM ที่ไม่มี EK certificate จะได้ระดับ 🟡 NATIVE-ELIGIBLE ซึ่ง **เพียงพอสำหรับเฟสนำร่อง** (เพดานระบบตอนนี้ก็คือ `NATIVE`) เสียเพียงสิทธิ์ขยับไป `APPLIANCE` ในอนาคต ไม่ได้ทำให้ติดตั้งไม่ได้

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. ส่งจดหมายถามผู้ขายก่อน แล้วซื้อ 1–2 เครื่องเป็นตัวอย่างเพื่อรับรองรุ่น ก่อนสั่งล็อต (แนะนำ)** | ตรงตาม ADR 0020 ความเสี่ยงเงินน้อยสุด ได้ข้อมูลจริงก่อนตัดสินล็อต | ช้ากว่าสั่งทีเดียว 1–3 สัปดาห์ (ประมาณ) |
| B. บังคับ dTPM ที่มี EK cert ตั้งแต่ต้น | เปิดทาง `APPLIANCE` ในอนาคต | อาจแพงกว่า/หาเครื่องยาก · ไม่จำเป็นในเฟสนี้ |
| C. รับ fTPM ที่ไม่มี EK cert เป็น NATIVE-ELIGIBLE | เร็วที่สุด | ต้องรับรองกันเองว่าจะไม่อ้าง `APPLIANCE` และอาจต้องเปลี่ยนเครื่องภายหลัง |

**คำแนะนำ**: เลือก **A** และตั้งเงื่อนไขในใบสั่งซื้อล็อตว่า "ล็อตต้องใช้ TPM ชนิดและ firmware เดียวกับตัวอย่างที่ผ่านการรับรอง" · ใช้จดหมายที่ร่างไว้ใน [RFQ-VENDOR-LETTER-TH](../procurement/RFQ-VENDOR-LETTER-TH.md) · กฎทั้งหมดอยู่ใน [SETBOX-PROCUREMENT-STANDARD](../procurement/SETBOX-PROCUREMENT-STANDARD.md)

**ต้องมีคนทำ**: ผู้จัดซื้อส่งจดหมาย · Attestation Policy Steward (ปัจจุบันตาม doc 344 คือ Lead เอง) รับรองรุ่นจากการวัด · Hermes ทำสคริปต์รับรองฮาร์ดแวร์ (doc 344 ระบุว่ายังไม่มีและต้องมี WO)

## ข้อ 3: OTP / Secure Boot ของ KeySign (เขียนแล้วย้อนไม่ได้)

**ข้อเท็จจริง**: doc 347 §7 ระบุว่า "เขียน OTP · ล็อก secure boot · ปิด debug" **เขียนแล้วย้อนไม่ได้ ถ้าพลาดคืออุปกรณ์ทิ้ง** · ชิปที่ถือเป็น A4 · ตอนนี้ `debug enable = 1`, `secure boot = 0`, OTP ยังไม่เขียน · ยังไม่ออกแบบ PIN · OTP bit-array vulnerability ยังไม่แก้ใน A4 (มี application note ที่จะออกแนะนำการเก็บความลับใน OTP) · ผ่าน conformance PKT-R1..R10 แล้วในสภาพ **ยังไม่ล็อก**

**คำแนะนำ: ยังไม่ตัดสินให้ล็อก และตั้งขั้นตอนก่อนล็อกไว้ให้ชัด (เลื่อนแบบมีเงื่อนไข ไม่ใช่ปฏิเสธ)**

| ลำดับ | เงื่อนไขก่อนเขียน OTP/ล็อก | เหตุผล |
|---|---|---|
| 1 | **ห้ามทำบนอุปกรณ์ต้นแบบตัวเดียวที่มี** ซื้อเพิ่มอย่างน้อย 3 ตัว เป็นตัวทดลองที่ยอมทิ้งได้ | พลาดแล้วเสียแค่ตัวทดลอง |
| 2 | ซ้อมลำดับล็อกเต็มบนตัวทดลอง พร้อมอ่านกลับยืนยันทุกขั้น และบันทึก evidence | ตามหลัก "วัดก่อนเดา" ของ doc 347 |
| 3 | **ออกแบบ PIN ก่อน** และตัดสินว่า PIN/กุญแจอยู่ตรงไหนใน OTP | ตอนนี้อุปกรณ์หลุดมือ = ถือว่ากุญแจไม่ปลอดภัย (doc 346 §9) |
| 4 | รออ่าน application note ของ Raspberry Pi เรื่องการเก็บความลับใน OTP | doc 345 ระบุว่าจะมี · ผมยังไม่ได้อ่านฉบับนั้น |
| 5 | ให้ผู้เชี่ยวชาญภายนอกทบทวนแผนล็อก (ราคาต่ำเมื่อเทียบกับอุปกรณ์ที่ล็อกผิดจำนวนมาก) | การล็อกผิดพลาดย้อนไม่ได้ |
| 6 | ทำ checklist go/no-go และให้ Lead ลงนามก่อนล็อกล็อตใช้งานจริง | มีร่องรอยความรับผิดชอบ |

**ระหว่างนี้**: ติดป้ายอุปกรณ์ว่า **"ต้นแบบ ห้ามใช้ปกป้องมูลค่าจริง"**, ใช้ได้เพียงยืนยัน user presence ตาม doc 346 และไม่ต้องเปลี่ยนสถานะ `NATIVE`

**ความเสี่ยงของการเลื่อน**: ผู้ใช้ทดสอบอาจเข้าใจว่าปลอดภัยเกินจริง ต้องสื่อสารข้อจำกัดใน doc 346 §9 ให้ชัดเจนทุกครั้ง

## ข้อ 4: ตรวจ ID ที่ใช้ `Math.random` (ผมตรวจเบื้องต้นให้แล้ว)

**ผลการตรวจ (อ่านโค้ด ไม่ได้รัน)**

| จุด | ผลตรวจ | ความเสี่ยง |
|---|---|---|
| `data-share-broker-service` (`shareId`) | การเข้าถึงตรวจ `requesterDid`/`ownerDid` (บรรทัด 128, 158) จึง **ไม่ใช้ ID เป็นสิทธิ์ (bearer)** | ต่ำ |
| `reclaim-connect-service` (`requestId`), `opof-service` (`recordId`, `importId`, `verificationId`) | ใช้ตัวสร้าง ID แบบเดียวกัน · **ผมยังไม่ได้ตรวจว่าการเข้าถึงผูกกับเจ้าของหรือไม่** | ไม่ทราบ ต้องตรวจ |
| `packages/events` (`cryptoSafeId`) | ใช้ `crypto.randomUUID()` ก่อน แต่ **ถ้าไม่มีจะถอยไปใช้ `Math.random` แบบเงียบ** | ต่ำที่ตัว ID แต่ **เป็นรูปแบบเดียวกับ fallback เงียบที่ D1 ห้าม** |
| `apps/member-portal/app.js`, `scripts/ops/incident.mjs` | ใช้ในโหมดจำลอง/รหัสเหตุการณ์ | ต่ำ |

**ข้อเสนอ**: ออกใบงานเล็ก [WO-PROPOSAL S1](../work-orders/WO-PROPOSAL-S1-S3.md) (ตรวจได้เร็ว ประมาณครึ่งวันถึงหนึ่งวัน) เปลี่ยนตัวสร้าง ID ทุกจุดเป็น `crypto.randomUUID()` แบบ fail loud ไม่ถอยเงียบ และเพิ่มกฎ lint ห้าม `Math.random` ในโค้ดที่ไม่ใช่เทสต์

- ผู้ขายและรุ่นเครื่องในใบเสนอราคาปัจจุบัน งบประมาณ และกฎหมายจัดซื้อ/ภาษีที่เกี่ยวข้อง
- ผู้ขายจะตอบได้เร็วเพียงใด (ระยะเวลาที่ให้ในตารางเป็นการประมาณ)
