# บันทึกคำตัดสิน SPD-DEC-006: ADR 0024, 0025, 0026 และ doc 340 §10

- **รหัสเอกสาร: SPD-DEC-006** · 2026-09-30
- ฐานข้อมูล: อ่านข้อความเต็มของ ADR 0024, 0025, 0026, 0016 และ doc 340 ใน `spada-monorepo` @ `206d1f9` (อ่านอย่างเดียว) · **ไม่ได้รันโค้ดหรือเทสต์** · ไม่ได้อ่านโค้ดที่ ADR อ้างถึง ยกเว้นบรรทัดที่อ้างในข้อสังเกต
- **สถานะการตัดสิน:** Lead มอบอำนาจให้ Claude ตัดสินตามความเห็นที่ตรงกันเมื่อ 2026-09-30 ([SPD-DEC-005](APPROVAL-LOG-2026-09-30-FINAL-ADJUSTMENT.md) รอบ 2) บันทึกนี้จึงเป็น **คำตัดสินที่ตัดสินโดย Claude ตามอำนาจที่ได้รับมอบ** ไม่ใช่ลายเซ็นของ Lead · **Lead กลับคำหรือแก้ได้ทุกเมื่อ** · ตามแบบของ ADR 0018–0020 ที่ Cowork ลงนามแทน Lead และ SPD-GAP-001 แนะนำให้ Lead ยืนยันย้อนหลัง ผมแนะนำให้ทำเช่นเดียวกับบันทึกนี้
- **ข้อจำกัดด้านการมีผล:** ผมมีสิทธิ์อ่านอย่างเดียวใน monorepo จึง **ไม่ได้แก้สถานะของ ADR ในนั้น** สถานะใน monorepo ยังเป็น Proposed จนกว่าผู้ดูแล ADR จะนำ "ข้อความแก้ไขสถานะ" ด้านล่างไปใช้ (ต้องตรวจ ACTIVE CLAIMS ก่อนแก้)

## 1. ADR 0024: Genesis ของ TrustScore

**คำตัดสิน: Accept** เหตุผล: โค้ดตามคำตัดสินของ Lead 2026-09-27 merge แล้ว (PR #63) ความเสียหายสูงสุดมีขอบเขตชัด (ไม่เกิน N คนต่อ node, คนละไม่เกิน 500, เปิด AUTONOMOUS 700 หรือ federation 900 ไม่ได้) และตรวจย้อนหลังได้ใน TrustedBook

| คำถามเปิด | คำตัดสิน |
|---|---|
| 1 โควตา 3 คนต่อ node | ใช้ตามข้อเสนอ: 3 สำหรับ node ใหม่ และตั้ง `BCX_TRUST_SCORE_GENESIS_MAX_GRANTS=0` เมื่อมีสมาชิก ≥ 300 จากการใช้งานจริงครบ 3 คน |
| 2 พยานคนที่สอง | ใช้ตามข้อเสนอ (`operatorId` เป็น DID ผู้ดูแล, `reason` อ้างเลขใบงานหรือหนังสืออนุมัติ) **เพิ่มเงื่อนไขของ Claude:** ต้องมีพยานคนที่สองก่อนเปิด node ที่ให้บริการสมาชิกนอกกิจการของผู้พัฒนา (สอดคล้อง SPD-DEC-002 ที่ให้ลดการรวมอำนาจเมื่อมีคนเพิ่ม) |
| 3 เพิกถอน/ปรับลด genesis | ไม่ทำผ่าน genesis ต้องออก ADR แยกเรื่องบทลงโทษ/การลดคะแนน **ก่อนเปิดเครือข่ายให้สมาชิกภายนอก** |
| 4 เปิดเผยรายชื่อ | ใช้ตามข้อเสนอ: แสดงป้าย "genesis" ในประวัติคะแนนของสมาชิกเอง และให้ผู้ดูแลเครือข่ายตรวจจาก TrustedBook ได้ |

**เงื่อนไข:** (ก) ข้อ 3 และพยานคนที่สองข้างต้นเป็นเงื่อนไขก่อนเปิดให้สมาชิกภายนอก (ข) ปัญหา "service ภายในเชื่อ caller ทุกตัวใน compose เดียวกัน" ซึ่ง ADR ระบุเองว่าทำให้การป้องกัน genesis ขึ้นกับการคุมเครื่อง node ต้องมีใบงานแก้แยก (ค) runbook ของ trust-score ต้องมีขั้นตอนปิด genesis

## 2. ADR 0025: Home Node และ Pointer Directory

**คำตัดสิน: Accept ทิศทาง** (หนึ่ง DID มี home node เดียว, สมุดรายชื่อเก็บเฉพาะตัวชี้ที่ home node เซ็น, rendezvous hashing บนทะเบียน node, ย้าย home ด้วย epoch + `transferProof`, checkpoint เข้า consensus แทนเหตุการณ์ราย DID) ตรงกับ ADR 0005 §4, §15 และกฎ 5 Books ข้อ 10 · P1 ลงมือแล้วตามคำสั่ง Lead (ADR บันทึกผลวัดจริง: 200,000 record heap เดิมโต 186 MB ใหม่ 0 MB)

| คำถามเปิด | คำตัดสิน |
|---|---|
| 1 SPADA ID ข้าม node | ใช้ข้อเสนอ: issuer ของ Setbox = home node ของธุรกิจ ส่งต่อการยืนยันไป home node ของสมาชิกผ่าน federation |
| 2 ใครเป็น holder ได้ | ใช้ข้อเสนอ (TrustScore ≥ 900 และ uptime 30 วัน ≥ 99%) **ข้อสังเกต:** genesis จำกัด 500 จึงไม่มี node ใดถึง 900 ด้วย genesis เกณฑ์นี้มีผลเฉพาะโหมด `SHARDED` (> 20 node) ส่วนโหมด `FULL` (≤ 20 node) ทุก node เป็น holder อยู่แล้ว |
| 3 ค่า k และ cache | k = 3, cache 10 นาที ทบทวนหลังวัดจริงในเฟส P3 |
| 4 ผู้รับรองย้าย home เมื่อ node ต้นทางสูญหาย | เลื่อนไป ADR ย่อย (ต้องมีก่อน P4) |
| 5 เพดานสมาชิกต่อ node | 100,000 สำหรับ mini PC เป็นค่าเริ่มต้น ปรับหลังวัดจริง |
| 6 รอบ checkpoint/witness | ทุก 1 ชั่วโมง และ 3 witness ทบทวนหลังวัดจริงในเฟส P7 |
| 7 บทลงโทษ equivocation | ใช้ข้อเสนอ: ระงับสิทธิ์ holder/witness ทันที แล้วเข้ากระบวนการตาม ADR 0005 §3, §7 (อุทธรณ์ได้) |

**เงื่อนไข:** (ก) **ทะเบียน node ที่เซ็นรับรองและกระจายอัตโนมัติ** ต้องมี ADR แยกก่อนเริ่ม P3 (ปัจจุบัน `admission.json` แก้ด้วยมือ) (ข) P2–P8 เป็นใบงานแยก แต่ละเฟสมีเกณฑ์ผ่านตามตารางใน ADR (ค) **ห้ามใช้ตัวเลขขนาด 100 ล้าน DID / 90 MB ต่อ node ในเอกสารภายนอก** เพราะ ADR ระบุเองว่า "ยังไม่ได้วัด" (ง) P8 (ส่ง checkpoint เข้า consensus) รอ CometBFT เข้า node stack

## 3. ADR 0026: แบบของ App (Node App / Setbox App / Hybrid)

**คำตัดสิน: Accept เฉพาะ A1 (Catalog v0) และ A2 (ดูแลรักษา + SLA + เพิกถอน/อุทธรณ์)** ใช้ได้ทันทีเพราะส่วนใหญ่ต่อยอดของเดิม (listing, subscription, entitlement, metering, finance, OIDC) **A3–A4 (Setbox App, ตรวจ hash, แบ่งรายได้อัตโนมัติ, ค้นข้าม node) ยังไม่ตัดสิน**

| คำถามเปิด | คำตัดสิน |
|---|---|
| 1 สัดส่วนแบ่งรายได้ | **ไม่ตัดสิน** ต้องผ่านโมเดลการเงินและที่ปรึกษากฎหมาย และต้องสอดคล้อง Fee Constitution (SPD-ECO-001 M3) · **ข้อสังเกต:** ADR §6 กำหนดว่า "ส่วนที่เครือข่ายเก็บรวมไม่เกิน 20%" ทั้งที่บอกว่าตัวเลขไม่อยู่ใน ADR ให้ถือ 20% เป็นเพดานชั่วคราวจนกว่า Fee Constitution จะประกาศ (ตัวเลขเพดานใน SPD-ECO-001 ยังเป็น "X") |
| 2 ผู้ตรวจแอประดับใช้คน | ใช้ข้อเสนอ: คณะผู้ตรวจที่กองทุนเครือข่ายจ้าง แยกจากผู้เผยแพร่ **การแต่งตั้งบุคคล Lead ต้องทำเอง** |
| 3 นโยบายเซ็นไฟล์ Setbox App กับ OneManOS | **ไม่ตัดสิน** เป็นนโยบายของ OneManOS (ของ Lead) ข้อเสนอของ Claude ให้พิจารณา: ผู้ถือกุญแจเซ็นแยกคนจากผู้เผยแพร่ และตรวจ `artifactHash` ตรงกับ `APP_REVIEWED` ก่อนเซ็น |
| 4 SLA ขั้นต่ำ | ใช้ข้อเสนอ: แอปที่เก็บเงินต้องประกาศ SLA เสมอ |
| 5 MyAI เป็นแอปใน Catalog หรือไม่ | **ไม่ใช่** MyAI เป็นชั้น L5 ของ SPADA (ADR 0016 §1) ไม่เป็นแอปใน Catalog |

**เงื่อนไข:** (ก) ต้องขยาย consent model ตาม ADR 0016 §6 ก่อน (ปัจจุบัน `granteeDid` เป็น person เท่านั้น ADR 0018 ตัดสินให้เป็น discriminated union แล้ว ต้องตรวจว่า implement เพียงใด) (ข) `ISPADAServiceListing.ownerDid` ต้องรับ `did:spada:org` ก่อนธุรกิจเผยแพร่ได้ (ค) ข้อผูกพันของกองทุนเครือข่ายสำหรับการตรวจแอปด้วยคนต้องมีที่มาของเงินก่อน (ง) ตรวจความสอดคล้องกับ Rights-are-Free Schedule ของ SPD-ECO-001 ข้อ 4

## 4. doc 340 §10: เรื่องที่ยังต้องตัดสิน

| รายการ | คำตัดสิน | เหตุผล |
|---|---|---|
| SLA, RPO, RTO | **ตัดสินเป็นค่าตั้งต้น:** ใช้ RPO 24 ชม. / RTO 4 ชม. เป็นค่าเริ่มต้นของ SetBox นำร่อง (ค่าเดียวกับ SLO v1.0 ใน `scripts/ops/backup.mjs` ของ node) และแทนด้วยค่าที่วัดจริงจากการซ้อมกู้คืน (ใบงาน S3) | มีค่าอ้างอิงในโค้ดแล้ว ตัวเลขปรับได้ตามผลซ้อมจริง ไม่ผูกลูกค้าจนกว่ามีสัญญา |
| Retention และ residency | **ตัดสินเป็นหลักตั้งต้น:** ข้อมูลธุรกิจอยู่ในกล่องของลูกค้า SPADA รับเฉพาะหลักฐาน (ADR 0014) ข้อมูลที่ ADR 0005 §8 ห้ามออกนอกประเทศต้องไม่ออก · **ระยะเก็บรักษาตามกฎหมายที่ใช้บังคับ ต้องให้ทนายยืนยัน** ไม่ระบุตัวเลขปี | ตัวเลขระยะเก็บเป็นประเด็นกฎหมาย |
| Business / Data / Technical / Support Owner | **ไม่ตัดสิน** ต้องระบุตัวบุคคล · เสนอให้แยกบทบาทกันเมื่อมีคน (ตาม SPD-DEC-002 ข้อสังเกตการรวมอำนาจ) | Lead ต้องกรอกชื่อ |
| Trusted Service trust tiers | **เลื่อน** จนกว่ามี Trusted Service ภายนอกรายแรก | ยังไม่มีกรณีจริงให้ออกแบบ |
| ผู้มีอำนาจรับรองหรือพักใช้บริการ | **ตัดสินชั่วคราว:** Steward (Lead) พร้อมผู้ตรวจคนที่สองเมื่อมีคน | สอดคล้อง SPD-ADR-D02 ผู้ลงนามแบบเดี่ยวชั่วคราว |
| Pricing และความรับผิดเมื่อบริการภายนอกล้มเหลว | **ไม่ตัดสิน** | เรื่องกฎหมายและการเงิน ต้องผ่านทนายและ Fee Constitution |
| Transaction profile ของหน่วยงานรัฐ | **ไม่ตัดสิน** | ยังไม่มีคู่กรณีจริง |

## สิ่งที่บันทึกนี้ไม่ได้ทำ

ไม่ได้แก้ไฟล์ใดใน monorepo · ไม่ได้ตัดสินสัดส่วนรายได้ ราคา ความรับผิด หรือนโยบายเซ็นไฟล์ · ไม่ได้ระบุตัวบุคคลผู้รับผิดชอบ · ไม่ได้ตรวจว่าโค้ดตรงกับ ADR (ตรวจเฉพาะข้อความ)
