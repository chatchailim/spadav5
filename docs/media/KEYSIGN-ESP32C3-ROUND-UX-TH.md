# ข้อเสนอ UX/UI ของ SPADA KeySign บนบอร์ด ESP32-C3 จอกลม GC9A01 1.28"

**รหัสเอกสาร:** SPD-MED-007 · **สถานะ:** ข้อเสนอ UX (ภาพจำลอง ยังไม่ได้รันบนอุปกรณ์จริง ยังไม่ผ่านผู้ตรวจ) · **วันที่:** 2026-10-02
**อ้างอิง:** doc 345 (Personal Key Token firmware guide v1.2, RP2350), ADR 0015/0020, ข้อบังคับ PKT-R1..R10
**วิดีโอประกอบ:** keysign-esp32c3-ux-demo (116 วินาที ไม่เก็บใน repo)

## 1. สิ่งที่ต้องบอกก่อน (ข้อสังเกตเชิงข้อเท็จจริง)
1. **ESP32-C3 เป็น RISC-V แกนเดี่ยว (single-core) สูงสุด 160 MHz** ตามเอกสารข้อมูลของผู้ผลิตชิป ข้อความในใบสินค้าว่า "Dual Core" ไม่ตรง ต้องตรวจสเปกบอร์ดจริงก่อนอ้างต่อ
2. **เอกสารทางการของโครงการ (doc 345) อ้างอุปกรณ์ RP2350 ไม่ใช่ ESP32-C3** การเปลี่ยนแพลตฟอร์มต้องผ่านการตัดสินใจของ Lead และทำชุดตรวจ PKT-R1..R10 และการรับรองฮาร์ดแวร์ (ADR 0020/doc 344) ใหม่ทั้งหมด วิดีโอและเอกสารนี้จึงเป็น **การออกแบบ UX ที่ไม่ผูกกับชิป** ไม่ใช่การยืนยันว่า ESP32-C3 ผ่านเกณฑ์
3. **ความสามารถด้านความปลอดภัยของ ESP32-C3 ที่ต้องตรวจ:** Secure Boot, Flash Encryption, ปิด JTAG ด้วย eFuse; ไม่มี secure element จึงทำหน้าที่ **user presence** ไม่ใช่ **root of trust** (เพดาน `deviceAssurance` = NATIVE ตาม PKT-R10)
4. ทางเชื่อมต่อ WiFi/BLE เพิ่มพื้นที่โจมตีเมื่อเทียบกับ USB เท่านั้น (PKT-R1 ถึง R10 เขียนสำหรับ USB) ต้องเพิ่มข้อกำหนดสำหรับ BLE (จับคู่แบบเทียบรหัส ปิด WiFi เมื่อไม่ใช้)
5. **ปุ่มกายภาพ:** ข้อ PKT-R5 กำหนด "การกดปุ่มหนึ่งครั้ง" ถ้ารุ่นที่เลือกมีเฉพาะหน้าจอสัมผัส ต้องตัดสินว่าการแตะ/กดค้างบนทัชนับเป็น user presence เทียบเท่าปุ่มได้หรือไม่ (ชิปทัชสื่อสารผ่าน I2C กับ MCU) รุ่นที่มีปุ่ม BOOT/ปุ่มกายภาพควรเป็นแนวทางหลัก

## 2. ข้อกำหนดฮาร์ดแวร์ที่ใช้ออกแบบ
จอ IPS GC9A01 1.28" วงกลม 240×240 · ESP32-C3 (WiFi 4, Bluetooth 5.0 LE) · Arduino IDE + LVGL · เคสสีดำ มี/ไม่มีหน้าจอสัมผัส
**กฎ UI:** เนื้อหาสำคัญอยู่ในวงรัศมี ≤ 105 px จากจุดกลาง · ตัวอักษรไทยขนาด ≥ 14 px (ที่หน้าจอจริง) · ใช้สีสื่อสถานะซ้ำกับข้อความ (เขียว=สำเร็จ ทอง=เวลา/ระวัง เหลือง=เตือน แดง=ปฏิเสธ) · ไม่มีคำว่า FIDO/FIDO2/U2F (PKT-R9)

| สถานะ | สิ่งที่แสดง | การโต้ตอบ |

## 4. หลักออกแบบสำคัญ
1. **WYSIWYS (เห็นอะไรเซ็นอันนั้น):** อุปกรณ์แสดงข้อความมาตรฐานของคำขอ และ **คำนวณแฮชเองจากข้อความที่แสดง** เพื่อสร้าง `contextHash` ตาม PKT-R7 เพื่อไม่ให้คอมพิวเตอร์ส่งข้อความหนึ่งแต่ขอเซ็นอีกอย่าง
2. **หนึ่งการกด หนึ่งลายเซ็น (PKT-R5)** และหมดเวลาที่ 15 วินาที ไม่มีลายเซ็นค้างในระบบ
3. **ปฏิเสธโดยค่าเริ่มต้น:** เครื่องที่ไม่เคยจับคู่ คำขอที่แสดงไม่ครบ หรือตัวนับผิดปกติ ถูกปฏิเสธและเตือนด้วยสีและเสียง
4. **ทุกอย่างสื่อได้ด้วยสี เสียง และการสั่น** ผู้ใช้ไม่ต้องอ่านศัพท์เทคนิค
5. **แสดงสถานะความเชื่อมั่นตรงๆ:** ป้าย NATIVE ไม่ใช่ APPLIANCE (PKT-R10)

## 5. สิ่งที่ต้องตรวจกับบอร์ดจริงก่อนตัดสินใจ
- [ ] จำนวนแกนและสเปกชิปตรงตามที่ผู้ขายระบุหรือไม่ (single-core)
- [ ] มีปุ่มกายภาพกี่ปุ่ม ชิปทัชรุ่นใด (เช่น CST816) อ่านค่าอย่างไร
- [ ] เปิด Secure Boot + Flash Encryption ปิด JTAG และบันทึกสถานะ eFuse ในหลักฐานแบบ append-only
- [ ] ทดสอบ PKT-R1..R10 เวอร์ชัน BLE (ปรับข้อกำหนดที่เขียนสำหรับ USB)
- [ ] ทดสอบการอ่านได้ของตัวอักษรไทยบน GC9A01 240×240 ที่แสงต่างๆ
- [ ] ทดสอบกับผู้ใช้จริง 5 คนต่อรุ่น (มีทัช/ไม่มีทัช) ว่าทำขั้นอนุมัติได้โดยไม่ต้องอ่านคู่มือ
- [ ] Lead ตัดสินใจเรื่องการใช้ ESP32-C3 เป็นอุปกรณ์เสริมหรือแทน RP2350 และบันทึกเป็น ADR
