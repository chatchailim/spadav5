# บันไดแอป: จากสมาชิกสร้างใช้เอง สู่ชุมชน สู่ App Store ของ SPADA Node/Network และการลงทะเบียน Service

**รหัสเอกสาร:** SPD-PLN-004 · **สถานะ:** ร่างเพื่อทบทวน v0.1 (แนวทางและเกณฑ์เสนอ ยังไม่ใช่มาตรฐานที่ Lead ตัดสิน) · **วันที่:** 2026-10-02
**ต่อจาก:** SPD-PLN-003 (แคตตาล็อกแอปหาดใหญ่), SPD-MED-008 (คู่มือ Harness/App Catalog)
**อ้างอิง:** วงจร CIDER ใน `onemanos-setbox/app-catalog.js` (ตามที่ SPD-MED-008 ตรวจ), ADR 0014, 0016, 0017, 0021, 0022, 0023, **0026 (Proposed)**, 0019 (Digital Will), PROP-0003, PROP-0010, MEMBER-ECONOMY

> **ข้อควรรู้:** App Manifest 3 ชนิด `APP_REVIEWED/APP_INSTALLED`, metering ต่อแอป, การแบ่งรายได้และอุทธรณ์ เป็นข้อเสนอใน ADR 0026 ยัง Proposed ผู้ร่างยังไม่พบโค้ดครบ ผู้ร่างไม่ได้อ่านซอร์สใน `services/` `packages/` `modules/` จึงไม่ยืนยันว่า service-registry (`ISPADAServiceListing`) รองรับตามที่ระบุ เกณฑ์ผ่านแต่ละขั้นและตัวเลขที่เป็น [●] เป็นข้อเสนอให้ชุมชน/Lead ตัดสิน ไม่ใช่กติกาที่ใช้งานแล้ว

---

## 1. แนวคิดหลัก

สมาชิกที่มี SetBox สร้างแอปที่ตนต้องการก่อน ใช้เอง ถ้าใช้ดีและเป็นประโยชน์ จึงเสนอต่อชุมชน แล้วค่อยๆ ยกระดับขึ้น App Store ของ SPADA Node/Network และลงทะเบียนเป็น Service ตามมาตรฐาน SPADA Framework เพื่อขยายผล

**หลักการ:** *ได้รับความไว้วางใจก่อน แล้วค่อยได้รับการเผยแพร่* ทุกขั้นเพิ่มผู้ใช้และความรับผิดชอบทีละระดับ และทุกขั้นมีเกณฑ์ผ่านเป็นหลักฐาน ไม่ใช่ความรู้สึก

```
ขั้น 0 ส่วนตัว ─▶ ขั้น 1 วงใกล้ชิด ─▶ ขั้น 2 เสนอชุมชน ─▶ ขั้น 3 ผู้สมัครขึ้นสโตร์ ─▶ ขั้น 4 เผยแพร่ใน Node Catalog ─▶ ขั้น 5 Service ที่ลงทะเบียน
 (ข้อมูลตนเอง)   (คนที่รู้จัก)      (รีวิวโดยชุมชน)    (ตรวจทางการ + manifest)     (ผู้ใช้ทั่วไป ผ่าน consent)      (ตามมาตรฐาน Service)
```

## 2. ภาพรวมแต่ละขั้น

| ขั้น | ใครใช้ | ข้อมูลที่ใช้ได้ | ผู้ตัดสินให้ขึ้นขั้น | สิ่งที่ได้ |
|---|---|---|---|---|
| 0 ส่วนตัว | เจ้าของ SetBox คนเดียว | ข้อมูลของตนเองเท่านั้น | เจ้าของ | ทดลองสร้างและใช้ |
| 1 วงใกล้ชิด | ครอบครัว/ทีม/ลูกค้าที่รู้จัก ≤ [●] คน | ข้อมูลที่ผู้ใช้แต่ละคนให้ consent ชัดเจน | เจ้าของ + ผู้ใช้วงใกล้ชิดยินยอมเป็นรายคน | หลักฐานการใช้จริง |
| 2 เสนอชุมชน | สมาชิกชุมชนที่สนใจ (สาธิตและทดลอง) | ข้อมูลสังเคราะห์หรือข้อมูลของผู้ทดลองที่ยินยอม | คณะกรรมการชุมชน/ผู้รีวิวชุมชน | ข้อเสนอแนะ ความเห็น และรายชื่อผู้สนับสนุน |
| 3 ผู้สมัครขึ้นสโตร์ | ผู้ทดสอบที่เลือกไว้ | ตาม manifest ที่ประกาศ | ผู้รีวิวทางการ + คนอนุมัติ 2 ประตู (CIDER) | สถานะ "ผ่านรีวิว" `APP_REVIEWED` (ข้อเสนอ) |
| 4 เผยแพร่ใน Node Catalog | สมาชิกทั่วไป ผ่าน consent | ตาม `dataScopes` ที่ประกาศ | ผู้ดูแล Catalog + หลักฐานครบ | `LISTING_PUBLISHED` ใน ServiceBook |
| 5 Service ที่ลงทะเบียน | สาธารณะ รวมข้ามชุมชน | ตาม scope + trust gate | ตามมาตรฐาน SPADA Framework ชั้น Service | ID ของบริการ ทะเบียนบริการ หลักฐานใน BookChain |

## 3. รายละเอียดแต่ละขั้น

### ขั้น 0 — ส่วนตัว (สร้างและใช้เอง)
- **ทำอย่างไร:** สมาชิกใช้ MyAI/Harness สร้างแอปจาก Journey/Workflow ของตนบน SetBox ของตนเอง (SPD-MED-008) และผ่านวงจร CIDER ในระดับสมาชิกคนเดียว
- **ข้อกำหนด:** ลงทะเบียนแอปพร้อมชื่อเจ้าของและเหตุผล (`register`) · เข้าคลังผ่าน API/สัญญาเท่านั้น (`directStorageAccess=false`) · ใช้ข้อมูลของตนเองเท่านั้น · ห้ามให้ agent ใส่ชื่อตัวเองอนุมัติ
- **ขอบเขตความเสี่ยง:** ความเสียหายจำกัดอยู่ที่เจ้าของ แต่ยังต้องป้องกันไม่ให้แอปรั่วข้อมูลของตนเอง
- **ออกจากขั้นเมื่อ:** เจ้าของใช้งานจริงต่อเนื่อง [●] สัปดาห์ และบันทึกผลที่ได้ (เวลาที่ประหยัด ปัญหาที่พบ)

### ขั้น 1 — วงใกล้ชิด
- **ทำอย่างไร:** เจ้าของเชิญคนที่รู้จักมาใช้ ผู้ใช้แต่ละคนเห็นและกดยินยอมรายการข้อมูลที่แอปขอ (`dataScopes`) พร้อมวัตถุประสงค์ ผ่าน consent ตาม PROP-0003
- **ข้อกำหนด:** ประกาศความเป็นส่วนตัวสั้นๆ เป็นภาษาไทย · ถอน consent ได้ทันที · บันทึกการเข้าถึงที่ผู้ใช้เปิดดูได้ · เจ้าของแอปตระหนักว่าตนอาจเป็นผู้ควบคุมข้อมูลของผู้อื่น (ให้ที่ปรึกษากฎหมายยืนยันบทบาท)
- **ห้าม:** เก็บข้อมูลของผู้อื่นเกินที่ consent, เก็บเงิน, ใช้ข้อมูลอ่อนไหว (สุขภาพ พิกัดบ้าน) ในขั้นนี้
- **เกณฑ์ออก (เสนอ):** ผู้ใช้ ≥ [●] คนใช้ต่อเนื่อง ≥ [●] สัปดาห์ · ไม่มีเหตุข้อมูลผิดปกติร้ายแรง · อัตราการถอน consent ไม่สูงผิดปกติ [●] · เจ้าของเขียนสรุปผลหนึ่งหน้า

### ขั้น 2 — เสนอชุมชน
- **ทำอย่างไร:** เจ้าของนำเสนอสาธิตในที่ประชุมชุมชนหรือช่องทางที่ตกลง พร้อม "ชุดข้อมูลเสนอ" (ข้อ 5) ชุมชนทดลองด้วยข้อมูลสังเคราะห์ก่อน
- **รีวิวโดยชุมชน:** คุ้มค่าไหม · ซ้ำกับแอปที่มีอยู่ไหม · ข้อมูลที่ขอสมเหตุสมผลไหม · มีผลกระทบต่อกลุ่มเปราะบางไหม · ใช้ภาษาที่ชุมชนเข้าใจไหม
- **ผลได้:** คำตัดสิน "สนับสนุน / ปรับแก้ / ไม่ผ่าน" บันทึกพร้อมเหตุผล และชื่อผู้สนับสนุนที่ยอมรับว่าตนได้ตรวจแล้ว
- **เกณฑ์ออก (เสนอ):** ได้รับการสนับสนุนตามเกณฑ์ที่ชุมชนกำหนด [●] · ผู้รีวิวอิสระ ≥ [●] คนที่ไม่ใช่เจ้าของแอป ยืนยันว่าผ่านเช็กลิสต์ขั้น 2

### ขั้น 3 — ผู้สมัครขึ้นสโตร์ (รีวิวทางการ)
- **ทำอย่างไร:** เจ้าของส่ง **App Manifest** (ข้อเสนอ ADR 0026 ดู §4) และ **ชุดหลักฐาน** ให้ผู้รีวิวของ Node/Catalog
- **ผ่านวงจร CIDER จริง:** `submitVersion` → 🔒 คนอนุมัติสัญญา (`approveVersion`) → ตรวจ (`beginEvaluation`) → 🔒 คนยืนยันผล (`activateVersion` พร้อมผลทดสอบสัญญาครบและผลตรวจต้านไซโล) → ผูกบัญชี SERVICE (`bindService`)
- **การตรวจ (เสนอ):** ความปลอดภัย (รวมการตรวจโดยบุคคลที่สามตามความเสี่ยง) · การปฏิบัติตาม PDPA · การทดสอบสัญญา · ทดสอบเมื่อเน็ตหลุด (ถ้าเป็น Setbox App) · การส่งออกข้อมูลคืน `export` · แผนเลิกใช้ `retire`
- **ผลได้:** `APP_REVIEWED` พร้อม hash ของไฟล์ (`artifactHash` ตาม ADR 0021) ถ้าแก้ scope หรือราคา = เวอร์ชันใหม่ที่ต้องรีวิวใหม่
- **ผู้ตัดสิน:** คนที่มีชื่อ ไม่ใช่ agent

### ขั้น 4 — เผยแพร่ใน Node Catalog
- **ทำอย่างไร:** ผู้ดูแล Catalog เผยแพร่ (`LISTING_PUBLISHED`) สมาชิกเห็น `dataScopes`+วัตถุประสงค์ก่อนติดตั้ง, trust gate, SLA (ถ้ามี), `export`, ผลรีวิว
- **การติดตั้งโดยผู้ใช้:** บันทึก `APP_INSTALLED` และ consent เป็นรายวัตถุประสงค์
- **การใช้งานและค่าธรรมเนียม (ถ้ามี):** metering ต่อ `appId` และแบ่งรายได้ตาม ADR 0026 §4 และ MEMBER-ECONOMY — **ยังไม่พบโค้ดแบ่งรายได้** อย่าสัญญารายได้ให้ผู้สร้างจนกว่าจะมี
- **ระยะทดลองหลังเผยแพร่ (เสนอ):** จำกัดจำนวนผู้ใช้ในช่วง [●] สัปดาห์แรก มีผู้เฝ้าระวังเหตุการณ์

### ขั้น 5 — Service ที่ลงทะเบียนตามมาตรฐาน SPADA Framework
- **คืออะไร:** แอปที่ผ่านขั้น 4 และมีผู้ใช้/หลักฐานเพียงพอ ลงทะเบียนเป็น **Service** ในชั้น Service ของ SPADA (Place → Space → **Service** → BookChain) ได้ ID แบบ `spada-service:...` และมีบันทึกหลักฐานใน ServiceBook
- **ข้อกำหนดเพิ่มจากขั้น 4 (เสนอ ต้องให้ผู้ดูแลมาตรฐาน SPADA Framework ยืนยัน):**
  1. ผู้เผยแพร่มี DID ที่ผ่านการยืนยันตามระดับที่กำหนด (`publisherDid`)
  2. มีข้อกำหนด SLA และผู้รับผิดชอบเหตุการณ์ (`APP_INCIDENT_*`, `SLA_BREACH_RECORDED` เป็นข้อเสนอ)
  3. มีแผนต่อเนื่อง: ผู้ดูแลสำรอง/ผู้สืบทอดของแอป (แนวเดียวกับ ADR 0019) เพื่อไม่ให้บริการหายเมื่อเจ้าของไม่อยู่
  4. ผ่านเกณฑ์ TrustScore ของเจ้าของ/ผู้เผยแพร่ตามขั้นที่กำหนด (ADR 0024 ยัง Proposed จึงยังตัดสินตัวเลขไม่ได้)
  5. ผ่านการตรวจความเข้ากันได้กับ Service อื่นและไม่สร้างไซโลข้อมูล
- **ผลได้:** ค้นหาและใช้ได้ข้ามชุมชนในเครือข่าย ตามขอบเขตที่ consent ให้
- **หมายเหตุสถาปัตยกรรม:** SetBox อยู่นอก SPADA Node/Network (ADR 0014) การยกจาก Setbox App เป็น Node App หรือ Hybrid อาจต้องออกแบบส่วนหลังบ้านใหม่ ไม่ใช่แค่ย้ายไฟล์ ให้ประเมินตั้งแต่ขั้น 3

## 4. App Manifest ที่ต้องเตรียม (ข้อเสนอ ADR 0026)
ใช้ตามโครงที่ SPD-MED-008 §3.3 สรุปไว้ ไม่ประดิษฐ์ฟิลด์ใหม่

| ฟิลด์ | สิ่งที่ผู้สร้างต้องเตรียมในแต่ละขั้น |
|---|---|
| `appId`, `publisherDid`, `kind` (node/setbox/hybrid), `version`, `artifactHash` | ขั้น 3 เป็นต้นไป |
| `dataScopes` (scope, purpose, sensitivity) | ขั้น 1 ร่างไว้ ขั้น 3 ตรึง |
| `trustGates` (ขั้นไหนต้อง KeySign) | ขั้น 3 |
| `pricing` | ขั้น 4 (ถ้าเก็บเงิน ต้องมี `sla`) |
| `sla` | ขั้น 4–5 |
| `export` | ขั้น 3 เป็นต้นไป (เลิกใช้แล้วได้ข้อมูลคืน) |

## 5. ชุดข้อมูลเสนอ (ใช้ตั้งแต่ขั้น 2)
1. สรุปหนึ่งหน้า: ปัญหาที่แก้ ผู้ใช้เป้าหมาย ผลที่ได้
2. สถิติการใช้ขั้น 0–1 (จำนวนผู้ใช้ ความถี่ เวลาที่ประหยัด) พร้อมวิธีวัด
3. ข้อมูลที่แอปใช้ ทำไมต้องใช้ ใครเห็น เก็บนานเท่าใด วิธีถอน consent
4. ผลทดสอบสัญญา ผลต้านไซโล และเหตุการณ์ผิดปกติที่เกิดขึ้นพร้อมวิธีแก้
5. ภาพหน้าจอและวิดีโอสาธิตสั้นๆ
6. ใครรับผิดชอบดูแล และแผนเมื่อเจ้าของไม่สะดวกดูแล
7. แผนเลิกใช้และส่งออกข้อมูล

## 6. เช็กลิสต์ผ่านด่าน (สรุป)

| ด่าน | ต้องมี |
|---|---|
| 0→1 | ผ่าน CIDER ระดับส่วนตัว · มีบันทึกการใช้ · ข้อมูลของผู้อื่นยังไม่เข้ามา |
| 1→2 | consent รายคน · ไม่มีเหตุร้ายแรง · สรุปผลหนึ่งหน้า |
| 2→3 | ชุดข้อมูลเสนอครบ · ชุมชนสนับสนุน · ผู้รีวิวอิสระยืนยัน |
| 3→4 | manifest + hash · ทดสอบสัญญาและต้านไซโลผ่าน · ตรวจความปลอดภัยตามระดับ · PDPA ผ่าน · คนอนุมัติ 2 ประตู |
| 4→5 | ใช้งานจริงต่อเนื่อง [●] เดือน · SLA และผู้สืบทอด · TrustScore ตามเกณฑ์ (หลัง ADR 0024) · ตรวจโดยผู้ดูแลมาตรฐาน Service |

## 5.1 กรณีเสี่ยงสูงและข้อมูลอ่อนไหว
แอปที่ใช้สุขภาพ พิกัดบ้าน หรือกระทบความปลอดภัย (เช่น M7 ใน SPD-PLN-003) **ห้ามขึ้นบันไดแบบทีละขั้นตามปกติ** ต้องผ่านข้อ 8 ของ SPD-PLN-003 ครบ และมีหน่วยงานที่มีอำนาจเห็นชอบก่อนขั้น 4 เสมอ แม้ชุมชนสนับสนุนแล้วก็ตาม

## 7. บทบาท

| บทบาท | หน้าที่ | หมายเหตุ |
|---|---|---|
| เจ้าของแอป (สมาชิกผู้สร้าง) | สร้าง ใช้ สรุปผล ดูแล ตอบเหตุการณ์ | ต้องเป็นคนที่มีชื่อ |

| ผู้รีวิวชุมชน | ตรวจขั้น 2 | ไม่ใช่เจ้าของแอป |
| ผู้รีวิวทางการ/ผู้ดูแล Catalog | ตรวจขั้น 3–4 | ต้องมีความเป็นอิสระ ไม่มีผลประโยชน์ทับซ้อน |
| คณะกรรมการชุมชน | ratify กติกา ตัดสินข้อพิพาท | ตาม ADR 0005 ซึ่ง safeguards รอ ratification |
| ผู้ดูแลมาตรฐาน Service | ยืนยันขั้น 5 | [●] ยังไม่ระบุตัวในเอกสารที่ตรวจ |

## 8. การลดระดับ ระงับ และเลิกใช้
- **เหตุให้ระงับ:** เหตุละเมิดข้อมูล, ไม่ตอบเหตุการณ์ตาม SLA, ใช้ข้อมูลเกิน consent, ผู้ดูแลหายไป ผลคือ `APP_SUSPENDED` (ข้อเสนอ) และแจ้งผู้ใช้
- **การลดระดับ:** ถอยกลับขั้นก่อนหน้าพร้อมเหตุผลที่เปิดเผยได้
- **การเลิกใช้:** `retire` ต้องมีคนตัดสินและเหตุผล ผู้ใช้ได้ข้อมูลคืนผ่าน `export` ลบข้อมูลตามระยะที่ประกาศ
- **สิทธิ์อุทธรณ์:** ผู้สร้างอุทธรณ์ได้ (ADR 0026 กล่าวถึงอุทธรณ์ ข้อเสนอ ยังไม่พบโค้ด) กำหนดผู้ตัดสินอุทธรณ์ที่ไม่ใช่ผู้ตัดสินเดิม

## 9. ความเสี่ยงของแนวทางนี้

## 11. คำถามที่ต้องตัดสิน
1. ข้อกำหนด Service Registration ในมาตรฐาน SPADA Framework ฉบับที่ใช้จริงอยู่ที่ใด และตรงกับเกณฑ์ขั้น 5 หรือไม่ (ผู้ร่างไม่ได้อ่านเอกสารฉบับเต็มของมาตรฐาน)
2. ADR 0026 ตัดสินเมื่อใด และระหว่างนั้นขั้น 3–4 จะใช้ทะเบียนที่มีโค้ดจริงชั่วคราวอย่างไร
3. ใครคือผู้รีวิวทางการ และจะป้องกันผลประโยชน์ทับซ้อนอย่างไร
4. ข้อตกลงสิทธิ์ในแอปที่สมาชิกสร้าง (ลิขสิทธิ์ สัญญาอนุญาต ความรับผิด)
5. ค่าธรรมเนียมและการแบ่งรายได้ที่ผู้สร้างควรคาดหวัง (หลังมี fee schedule ตาม GAP-ANALYSIS)
6. ตัวเลข [●] ทุกช่อง: จำนวนผู้ใช้ ระยะเวลา อัตราสนับสนุนของชุมชน
