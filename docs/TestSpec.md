# 1. บทนำ

## 1.1 วัตถุประสงค์

กำหนดว่า **จะทดสอบอะไร ด้วยข้อมูลอะไร ใครทดสอบ เกณฑ์ผ่านคืออะไร** เพื่อให้ผู้ทดสอบที่ไม่เคยเห็นระบบ ทำตามได้และให้ผลที่เปรียบเทียบกันได้ ก่อนประกาศว่าระบบ "พร้อมใช้งานจริง"

## 1.2 ขอบเขต

**อยู่ในขอบเขต** (Track S ใช้เดี่ยว ตามที่คู่มือผู้ใช้อธิบาย):
- การติดตั้งและตรวจรับ (`setup check/install/backup/restore/accept/token/join/demo/prep`), การดูแล (`care`), การส่งมอบ (`handover` H1–H7), ชุดส่งมอบ (`build-kit/sign-kit/verify-kit`), ตั้งต้นองค์กร (`init-organization`)
- ระบบบริหารเอกสาร (DMS): เข้าสู่ระบบ, เอกสาร, เวอร์ชัน, ไฟล์แนบ, สิทธิ์, ความเป็นเจ้าของ, กล่องงาน, workflow/อนุมัติ, ลายเซ็น, ค้นหา/OCR, legal hold
- เครื่องยนต์ธุรกิจ (171 เส้นทาง ใน 23 โมดูล), หน้าจอเว็บ 5 หน้า + Help
- MCP server (เครื่องมือของ agent), Human Gate, วงจรแอป CIDER
- การย้ายข้อมูลจากระบบเดิม (wave, ข้อยกเว้น, กระทบยอด, ปิดผนึก), สำรอง/กู้คืน

**นอกขอบเขตรอบนี้** (ต้องมีเอกสารทดสอบแยก เมื่อพร้อม):
- Track C: การผูกกับ SPADA (SubjectBinding C1, canonical hash C2) — ยังไม่เสร็จ
- ตัวตรวจ hardware attestation (TPM/EK) — ยังไม่มีในโค้ด · KeySign — ต้นแบบ
- App Manifest / สโตร์แอป (ADR 0026) · Optimus edition · หน้าจอที่ยังไม่ merge (PR #12, #14 ของ `onemanos-setbox`) ยกเว้นระบุไว้
- การทดสอบเจาะระบบ (penetration test) โดยผู้เชี่ยวชาญอิสระ · การทดสอบโหลดระดับผลิต

# 3. กลยุทธ์การทดสอบ

## 3.1 ระดับและชนิดการทดสอบ

| ระดับ | ทดสอบอะไร | ใคร | เครื่องมือ | ความถี่ |
|---|---|---|---|---|
| L1 ยูนิต/โมดูล | ตรรกะของโมดูลเดี่ยว | ผู้พัฒนา/Codex | `node --test` (`npm test`) | ทุก PR |
| L2 ชั้น HTTP/API | เส้นทาง สิทธิ์ รหัสข้อผิดพลาด | Tester + CI | `docs/testdata/smoke-dms.js` + เทสต์ `*-http.test.js` | ทุกรุ่น |
| L3 หน้าจอ | หน้าเว็บในเบราว์เซอร์จริง | Antigravity/Tester | เบราว์เซอร์ + ภาพหน้าจอ | ทุกรุ่น |
| L4 ระบบ/E2E | สถานการณ์ใช้งานจริง (UC-T01–T14) | Tester อิสระ | ขั้นตอนมือ + ข้อมูลสังเคราะห์ | ก่อนส่งมอบ |
| L5 ชุดส่งมอบ/ติดตั้ง | ประกอบ ลงชื่อ ตรวจ ติดตั้ง | Release Owner + ช่าง | `build-kit`, `verify-kit`, `1-CHECK`…`4-ACCEPT` | ทุกรุ่นที่จะส่ง |
| L6 หน้างาน | Windows สะอาด + เจ้าหน้าที่คนใหม่ | ผู้ที่ไม่ใช่ผู้พัฒนา | ใบตรวจรับ `kit/CHECKLIST-TH.md` | ก่อนลูกค้ารายแรก |

ชนิด: ฟังก์ชัน · ความปลอดภัย · สำรอง-กู้คืน (recovery) · ความเข้ากันได้ (OS/เบราว์เซอร์) · การใช้งาน (usability) · การเข้าถึง (accessibility) · ภาษา/การเข้ารหัสอักขระ · ประสิทธิภาพพื้นฐาน (ภาค 9)

## 3.2 หลักการออกแบบการทดสอบ

1. **ทดสอบที่ชั้น HTTP จริง ไม่ใช่แค่โมดูล** เพราะข้อบกพร่องที่ชั้นโมดูลมองไม่เห็นมักอยู่ที่เส้นทางลืมส่งตัวแทนผู้ใช้หรือไม่ได้ต่อกับโมดูล (หลักการเดียวกับ `admin-console-http.test.js`)
2. **ทุกฟังก์ชันที่มีสิทธิ์ ต้องมีทั้งเคสที่ได้รับอนุญาตและเคสที่ถูกปฏิเสธ** (ข้ามนิติบุคคล, ไม่ใช่ผู้ดูแล, ไม่มีโทเคน)
3. **ทุกเคสที่เปลี่ยนสถานะ ต้องมีเคส idempotency/ซ้ำ/ชนกัน**
4. **ข้อมูลสังเคราะห์เท่านั้น** ห้ามนำข้อมูลลูกค้าจริงเข้ามาทดสอบ (ภาค 6.5)
5. **ผู้ทดสอบ ≠ ผู้เขียนโค้ด** สำหรับระดับ L4–L6 ผู้ตรวจที่เป็น AI ไม่นับเป็นการตรวจอิสระ
6. **ผลที่ไม่รู้ = ไม่ผ่าน** (fail-closed) เช่นเดียวกับหลักของ `prep`: `REVIEW` ห้ามนับเป็น PASS
7. **ข้อสังเกตที่ทราบ (KI) ต้องมีเทสต์ที่ล้มเมื่อพฤติกรรมเปลี่ยน** เพื่อให้คนกลับมาแก้เอกสาร (สคริปต์ smoke พิมพ์ `CHANGED`)

## 3.3 เกณฑ์เข้า/ออก/พักการทดสอบ

| | เกณฑ์ |
|---|---|
| **เกณฑ์เข้า** (เริ่มรอบทดสอบ) | CI เขียวบนคอมมิตที่ทดสอบ · ชุดถูกประกอบจากคอมมิต (ไม่ใช้ `--from-working-tree`) · มีข้อมูลสังเคราะห์ครบตามภาค 6 · ผู้ทดสอบได้รับ `help/readme.md` และเวอร์ชันซอฟต์แวร์ที่ระบุ |
| **เกณฑ์ออก** (สรุปรอบ) | TC ระดับ P0 ผ่าน **ทั้งหมด** · P1 ผ่าน ≥ 95% และข้อที่ไม่ผ่านมีข้อบกพร่องที่เจ้าของรับทราบ · ไม่มีข้อบกพร่องความรุนแรง S1 ค้าง · ไม่มี S2 ที่เกี่ยวกับความปลอดภัยหรือการสูญเสียข้อมูลค้าง · ผลระดับ L4–L6 มีผู้ทดสอบที่ระบุชื่อและไม่ใช่ผู้เขียนโค้ด · **สำหรับ "พร้อมส่งลูกค้า" ต้อง T2 (Windows สะอาด) ผ่านด้วย** |
| **เกณฑ์พัก** | ติดตั้งพื้นฐานไม่ผ่าน (`install` หรือการซ้อมติดตั้งล้ม) · ข้อบกพร่อง S1 ที่ทำให้ทดสอบต่อไม่ได้ · พบข้อมูลจริงหลุดเข้าชุดทดสอบ (หยุดทันที) |
| **เริ่มต่อ** | แก้แล้วประกอบชุดใหม่ ทำรอบสั้น (smoke + P0) ซ้ำก่อนเดินต่อ |

เกณฑ์ตัวเลขเช่น "P1 ≥ 95%" เป็น **ข้อเสนอ [ต้องตัดสิน]** โดย Lead

## 6.1 หลักการ

- **สังเคราะห์ทั้งหมด** · กำหนดผลได้ซ้ำ (deterministic) เมื่อสร้างด้วยโค้ด · แยกจากคลังจริง

- ไฟล์ผลทดสอบที่แนบรายงาน ต้องไม่มีโทเคน กุญแจ หรือรหัสผ่าน (ปิดบังก่อนแนบ)

# 7. Use Case สำหรับการทดสอบ (UC-T)

แต่ละ UC เป็นสถานการณ์ใช้งานที่เป็นไปได้จริง ใช้ข้อมูลตามภาค 6 และผูกกับ TC ในภาค 8 · **ป้าย `[รันจริง]` ใน UC หมายถึงส่วนที่ครอบคลุมโดย `smoke-dms.js`** ที่เหลือคือขั้นตอนมือที่ผู้ทดสอบต้องทำ

## UC-T01 ติดตั้งรุ่น S บน Windows สะอาด (P0 · ENV-2 · D8)

| | |
|---|---|
| ผู้ทำ | เจ้าหน้าที่ใหม่ที่ไม่เคยใช้ระบบ + ผู้สังเกตการณ์ |

## UC-T02 พนักงานสร้างและแก้เอกสารหลายเวอร์ชัน (P1 · D1–D3 · ENV-1) **[รันจริง]**

ผู้ทำ: พนักงาน co-alpha · ขั้น: เข้าสู่ระบบ → สร้าง `GeneralDocument` (D3.base) → เปิดดู → แก้เป็นเวอร์ชัน 2 พร้อมเหตุผล → ดูรายการ → ค้นหาด้วยเลขที่เอกสาร → ออกจากระบบ · ทางเลือก: ไม่ใส่ชื่อ/ชื่อว่าง → ปฏิเสธ; ข้อความมีแท็กและ `<script>` → เก็บเป็นข้อความ · ผลที่คาด: เวอร์ชัน 2 มี `versionNo=2`, ค้นเจอ, ออกจากระบบแล้วโทเคนเดิมใช้ไม่ได้ · TC: DMS-002/004/005, VER-001, SRCH-001, AUTH-003, DAT-001…003, NEG-001/002

## UC-T03 สองคนแก้เอกสารเดียวกันพร้อมกัน (P0 · optimistic concurrency) **[รันจริง]**

ขั้น: คนที่ 1 และคนที่ 2 เปิดเวอร์ชัน 1 → คนที่ 1 บันทึกเป็นเวอร์ชัน 2 → คนที่ 2 บันทึกโดยอ้าง `expectedVersion=1` ด้วยเนื้อหาต่าง · ผลที่คาด: คนที่ 2 ถูกปฏิเสธและต้องเปิดใหม่ ไม่มีเวอร์ชันซ้อน · **ข้อควรระวังจากการทดสอบจริง:** ถ้าเนื้อหาเหมือนกันเป๊ะ ระบบตอบ 200 (นับเป็นคำขอซ้ำ) ไม่ใช่ปฏิเสธ — ใช้เนื้อหาต่างกันเมื่อทดสอบชนกัน · TC: VER-001/002/003

## UC-T04 แยกข้อมูลข้ามนิติบุคคล (P0 · ความปลอดภัย) **[รันจริง]**

ขั้น: ผู้ใช้ co-alpha สร้างเอกสาร + แนบไฟล์ → ผู้ใช้ co-beta พยายาม: เปิดตรง ด้วย id, ดูรายการ, สร้างเวอร์ชัน, ดาวน์โหลดไฟล์แนบ · ผลที่คาด: ถูกปฏิเสธ/ไม่เห็นทุกกรณี · ผู้ดูแลระบบ (dev admin) เห็นข้ามนิติบุคคล · TC: ACC-001…004, DMS-008

2. ตัวอย่าง body ของโมดูลธุรกิจ (UC-T11…T13) **ยังไม่ได้เขียน** เพราะต้องอ่านรูปแบบจากโค้ดแต่ละโมดูล — เป็นงานต่อเนื่องที่ควรให้ Codex/ผู้ทดสอบทำและตรวจกับเทสต์ในโมดูลนั้น
3. ไม่มีแมตทริกซ์บทบาท × เครื่องมือ MCP × การกระทำ DMS ฉบับสมบูรณ์ (TC-ACC-007, TC-MCP-007) ต้องสร้างจากโค้ดนโยบายก่อน
4. เกณฑ์ตัวเลข (ประสิทธิภาพ ความจุ อายุเซสชัน ขีดจำกัดไฟล์ usability) ยังไม่ถูกตัดสิน ผมไม่ได้เดา
5. `smoke-dms.js` ใช้ `DMS_DEV_AUTH` เพื่อเข้าสู่ระบบแบบพัฒนา จึงไม่ได้ทดสอบเส้นทาง OIDC และไม่ได้ทดสอบผ่านเบราว์เซอร์
6. ตัวเลขผลรันทั้งหมดมาจาก Linux, Node 22.22.0 ไม่ใช่ Windows
