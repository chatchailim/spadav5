# รายการสิ่งที่ต้องเพิ่มให้ MyAI / Team Agent ทำงานแบบ "เอเจนต์ที่รับผิดชอบงานต่อเนื่อง"

- **รหัสเอกสาร: SPD-ANL-002** · ร่าง 2026-09-30 · ต่อจาก [SPD-ANL-001](DOT-VS-MYAI-TEAMAGENT-COMPARISON.md)
- ฐานข้อเท็จจริง: อ่านโค้ด/เอกสารใน spada-monorepo และ onemanos-setbox (ไม่ได้รันระบบ ไม่ได้ทดสอบ)
- ขอบเขตต้องไม่ขัด ADR 0014 (SetBox นอก SPADA), ADR 0016 (Team Agent ไม่มี DID ของตัวเอง, การอนุมัติที่ SPADA เชื่อคือ actor assertion), D2.1 (MyAI อิสระเฉพาะงานย้อนกลับได้)

## 1. สถานะจริงที่พบ

| ส่วน | สิ่งที่มีอยู่ | ข้อสังเกต |
|---|---|---|
| **MyAI (Phase 0–1)** | `myai-inference-service`: ถาม–ตอบผ่าน `POST /api/v1/spada/myai/ask` เรียกโมเดลท้องถิ่น (Ollama หรือ vLLM/Qwen) ผ่านด่าน TrustScore และ BookChain gateway มี quota และ metering ไม่เก็บข้อความในบัญชีหรือ log | ปัจจุบันเป็น **ถามแล้วตอบ (Q&A)** ยังไม่มี tool ใช้งาน ตัวตั้งเวลา ความจำต่อเนื่อง หรือ planner |
| **Shared AI Host** | `ai-host-gateway` หน้า vLLM บน DGX: key ต่อโหนด, จำกัดการใช้พร้อมกัน, นับการใช้, ไม่เก็บข้อความ | ทางเข้าโมเดลรวมที่ใช้ต่อยอดได้ (ADR 0027) |
| **Team Agent (SetBox)** | ไม่ได้เป็นรันไทม์เอเจนต์ของเราเอง แต่เป็นเอเจนต์ภายนอก (Claude Code, Claude Desktop, Codex) ที่ผูกกับ **MCP server `onevault`** ตามบทบาท architect / secretary / builder โดยเครื่องรองใช้โทเคนบทบาทจาก PC1 ป้องกันการยกระดับสิทธิ์ และมี SKILL.md ต่อบทบาท | มีแกนที่ดี: MCP, บทบาทแยก, สิทธิ์ผูกโทเคน ยังขาดชั้นที่ทำให้ "ทำต่อเนื่องเอง" |

**ข้อสรุป**: ช่องว่างไม่ได้อยู่ที่ "ต้องเขียน AI ใหม่" แต่ต้องเพิ่มชั้นควบคุมและชั้นเวลา/ความจำรอบเอเจนต์ที่มีอยู่ และให้ MyAI ก้าวจาก Q&A เป็นผู้ทำงานภายใต้ขอบเขต

## 3. ข้อแตกต่างของ MyAI กับ Team Agent ในการเพิ่ม

| เรื่อง | MyAI (ใน SPADA) | Team Agent (นอก SPADA) |
|---|---|---|
| ระดับอิสระสูงสุด | Steward เฉพาะงานย้อนกลับได้ (D2.1) | Steward เฉพาะงานย้อนกลับได้ งานอื่นต้องมีลายเซ็นเจ้าของ |
| ตัวตน | `did:spada:agent` ตามที่สงวนไว้ ต้องผ่าน Constitutional | ห้ามมี DID ของตัวเอง ทำในนามเจ้าของ |
| สิ่งที่ควรเริ่ม | ข้อ 1, 5 แล้ว 4 บนอุปกรณ์เจ้าของ | ข้อ 1, 2, 3, 4, 6 บน SetBox (เร็วและใกล้ธุรกิจจริงกว่า) |
| โมเดล | ท้องถิ่นเท่านั้น (on-device) | เลือกได้ตามนโยบายข้อ 9 |

**แนะนำให้ทำที่ Team Agent ก่อน** เพราะโครงสร้างมี MCP และบทบาทอยู่แล้ว และลูกค้ากิจการอย่างกรณีน้องอิงอรใช้ SetBox เป็นหลัก ส่วน MyAI ค่อยยกระดับหลังรูปแบบ Responsibility นิ่ง

## 4. แผนเป็นเฟส

| เฟส | เนื้อหา | ผลที่ผู้ใช้เห็น | เกณฑ์ผ่าน |
|---|---|---|---|
| F0 (ไม่ต้องเขียนโค้ดมาก) | ตัดสิน ADR Responsibility, นโยบายโมเดลภายนอก, doc 335 ข้อ 9; เลือกงานทดสอบ 10 งาน | เอกสารกำหนดชัด | Lead อนุมัติ |
| F1 | ข้อ 1, 2, 3, 11 บน SetBox | ตั้ง "งานที่ให้ดูแล" ได้ ระบบถาม/หยุดตามกฎ มีลายเซ็นและรายงาน | ทดสอบกรณีต้องถาม 20 กรณีผ่านหมด |
| F2 | ข้อ 4, 5, 6, 8 | สรุปเช้าอัตโนมัติ ตามงานต่อเนื่อง แจ้งเมื่อต้องตัดสินใจ | 10 งานจริงผ่านเกณฑ์ความถูกต้องและเวลา |
| F3 | ข้อ 7, 9, 10 | ใช้กับอีเมลและแอปจริง | ทดสอบ prompt injection ผ่าน |
| F4 | MyAI ยกระดับเป็นผู้ทำงานภายใต้ขอบเขต, ข้อ 12 | ผู้ช่วยส่วนตัวต่อเนื่อง | ตัดสินภายหลัง |

ขนาดงานและระยะเวลา: **ยังไม่ประเมินเป็นตัวเลข** เพราะต้องดูโค้ด `onevault-mcp` และโครงสร้าง SetBox ในรายละเอียดก่อน ผมเสนอให้ออกใบงานสำรวจ (spike) ก่อนเริ่ม F1

## 5. ความเสี่ยงที่ต้องคุม

1. **เอเจนต์ทำผิดพลาดแม้มีกฎ** → ขั้นตรวจ (ข้อ 6), kill switch (ข้อ 11), จำกัดเฉพาะงานย้อนกลับได้
2. **ความเหนื่อยจากการกดอนุมัติ** (ถามบ่อยจนผู้ใช้กดผ่านโดยไม่อ่าน) → รวมคำขอเป็นชุด, ใช้ pre-approved สำหรับงานความเสี่ยงต่ำ, ตรวจสถิติอนุมัติ
3. **ข้อมูลรั่วผ่านโมเดลภายนอก** → นโยบายข้อ 9 ตั้งค่าเริ่มต้นเป็นปิด
4. **การอ้างเกินจริง** → ยังไม่บอกลูกค้าหรือนักลงทุนว่า "ทำเหมือน dots" จนกว่าผ่านแผนพิสูจน์ใน SPD-ANL-001 ข้อ 6
5. **ขอบเขต ADR** → ห้ามยกฟังก์ชันของ Team Agent เข้ามาไว้ใน SPADA และห้ามออก DID ให้ Team Agent

## 6. สิ่งที่ต้องให้ Lead ตัดสิน

1. เริ่มที่ Team Agent (แนะนำ) หรือ MyAI
2. อนุมัติให้ออก ADR Responsibility ฝั่ง OneManOS
3. อนุญาตโมเดลภายนอกหรือไม่ และข้อมูลใดห้ามออก
4. ตัดสิน doc 335 ข้อ 9 เป็นกฎเหล็ก
5. ออกใบงานสำรวจ (spike) ของ `onevault-mcp` และตัวตั้งเวลา
