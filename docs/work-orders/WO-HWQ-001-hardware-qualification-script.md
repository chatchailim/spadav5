# WO-HWQ-001: สคริปต์รับรองฮาร์ดแวร์ SetBox (ใช้ได้ทั้งแบบเดี่ยวและแบบเชื่อมต่อ)

## 1. Mission

สร้างเครื่องมือที่ **วัดคุณสมบัติจากเครื่องจริง** ตามรายการ 10 ข้อของ doc 344 §3 แล้วออก **รายงานพร้อมหลักฐานที่ตรวจย้อนได้** และ **ตัดสินระดับแบบกำหนดได้แน่นอน (deterministic)** เพื่อให้ผู้ลงนามตัดสินใจลงทะเบียนรุ่นโดยไม่ต้องเชื่อเอกสารผู้ขาย ใช้ได้กับ:

- การรับรองตัวอย่างก่อนสั่งล็อต (มาตรฐานจัดซื้อ D4)
- การสุ่มวัดซ้ำตอนตรวจรับ (D6) และการเทียบความสอดคล้องกับตัวอย่าง
- การอนุมัติเครื่องของลูกค้ารายกรณี (แบบเดี่ยว)
- การรับรองใหม่เมื่ออัปเดต BIOS/firmware (D8)

## 2. สิ่งที่ WO นี้ **ไม่ทำ**

- **ไม่เขียนทะเบียนอัตโนมัติ** สคริปต์ออก "ข้อเสนอรายการ" ให้มนุษย์ลงนามเท่านั้น (Steward/ผู้ลงนามเป็นผู้เพิ่มรายการ)
- **ไม่เปิด `APPLIANCE`** และไม่แตะ `SPADADeviceAssurance` หรือ verifier ใดใน SPADA
- **ไม่ตัดสินว่ารุ่นใดควรซื้อ** และไม่กำหนดเนื้อหา EK vendor-root allowlist (เป็นหน้าที่ของ Technical Owner ตาม ADR 0017 §7.6 สคริปต์รับ allowlist เป็นไฟล์นำเข้า)
- ไม่แก้ไขเครื่องที่วัด: **อ่านอย่างเดียว**

## 3. สิ่งที่วัดได้ด้วยซอฟต์แวร์ และสิ่งที่วัดไม่ได้ (อ่านก่อนออกแบบ)

| รายการ | วัดด้วยซอฟต์แวร์ได้? | วิธีที่เสนอ (บน Linux) | หมายเหตุ |
|---|---|---|---|
| มี TPM 2.0 จริง | ✅ | `tpm2_getcap properties-fixed` (family/revision) | |
| ผู้ผลิตและ firmware ของ TPM | ✅ | ค่า manufacturer, vendor string, firmware version จาก properties-fixed | |
| ชนิด dTPM / fTPM / iTPM | ⚠️ **ไม่แน่นอน** | ใช้รหัสผู้ผลิต TPM, ข้อมูล ACPI/DMI เป็น **ข้อบ่งชี้ (heuristic)** | ADR 0020 ยืนยันว่า **ชนิดไม่ใช่เกณฑ์ตัดสิน** ให้บันทึก "typeEvidence" และขอคำยืนยันผู้ขายเป็นลายลักษณ์อักษร |
| เป็น vTPM (ต้องปฏิเสธ) | ⚠️ ตรวจได้เฉพาะกรณีอยู่ใน VM | ตรวจ hypervisor (เช่น `systemd-detect-virt`, ธง hypervisor ใน CPUID/DMI) และผู้ผลิต TPM เป็นซอฟต์แวร์จำลอง | ตรวจพบ VM = REJECTED ทันที · **ตรวจไม่พบ VM ไม่ได้พิสูจน์ว่าเป็นฮาร์ดแวร์จริงเต็มที่** จึงต้องคู่กับ EK cert chain |
| EK certificate อ่านได้ | ✅ | อ่านจาก NV index ตามโปรไฟล์ TCG EK Credential (RSA 2048: `0x01C00002`, ECC P-256: `0x01C0000A` ตามที่ผมเข้าใจ **ต้องยืนยันกับเอกสาร TCG ฉบับปัจจุบันตอน implement**) | ห้ามดึง certificate จากอินเทอร์เน็ตโดยค่าเริ่มต้น (ดูกฎ) |
| chain ถึง vendor root ใน allowlist | ✅ (ออฟไลน์) | ตรวจกับไฟล์ allowlist ที่ผูก hash ไว้ | allowlist ว่าง = ตรวจไม่ได้ = ไม่ถึงระดับ APPLIANCE-CANDIDATE |
| สร้าง AK และ `TPM2_Certify` ผ่าน | ✅ | สร้างวัตถุชั่วคราว (transient) แล้วรัน certify | ไม่ทำวัตถุถาวร ไม่เปลี่ยน owner auth |
| PCR bank SHA-256 ครบ | ✅ | `tpm2_getcap pcrs` | |
| อ่าน event log ได้ | ✅ | `/sys/kernel/security/tpm0/binary_bios_measurements` และ `tpm2_eventlog` | |
| Secure Boot เปิดและอยู่ใน user mode | ✅ | อ่านตัวแปร EFI `SecureBoot` และ `SetupMode` (ต้องเป็นเปิด และ SetupMode = 0) | เครื่องมือรันต้องบูตผ่าน Secure Boot ได้ (ใช้ live image ที่ลงนาม) |
| **ปิดช่องดีบัก (DCI/JTAG) ถาวรได้** | ❌ **ซอฟต์แวร์วัดไม่ได้** | **ขั้นตอนมนุษย์**: ตรวจตัวเลือก BIOS/เอกสารผู้ขาย ถ่ายภาพหน้าจอ บันทึกชื่อผู้ตรวจ และ hash ของภาพ | ไม่มีหลักฐาน = "ไม่ครบ" ห้ามถือว่าผ่าน |
| รุ่น/BIOS/ผู้ผลิตเครื่อง | ✅ | อ่านจาก DMI (`bios_version`, `bios_vendor`, `product_name`, `sys_vendor`) | serial เป็นข้อมูลระบุตัว ดูกฎเรื่องข้อมูลส่วนบุคคล |

**ข้อสรุปเชิงออกแบบ**: สคริปต์ตัดสินได้เฉพาะสิ่งที่วัดได้ สิ่งที่วัดไม่ได้ต้องมีหลักฐานจากมนุษย์ และ **ผลรวมล้มเหลวแบบปิด (fail closed)**

## 4. Phases

| # | งาน | Acceptance |
|---|---|---|
| **H0** | Preflight: ตรวจสภาพแวดล้อม (root, tpm2-tools มีครบและเวอร์ชันถูกบันทึก, ไม่มีเครือข่ายโดยค่าเริ่มต้น), ขอความยินยอมเมื่อเป็นเครื่องลูกค้า, ประกาศ "อ่านอย่างเดียว" | สคริปต์หยุดถ้าไม่มี consent flag ในโหมดเครื่องลูกค้า |
| **H1** | ข้อมูลเครื่องและ BIOS (DMI) | บันทึก vendor/product/BIOS · serial ถูกปกปิดโดยค่าเริ่มต้น |
| **H2** | สำรวจ TPM: มีไหม, spec, ผู้ผลิต, firmware, ข้อบ่งชี้ชนิด | ผลถูกต้องบน fixture ทุกแบบ (ข้อ 8) |
| **H3** | อ่าน EK certificate และตรวจ chain กับ allowlist | allowlist ว่าง/ไม่มี cert = ผล "unverified" ไม่ใช่ "pass" |
| **H4** | สร้าง AK ชั่วคราวและ certify | สำเร็จ/ล้มเหลวบันทึกชัด ไม่ทิ้งวัตถุถาวร |
| **H5** | PCR banks และ event log | SHA-256 ครบ และอ่าน log ได้ |
| **H6** | Secure Boot (SecureBoot=1, SetupMode=0) | ตรงตามจริงบน fixture |
| **H7** | ตรวจการทำงานใน VM/hypervisor | VM = REJECTED พร้อมเหตุผล |

## 5. รูปแบบหลักฐานและรายงาน

- **evidence เป็น JSON Lines แบบ hash chain** ตามรูปแบบของ `scripts/ops/personal-key-token/evidence/` (ฟิลด์: `seq`, `ts`, `phase`, `checkId`, `result`, `note`, `operator`, `prevHash`, `hash`) เพื่อความคุ้นเคยของทีม
- **สูตร hash เสนอให้ใช้สัญญา C2 (ADR 0021)**: `"sha256:" + hex(SHA-256(UTF-8(RFC 8785(record ยกเว้น hash))))` เพื่อไม่เพิ่มสูตรที่สี่ในระบบ (โค้ดอ้างอิง: `architecture/contracts/c2-fact-hash/`) · หมายเหตุ: ตัวอย่าง evidence ที่ผมเห็นของ token ใช้ hash 64 หลักไม่มี prefix ผมไม่ได้ตรวจว่าสูตรตรงกับ C2 หรือไม่ ให้ผู้พัฒนาตรวจก่อน
- **ตัวตรวจ chain** (`verify-chain`) ที่ล้มเมื่อมี record ถูกแก้ ลบ หรือสลับลำดับ
- **รายงานสรุป** (JSON + Markdown ภาษาไทย): ข้อมูลเครื่อง, ผลรายข้อ (pass/fail/unverified/manual), ข้อบ่งชี้ชนิด TPM, ผลระดับ, เหตุผล, hash ของ evidence log, เวอร์ชันเครื่องมือ, ผู้ตรวจ
- **ข้อเสนอรายการทะเบียน** (ตาม §2 ของ doc 344 หรือ `HARDWARE-REGISTRY-STANDALONE-TEMPLATE`) เป็นไฟล์แยก ไม่เขียนทะเบียนเอง

## 6. กติกาตัดสินระดับ (deterministic)

| ผล | เงื่อนไข |
|---|---|
| ❌ **REJECTED** | ไม่มี TPM 2.0 · **หรือ** ตรวจพบ VM/vTPM · **หรือ** Secure Boot เปิดไม่ได้/ไม่อยู่ใน user mode ที่ตั้งได้ · **หรือ** ผู้ตรวจยืนยันว่าปิดช่องดีบักถาวรไม่ได้ |
| ⚪ **INCOMPLETE** (ไม่ลงทะเบียน) | ไม่ถึง REJECTED แต่ข้อใดข้อหนึ่งของเกณฑ์ฐาน HB ล้มเหลวหรือยืนยันไม่ได้ (เช่น อ่าน event log ไม่ได้, PCR ไม่ครบ, หลักฐานช่องดีบักไม่ครบ) · ลองใหม่ได้หลังแก้ BIOS/เก็บหลักฐานเพิ่ม |
| 🟡 **HB-PASS** (= NATIVE-ELIGIBLE) | ผ่านเกณฑ์ HB ทุกข้อ แต่ไม่มี EK certificate หรือ chain ตรวจไม่ได้ |
| 🟢 **HB-PASS+EK** (= APPLIANCE-CANDIDATE) | HB-PASS + อ่าน EK cert ได้ + chain ถึง root ใน allowlist + `TPM2_Certify` สำเร็จ |

> **ข้อสังเกตเรื่องช่องว่างใน ADR 0020**: ADR ระบุเฉพาะ REJECTED กับสองระดับที่ผ่าน ไม่ได้นิยามกรณี "ล้มเหลวบางข้อแต่ไม่ถึง REJECTED" ผมเสนอสถานะ INCOMPLETE (ไม่ลงทะเบียน = fail closed) และควรให้ Lead/Steward รับรองการเพิ่มสถานะนี้
> **ต่อให้ HB-PASS+EK ก็ยังไม่ใช่การเปิด `APPLIANCE`** เพดานระบบยังเป็น `NATIVE` ตาม ADR 0017 §7.5

## 7. กฎที่ห้ามละเมิด (ละเมิด = reject งาน)

- **อ่านอย่างเดียว**: ห้ามเรียก `tpm2_clear`, `tpm2_changeauth`, การตั้ง/เปลี่ยน lockout หรือ owner auth, การเขียน NV index หรือ persistent handle (`tpm2_evictcontrol`) · ตัวรันคำสั่งต้องใช้ **รายการคำสั่งที่อนุญาต (allowlist)** และมีเทสต์ยืนยัน
- **ห้ามใช้เครือข่ายโดยค่าเริ่มต้น** (รวมการดึง EK certificate จากเซิร์ฟเวอร์ผู้ผลิต) เปิดได้เฉพาะด้วยธงชัดเจนและบันทึกใน evidence
- **ห้ามเขียนลงดิสก์ภายในของเครื่องที่วัด** ผลลัพธ์เขียนลงสื่อภายนอก/หน่วยความจำ และแนะนำให้รันจาก live image ที่ไม่ persist (ไม่แตะระบบของลูกค้า)
- **ข้อมูลส่วนบุคคลและข้อมูลระบุตัว**: serial number, MAC, ชื่อผู้ใช้ ปกปิด (hash พร้อม salt ที่ผู้ตรวจเก็บ) โดยค่าเริ่มต้น · เปิดเผย serial ได้เฉพาะเมื่อจำเป็นต่อรายการรายตัวของแบบเดี่ยวและได้รับความยินยอม
- **ห้ามอนุมัติหรือเปลี่ยนระดับด้วยมือในสคริปต์** การเปลี่ยนผลต้องเป็น record ใหม่ที่ระบุผู้ตัดสินและเหตุผล
- **ห้ามเรียกผลว่าเป็นการรับรองจาก SPADA** ผลของ Track S เป็นการรับรองฝั่งเรา ไม่ใช่ `deviceAssurance`
- **ห้ามตัดสินชนิด TPM จากซอฟต์แวร์เพียงอย่างเดียวแล้วอ้างว่าแน่นอน** ให้ระบุว่าเป็นข้อบ่งชี้

## 8. เกณฑ์ตรวจรับ (ต้องผ่านทั้งหมด)

**ก. บน fixture (ไม่ต้องมีฮาร์ดแวร์)** — ใช้ผลคำสั่งที่บันทึกไว้ (golden transcripts) และ certificate ชุดทดสอบที่สร้างเอง (chain สังเคราะห์ที่ไม่ใช่ของผู้ผลิตจริง):

| กรณีทดสอบ | ผลที่ต้องได้ |
|---|---|
| TPM 2.0 จริงจำลอง มี EK cert chain ถึง root ทดสอบใน allowlist, Secure Boot ปกติ, หลักฐานช่องดีบักครบ | HB-PASS+EK |
| TPM มี แต่ไม่มี EK cert | HB-PASS |
| ไม่มี TPM | REJECTED |
| รันใน VM (swtpm หรือเทียบเท่า) | REJECTED (VM) |
| Secure Boot ปิด | REJECTED |
| SetupMode = 1 (ยังไม่ enroll key) | REJECTED |
| อ่าน event log ไม่ได้ | INCOMPLETE |
| PCR ไม่ครบ SHA-256 | INCOMPLETE |
| ไม่มีหลักฐานช่องดีบัก (H8) | INCOMPLETE |
| ผู้ตรวจยืนยัน "ปิดช่องดีบักไม่ได้" | REJECTED |
| allowlist ว่าง แม้ chain ดูถูก | ไม่เกิน HB-PASS |

**ข. ความถูกต้องและความปลอดภัยของเครื่องมือ**

- **รันซ้ำด้วยข้อมูลเดียวกัน ได้ผลระดับและ hash เหมือนเดิม** (deterministic)
- **ตัวตรวจ chain ล้ม** เมื่อแก้ ลบ หรือสลับ record
- **เทสต์ static** ยืนยันว่าตัวรันคำสั่งไม่เรียกคำสั่งนอก allowlist และไม่มีคำสั่งเขียน/ล้าง TPM ในโค้ด
- **รันโดยปิดเครือข่ายแล้วยังผ่าน**
- **ผลลัพธ์ default ไม่มี serial/MAC**
- ผลตรวจ hash ของ H10 ตรวจจับเครื่องที่ BIOS หรือ firmware TPM ไม่ตรงตัวอย่างได้

**ค. บนเครื่องจริง** (ต้องรอเงินซื้อตัวอย่าง จึงเป็นเกณฑ์ที่ปิดภายหลังได้)

- รันบนอย่างน้อยหนึ่งเครื่องจริงของแต่ละรุ่นตัวอย่าง สองรอบ ผลสอดคล้องกัน
- ผู้ลงนามอ่านรายงานและยืนยันว่าตรงกับการสังเกตด้วยมือ (เช่น สถานะ Secure Boot ใน BIOS) ก่อนลงทะเบียน
- ถ้าผลจากสคริปต์ไม่ตรงกับคำตอบผู้ขาย ให้บันทึกความคลาดเคลื่อนตามมาตรฐานจัดซื้อ D4

## 9. ผลลัพธ์ที่ต้องส่งมอบ

- `scripts/ops/setbox-hardware-qualification/` (README, สคริปต์หลัก, ตัวตรวจ chain, เครื่องมือเทียบล็อต, fixtures, เทสต์)
- runbook ภาษาไทยสำหรับผู้ตรวจ (รวมขั้นตอนมนุษย์ H8 และวิธีบูต live image)
- ตัวอย่างรายงานจาก fixture (ข้อมูลสังเคราะห์ทั้งหมด)
- บันทึกใน `AGENT_NOTES.md` ตามธรรมเนียมทีม

## 10. ความเสี่ยงและข้อควรระวัง

| ความเสี่ยง | มาตรการ |
|---|---|
| ผมยังไม่ได้ตรวจดัชนี NV ของ EK certificate และพารามิเตอร์ tpm2-tools กับเอกสารทางการ | ผู้พัฒนายืนยันกับเอกสาร TCG และ tpm2-tools เวอร์ชันที่ใช้ก่อน implement |
| ข้อบ่งชี้ชนิด TPM คลาดเคลื่อน | ไม่ใช้ตัดสินระดับ (ADR 0020) ใช้ EK cert เป็นเกณฑ์ |
| ช่องดีบักวัดด้วยซอฟต์แวร์ไม่ได้ | บังคับขั้นตอนมนุษย์ + หลักฐาน + fail closed |
| ผู้ตรวจกรอกหลักฐานเท็จ | เก็บชื่อผู้ตรวจ ภาพ hash และให้ผู้ลงนามตรวจ (four-eyes เมื่อมีคนที่สอง) |
| เครื่องลูกค้าถูกแตะโดยไม่ตั้งใจ | อ่านอย่างเดียว, live image, consent flag, ไม่เขียนดิสก์ภายใน |
| ขอบเขตแพลตฟอร์ม | อ้างอิง Linux (live image) ก่อน ส่วน Windows เป็นงานภายหลังถ้าจำเป็น (ผมไม่ได้ออกแบบเส้นทาง Windows ในรอบนี้) |

## 11. ขนาดงานและลำดับ

ประมาณการ: H0–H7 และตัวตรวจ chain หนึ่งถึงสองสัปดาห์งานของผู้พัฒนาหนึ่งคน (ประมาณคร่าวๆ ผมไม่ทราบความเร็วของทีม) · H8–H10 เพิ่มอีกสัปดาห์ · การตรวจรับบนเครื่องจริงรอการซื้อตัวอย่าง
ลำดับที่แนะนำ: fixture + กติกาตัดสิน (ข้อ 6, 8ก) → ตัวตรวจ chain → เครื่องมือเทียบล็อต → รอตัวอย่างจริงเพื่อปิด 8ค
