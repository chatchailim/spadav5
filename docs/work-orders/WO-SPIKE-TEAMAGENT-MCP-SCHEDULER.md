- ประเภท: **สำรวจ (spike) ห้ามแก้โค้ดผลิตภัณฑ์** ผลงานคือรายงานหนึ่งฉบับ

- ผู้ทำที่เสนอ: Codex · ผู้ตรวจรับที่เสนอ: Cowork แทน Lead ตามแบบใบงาน POO เดิม · ผู้ตัดสินขั้นสุดท้าย: Lead

## 1. วัตถุประสงค์

ตอบคำถามให้ได้ว่า **ต้องแก้หรือเพิ่มอะไรใน `onevault-mcp` และต้องสร้างตัวตั้งเวลาแบบใด** เพื่อให้ Team Agent รับ "ความรับผิดชอบต่อเนื่อง" (Responsibility) ได้อย่างปลอดภัย โดยไม่ขัดกับ:
- ADR 0014 (SetBox นอก SPADA), ADR 0016 (Team Agent ไม่มี DID ของตัวเอง, การอนุมัติที่ SPADA เชื่อคือ actor assertion ที่เจ้าของลงนาม)
- กฎเดิมของ OneVault: การเขียนต้องผ่านเมธอดของ Warehouse เสมอ, ไม่มี dependency ภายนอก, ติดตั้งแบบออฟไลน์ได้ (Node.js 22+)

## 3. คำถามที่ต้องตอบ

### ส่วน A — `onevault-mcp`

| # | คำถาม | ผลที่ต้องส่ง |
|---|---|---|
| A1 | รายการเครื่องมือทั้งหมด จัดกลุ่มตามบทบาทที่เรียกได้ และจำแนกว่า **ย้อนกลับได้หรือไม่** (อ่าน / เขียนที่แก้ย้อนได้ / เขียนที่ย้อนไม่ได้ เช่น seal, approve, retire, decommission) | ตารางเครื่องมือ × บทบาท × ประเภทผลกระทบ |
| A2 | จุดที่ตัดสินสิทธิ์ก่อนเรียกเครื่องมืออยู่ตรงไหน ใส่ policy engine 4 ทาง (allow / pre-approved / ask / handoff) ได้ที่ใดโดยแก้น้อยที่สุด และเครื่องมือใดมีประตู approval อยู่แล้ว | แผนภาพจุดเสียบ พร้อมอ้าง `ไฟล์:บรรทัด` |
| A3 | ผู้กระทำ (actor) ถูกบันทึกอย่างไรตอนเอเจนต์เรียกเครื่องมือ ตรงกับรูปแบบ C1 หรือไม่ และเอเจนต์ที่ทำแทนเจ้าของบันทึก "เจ้าของ" กับ "เอเจนต์" แยกกันได้หรือไม่ | คำอธิบาย + ตัวอย่างแถว audit จริงจากเครื่องทดสอบ |
| A4 | โทเคนขยายให้พก scope ของ Responsibility (รหัส, เครื่องมือที่อนุญาต, วันหมดอายุสั้น, งบการเรียก) ได้หรือไม่ การเพิกถอนทำได้อย่างไรและมีผลทันทีหรือไม่ | ผลประเมินพร้อมข้อเสนอรูปแบบ claim |
| A5 | **พื้นผิว prompt injection**: เครื่องมือใดคืนข้อความจากเอกสารหรือไฟล์ที่มาจากภายนอกให้เอเจนต์อ่าน และมีเครื่องมือเขียนใดที่เอเจนต์เรียกต่อได้ทันทีหลังอ่าน มีการแยก instruction กับ data หรือไม่ (เชื่อมกับ doc 335 ข้อ 9) | ตารางความเสี่ยง + ข้อเสนอด่านป้องกัน |
| A6 | เจ้าของอนุมัติได้อย่างไรในวันนี้ (admin console, CLI, ฯลฯ) หากต้องผลิต actor assertion ตาม ADR 0016 SetBox มีกุญแจอะไรให้ลงนาม (กุญแจเครื่อง หรือ KeySign) และผ่านเส้นทางใด | แผนภาพเส้นทางอนุมัติปัจจุบันและเส้นทางที่ต้องเพิ่ม |
| A7 | สถานะของ audit chain และ TLS ของ MCP (POO-WO-003) ในโค้ดปัจจุบัน ถ้ายังไม่เสร็จ ผลต่อการออกแบบคืออะไร | ผลตรวจ + ข้อสรุปว่าต้องเสร็จก่อนหรือไม่ |
| A8 | ชุดทดสอบปัจจุบัน: `cd onevault-mcp && ONEVAULT_ROOT=.. node --test test/*.test.js` และ `npm test` ที่ราก ผ่านกี่ข้อ ล้มกี่ข้อ | ผลรันเต็ม (แนบทั้งหมด ห้ามตัดบรรทัด) |

## 4. ขอบเขตและข้อห้าม

1. **อ่านอย่างเดียวกับโค้ดและข้อมูล** ห้ามแก้ไฟล์ผลิตภัณฑ์ ห้าม commit โค้ดเปลี่ยนพฤติกรรม (ยกเว้นไฟล์รายงานตามข้อ 5)
2. รันชุดทดสอบและการลองปลุกเอเจนต์ **บนสำเนาหรือเครื่องทดสอบเท่านั้น** ห้ามใช้ข้อมูลลูกค้าจริง
3. ห้ามเปิดพอร์ตสู่ LAN/อินเทอร์เน็ต เพื่อการทดลอง นอกเครื่องทดสอบที่แยกแล้ว
4. ห้ามใส่ความลับ (โทเคน กุญแจ) ในรายงาน ให้ปิดบังค่าเหลือเฉพาะรูปแบบ
5. ห้าม push เข้า `master` ให้ commit รายงานบน branch `codex/poo-wo-005-spike` แล้ว push ไป `origin` (ตามแบบใบงานเดิม)
6. ห้ามออกหรือแก้ ADR ผลสำรวจเป็นข้อเสนอให้ Lead ตัดสิน
7. ห้ามใช้ข้อความ "ทำได้" หรือ "ผ่าน" โดยไม่มีหลักฐาน (ไฟล์:บรรทัด หรือผลรันจริง) ส่วนที่ไม่รู้ให้เขียนว่า "ไม่ทราบ"

## 5. ผลงานที่ต้องส่ง

รายงานหนึ่งฉบับ `docs/spike/POO-WO-005-teamagent-mcp-scheduler-report.md` มีหัวข้อ:
1. สรุปผู้บริหาร (ไม่เกินหนึ่งหน้า): ทำได้หรือไม่ ต้องเพิ่มอะไร ความเสี่ยงหลัก
2. คำตอบ A1–A8 และ B1–B6 ทีละข้อ พร้อมหลักฐาน
3. แผนภาพจุดเสียบ policy engine และเส้นทางอนุมัติ → actor assertion
4. คำแนะนำหนึ่งทางสำหรับตัวตั้งเวลา (B3) และสิ่งที่ต้องรู้ก่อนตัดสิน (B4)
5. รายการใบงานตามหลัง (F1–F2) พร้อมขอบเขตร่างและ **ขนาดงานโดยประมาณเป็นช่วง** และสมมติฐานที่ใช้ประมาณ
6. รายการสิ่งที่ "ไม่ทราบ" และวิธีหาคำตอบ
