## 2. ผลทางเทคนิคของ B2 และการยืนยันกับซอร์ส

ผมอ่าน `supervisor.js` และ `lib.js` บน master เทียบกับข้อสรุปของ Codex:

| ข้อค้นพบของ Codex | ผลเทียบกับซอร์ส | ระดับ |
|---|---|---|
| **F1** state ใหม่: "Supervisor already running: PID 0" | **ยืนยันสาเหตุ:** บรรทัด 27 ใช้ `0` เมื่อไม่มีไฟล์ PID, บรรทัด 28 เรียก `isAlive(0)` และ `lib.js:16` ใช้ `process.kill(Number(pid), 0)` ซึ่ง PID 0 ไม่ใช่ PID ของโปรเซสจริง จึงอาจคืนค่าจริงและทำให้เริ่มไม่ได้ · เห็นซ้ำใน 2 สภาพแวดล้อม (Server Core VM วานนี้ตามที่ได้รับแจ้ง และ Windows 10 วันนี้) | บั๊กชัดเจน แก้ง่าย |
| **F2** หน่วงรอบ retry ไม่เกิดจริง (restart-scheduled ระบุ 2,000/5,000 ms แต่เริ่มใหม่หลัง 102/76 ms) | **ยืนยันสาเหตุที่ระดับโค้ด:** `startService` (บรรทัด 18) ไม่ตรวจ `nextRestartAt` ก่อนเริ่ม ส่วน `startEligible()` ถูกเรียกจาก `healthCheck` ทุกรอบ monitor (บรรทัด 22) และหลัง service อื่นพร้อม (ใน `startService`) จึงเริ่มบริการใหม่ได้ก่อนครบ backoff · `startService` ยัง `restarts.push(Date.now())` ทุกครั้งที่เริ่ม ทำให้การเริ่มก่อนกำหนด **กินโควตา `maxAttemptsInWindow` เร็วกว่าที่ออกแบบ** | บั๊กความถูกต้อง กระทบการจำกัด restart |
| **F3** crash หลัง effect ก่อน complete: 2 effects, 1 complete | ไม่มีกลไก idempotency/dedupe ในชุด supervisor + worker สอดคล้องกับที่ ADR/แผนระบุว่ายังไม่มี durable job | ช่องว่างสถาปัตยกรรม (ไม่ใช่บั๊กเดี่ยว) |
| **F4** หยุดข้ามรอบแล้วไม่มี catch-up | ตรงกับที่ supervisor ไม่ใช่ scheduler (ไม่มี cadence ในโค้ด) | ช่องว่างที่รู้อยู่แล้ว |
| กรณี 08 supervisor-only crash | Codex ไม่สรุปสาเหตุการจบของ worker เดิม เพราะไม่ได้เก็บ exit event · **เห็นด้วยที่ไม่สรุปเกินหลักฐาน** | ข้อจำกัดของ harness |

**ข้อสังเกตเรื่องรายงานวันก่อน:** Server Core VM รายงานว่า retry รอ 2 และ 5 วินาที แต่ raw log วันนี้ขัดกัน Codex ไม่ตัดสินย้อนหลังว่าผิดและขอเทียบ timestamp จริง **ผมเห็นด้วย** สาเหตุที่เป็นไปได้ตามโค้ดคือพฤติกรรมขึ้นกับความถี่ของ `healthCheck` (วันนี้ monitor 200 ms; production 15 วินาที) ผลจึงต่างตามสภาพแวดล้อมได้ แต่ **ยังยืนยันไม่ได้** จนกว่าจะได้ raw log ของ VM รอบเมื่อวาน (ยังไม่ได้รับ)

## 5. คำแนะนำต่อ Lead

1. **ยังไม่เปิดการเขียนหรืออนุมัติอัตโนมัติของเอเจนต์** (กฎถาวร SPD-DEC-005 ข้อ 6) ผลรอบนี้ **เสริมเหตุผล**: ไม่มี idempotency และ backoff บังคับใช้ไม่ได้
2. **แยกใบงานแก้ออกจากสไปก์** (Codex เสนอ ผมเห็นด้วยและเสนอขนาด/ลำดับ):
   - **ใบงานเล็ก (ทำได้ทันที):** ตรวจ PID ให้ถูกต้องก่อนเรียก `isAlive` (ไม่มีไฟล์/PID ผิดรูป/0 ต้องถือว่าไม่ทำงาน) พร้อมเทสต์ state ใหม่ และ PID ผิดรูป
   - **ใบงานกลาง:** บังคับ `nextRestartAt` ในทุกทางเข้า `startService` และไม่นับการเริ่มก่อนกำหนดเข้าโควตา restart พร้อมเทสต์ที่วัดเวลาจริงบน config ที่ monitor สั้นและยาว
   - **ใบงานใหญ่ (ผูกกับ F1 / SPD-ADR-D04):** durable job + idempotency key + ที่เก็บผลต่อ attempt ซึ่งเป็นส่วนของ Responsibility/scheduler ไม่ใช่แก้ supervisor อย่างเดียว (การแก้ PID อย่างเดียวไม่ปิดข้อกำหนดอื่น ตามที่ Codex ระบุ)
3. **สั่งให้ผู้ทำส่ง A1** ต่อ (ไม่ต้องใช้บัญชีหรืองบ) และส่ง raw log ของ VM รอบเมื่อวาน เพื่อเทียบเรื่อง backoff
4. **Lead ยืนยันเครื่องทดลอง** (ข้อ 4) และระบุอุปกรณ์/บัญชีสำหรับ A6, บัญชีและวงเงินสำหรับ B4 ใน SPD-WO-004
5. ยังไม่รับขั้นสุดท้ายจนกว่า A1, A6, B2 (ส่วนที่ค้าง), B4 และข้อสังเกตเดิมใน SPD-REV-001 ปิด
