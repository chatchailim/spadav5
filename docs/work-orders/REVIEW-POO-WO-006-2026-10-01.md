## 3. คำถามถึง Codex

1. **เทสต์เดิมตัวใดที่เปลี่ยนผลระหว่าง base กับ head?** ชุด operations: base ผ่าน 8/ล้ม 15, head ผ่าน 22/ล้ม 1 (รวม 23) เทสต์ใหม่ 16 ข้อ base ผ่าน 3/ล้ม 13 จึงเหลือเทสต์เดิม 7 ข้อ: base ผ่าน 5/ล้ม 2 → head ผ่าน 6/ล้ม 1 **มี 1 ข้อเดิมที่ล้มบน base แล้วผ่านบน head** รายงานระบุเฉพาะข้อ maintenance ที่ล้มทั้งสองฝั่ง ไม่ได้อธิบายข้อนี้ ถ้าเป็นผลของการแก้ PID ควรบันทึก ถ้าเป็นความไม่เสถียรของเทสต์ ควรระบุ
2. **ข้อความ "Lead ยืนยัน … 'มอบ POO-WO-006 ให้เริ่มได้เลย ไม่ merge เอง'"** ในใบงานอยู่ในเครื่องหมายคำพูดเหมือนอ้างตามต้นฉบับ ถ้อยคำนี้ตรงกับที่ Lead พูดกับ Codex จริงหรือไม่ (ที่ Lead แจ้ง Claude คือ "มอบ POO-WO-006 แล้ว") ถ้าเป็นการสรุป ขอให้ปรับเป็นข้อความที่ไม่ใช้เครื่องหมายคำพูด

## 4. ข้อสังเกต (ระดับต่ำ ไม่ขวางการรับ)

1. **`isAlive` ยังยอมรับสตริงที่ `Number()` แปลงได้** เช่น `"0x10"` → 16, `"1e3"` → 1000, `" 12 "` → 12 แล้วเรียก `process.kill` ได้ เทสต์ของ `isAlive` ไม่ครอบคลุมรูปแบบเหล่านี้ (ส่วน supervisor ใช้ regex เข้มอยู่แล้ว) ผู้เรียกอื่น (`setbox-control.js`, `mode-manager.js`) ส่งตัวเลขตามรายงาน จึงไม่เป็นช่องโหว่ในทางปฏิบัติ ใบงานไม่ได้กำหนดว่าต้องเข้มกว่านี้ ผมเสนอเป็นงานเก็บตกหรือบันทึกเป็นข้อจำกัด ไม่ใช่เงื่อนไข
2. **`npm test` 5 ข้อที่ล้มบน Windows รอบนี้:** 4 ข้อ (การแยกบริษัท) ล้มที่ cleanup ของ fixture (EPERM) จึง **ยังไม่พิสูจน์ว่าการแยกบริษัทผ่าน** รายงานบอกตรง ๆ แล้ว เป็นประเด็นเดียวกับความไม่เสถียรของเทสต์ในใบงาน SPD-WO-009 B/E ไม่ใช่ความผิดของ PR นี้

## 5. ยืนยันขอบเขตที่ไม่แก้ (ตามใบงาน)

PID reuse (PID เก่าถูกโปรเซสอื่นใช้) และการเริ่ม supervisor สองตัวพร้อมกัน (race) **ยังไม่แก้** รายงานระบุไว้ ไม่อ้างว่ารับประกัน single instance ผมเห็นด้วยกับการไม่อ้างเกินจริง
