## 3. ชิ้นงานและเกณฑ์รับงาน

### D1 · ตัวอย่างข้อมูล (body) ของเส้นทางธุรกิจ

- **ทำ:** สำหรับโมดูล `sales`, `accounting`, `stock`, `purchase`, `payroll`, `tax`, `leave`, `time`, `employees`, `reports` (ตามลำดับนี้) ทำชุดข้อมูลสังเคราะห์ที่รันได้ครบวงจรตาม UC-T11 (ขาย→ภาษี→ปิดงวด), UC-T12 (จัดซื้อ→สต็อก), UC-T13 (เงินเดือน/ลา/เวลา) โดย **อ่านรูปแบบ body จากโค้ดโมดูลและเทสต์เดิม** ไม่ใช่คาดเดา
- **ส่งมอบ:** ไฟล์ fixture JSON + สคริปต์รัน (แนวเดียวกับ `docs/testdata/smoke-dms.js` ใน repo `spadav5`) ที่เริ่มเซิร์ฟเวอร์ชั่วคราว ยิงคำขอตามลำดับ และพิมพ์ PASS/FAIL ต่อ TC
- **เกณฑ์รับ:** (1) สคริปต์รันจบ exit 0 บน Linux **และ Windows** (2) ทุกเส้นทางที่ใช้มีผลลัพธ์ที่คาดหวังเป็นตัวเลข/รหัส ไม่ใช่แค่ "200" (3) มีเคสสิทธิ์ถูกปฏิเสธและเคสข้อมูลผิดอย่างน้อยอย่างละ 1 ต่อโมดูล (4) `node scripts/scan-before-release.js` ยัง exit 0 — **ระวัง** เลข 13 หลักที่ดูเหมือนเลขผู้เสียภาษีในไฟล์ที่ติดไปกับชุด (ดูข้อสังเกตใน TestSpec ภาค 6.5) ให้ใช้รูปแบบ `000000000000N` และตรวจว่า fixture อยู่นอกรายการไฟล์ที่ `build-kit.js` คัดเข้าชุด หรือยืนยันว่าสแกนผ่าน

### D2 · แมตทริกซ์สิทธิ์จากโค้ด

- **ทำ:** (ก) ตาราง บทบาทโทเคน MCP 4 บทบาท (`architect secretary builder operator`) × เครื่องมือ `onevault_*` ทั้งหมดที่พบในซอร์ส (ได้/ไม่ได้ + อ้างบรรทัดโค้ด) (ข) ตาราง 10 บทบาทเอกสาร (`OWNER … ADMINISTRATOR`) × การกระทำ (view, search, create_version, …) ตามนโยบายสิทธิ์เริ่มต้น (ค) อธิบายว่าทำไมเอกสารระบุเครื่องมือ 25 ตัว แต่ซอร์สมี 34 ชื่อ (Codex ตรวจแล้ว; ตัวเลข 35 ที่เคยเขียนเป็นการนับผิดของผู้ร่าง) (KI-05) และจำนวนขั้นซ้อมติดตั้ง 21 กับ 22
- **ส่งมอบ:** `work-orders/reports/PERMISSION-MATRIX-<วันที่>.md` + เทสต์อัตโนมัติที่ยืนยันทุกช่องของตาราง (generate ตารางจากโค้ดได้ถ้าทำได้ เพื่อกันตารางล้าสมัย)
- **เกณฑ์รับ:** ทุกช่อง "ไม่ได้" ถูกยืนยันด้วยการเรียกจริงที่ได้ข้อผิดพลาดตามที่ระบุ · ช่องที่เอกสารกับโค้ดขัดกัน ต้องรายงานเป็นข้อค้นพบ ไม่ปรับโค้ดให้ตรงเอกสาร

### D3 · ตามรอยรายเส้นทางของ 171 เส้นทางธุรกิจ (แทนฮิวริสติก KI-06)

- **ทำ:** สร้างตาราง เส้นทาง → ไฟล์เทสต์ + ชื่อเทสต์ที่ครอบคลุมจริง (อ่านเทสต์ ไม่ใช่ค้นสตริง) ระบุเส้นทางที่ไม่มีเทสต์เลข
- **ส่งมอบ:** `work-orders/reports/BUSINESS-ROUTE-TRACE-<วันที่>.md` (และแก้ภาคผนวก B ของ TestSpec ผ่าน PR แยกใน repo `spadav5` ถ้า Lead สั่ง)
- **เกณฑ์รับ:** ครบ 171 แถว ทุกแถวมีหลักฐาน (ไฟล์:ชื่อเทสต์) หรือเขียนว่า "ไม่มี" · สุ่มตรวจ 20 แถวโดยผู้ตรวจ ต้องตรง

### D4 · สืบสวน KI-01 และ KI-02 (รายงานและข้อเสนอเท่านั้น)

- **ทำ:** ทำซ้ำปัญหาด้วยสคริปต์ที่ `docs/testdata/smoke-dms.js` (ดู `TC-DMS-003`, `TC-DMS-007`) · สืบจากประวัติ git/เอกสารว่าพฤติกรรมเป็นเจตนาหรือไม่ · **การยืนยัน KI-02 ในเบราว์เซอร์ด้วยบัญชีพนักงาน เป็นงานของ Antigravity (WO-TST-002 ข้อ E1)** ให้อ้างผลของเขา และยืนยันฝั่งโค้ด/ฐานข้อมูลเอง · เสนอวิธีแก้ที่เล็กที่สุดพร้อมเทสต์ที่จะล้มก่อนแก้และผ่านหลังแก้
- **ส่งมอบ:** `work-orders/reports/KI-01-KI-02-INVESTIGATION-<วันที่>.md` · **ห้ามเปลี่ยนโค้ดผลิตภัณฑ์** ในใบงานนี้ ถ้าต้องการลงมือแก้ ให้ส่ง `type: blocker`/`requires_human: true` ขออนุมัติ Lead ก่อน
- **เกณฑ์รับ:** รายงานบอกชัดว่า (ก) ทำซ้ำได้ไหมบน Windows (ข) ผู้ใช้จริงได้รับผลอย่างไร (อ้างผลเบราว์เซอร์จาก WO-TST-002) (ค) ตัวเลือกการแก้ 2 ทาง พร้อมข้อดี-ข้อเสีย (ง) คำแนะนำ

## 4. กฎการทำงาน (ตามโปรโตคอลของโครงการ)

1. เช็กกล่องจดหมายก่อนเริ่ม ก่อน commit และเมื่อติดขัด · ขอ Work Claim ก่อนแก้ไฟล์ในโซนที่ใช้ร่วม
2. PR เล็ก หนึ่งเรื่อง (แนะนำแยก D1 / D2+D3 / D4) พร้อมหัวข้อ Summary และผลกระทบตามแม่แบบ PR ของ repo · **DCO sign-off เป็นการรับรองของมนุษย์ Codex ไม่ใส่แทน**
3. CI ต้องเขียวบนคอมมิตล่าสุดก่อนส่งตรวจ
4. รายงานผลต้องแยก **"รันจริงแล้ว"** ออกจาก **"อ่านโค้ดอย่างเดียว"** เสมอ และต้องมีหัวข้อ "สิ่งที่ไม่ได้ทดสอบ"
5. ข้อมูลสังเคราะห์เท่านั้น · ห้ามเปลี่ยน `package.json` ให้มี dependency
6. พบสิ่งที่ขัดกับ `TestSpec.md` ให้รายงานเป็นข้อเสนอแก้ TestSpec ไม่ต้องแก้เอกสารนั้นเอง (เจ้าของคือ Claude/Lead)
