## 1. เป้าหมาย

ให้มีหลักฐานจากเบราว์เซอร์จริงสำหรับ TC ระดับ L3 ที่ TestSpec ระบุว่า "ออกแบบ-ยังไม่รัน" โดยเฉพาะ **การยืนยัน KI-02 ด้วยบัญชีพนักงาน** (ไม่ใช่ผู้ดูแล) และการตรวจการเข้าถึง/ฟอนต์ไทยที่ยังไม่เคยทดสอบ

## 2. ขอบเขต

**ทำ** (E1–E5 ด้านล่าง) · **ไม่ทำ (ห้าม):** แก้โค้ดผลิตภัณฑ์หรือไฟล์ใน `public/` · ตั้ง `DMS_DEV_AUTH=true` บนเซิร์ฟเวอร์ที่ทดสอบ (ต้องเข้าสู่ระบบด้วยรหัสผ่านจริงผ่านหน้าจอ) · ใช้ข้อมูลจริง · เปิดเซิร์ฟเวอร์ออกเครือข่าย (ใช้ `127.0.0.1` เท่านั้น) · นับผลของตนเองเป็นการตรวจอิสระของ UX (ผู้ใช้จริงต้องทำแยก)

## 3. การเตรียมสภาพแวดล้อม (ตรวจแล้วว่าใช้ได้)

```bash
node docs/testdata/seed-ui-env.js /path/to/onemanos-setbox 8080
```

สคริปต์เปิดเซิร์ฟเวอร์ **ไม่มี `DMS_DEV_AUTH`** ที่ `http://127.0.0.1:8080/` พร้อมบัญชี 3 บัญชีที่มีรหัสผ่านสุ่มพิมพ์ออกหน้าจอ และเอกสารเริ่มต้น 2 ฉบับ (ผูก/ไม่ผูกนิติบุคคล co-alpha):

| บัญชี | บทบาท | พฤติกรรมที่ตรวจแล้ว |
|---|---|---|
| `admin-user` | ผู้ดูแลระบบ | เข้าด้วยรหัสผ่านได้ ไม่ถูกบังคับเปลี่ยนรหัส |
| `alpha-staff` | พนักงาน co-alpha | เข้าได้และถูกบังคับเปลี่ยนรหัสครั้งแรก (`mustChangePassword=true`) |
| `beta-staff` | พนักงาน co-beta | เข้าได้ ไม่บังคับเปลี่ยน |

ตรวจแล้ว (ผ่านคำขอ HTTP): 3 บัญชีเข้าสู่ระบบด้วยรหัสผ่านได้ตามตาราง และ dev login ถูกปฏิเสธ (HTTP 422) · **ยังไม่ได้ทดสอบกับเบราว์เซอร์จริง** นั่นคืองานของใบงานนี้ · กด Ctrl+C เพื่อล้างข้อมูลชั่วคราว

## 4. ชิ้นงานและเกณฑ์รับงาน

### E1 · ยืนยัน KI-02 ในเบราว์เซอร์ (P0 ของใบงานนี้ — ทำก่อน)

1. เข้าด้วย `alpha-staff` (เปลี่ยนรหัสตามที่ถูกบังคับ) → เมนู "ระบบบริหารเอกสาร"
2. บันทึกว่ารายการ "เอกสารที่มีสิทธิ์เห็น" แสดงเอกสาร SEED-001 และ SEED-002 หรือไม่ (คาดว่าเห็น SEED-001 ไม่เห็น SEED-002)
3. สร้างเอกสารใหม่จากฟอร์ม แล้วดูว่า **เอกสารที่เพิ่งสร้างปรากฏในรายการหรือไม่** · ถ้าไม่ปรากฏ ผู้ใช้จะหาเอกสารตัวเองไม่เจอ ให้อธิบายว่าผู้ใช้เห็นอะไรบนหน้าจอหลังกดสร้าง (ข้อความสำเร็จ/หน้ารายละเอียดเปิดต่อหรือไม่)
4. เข้าด้วย `admin-user` เทียบผล · ทำซ้ำทั้งหมดบน `master` และบน branch PR #12
- **เกณฑ์รับ:** รายงานบอกชัดว่า KI-02 **ยืนยัน/ไม่ยืนยัน** ในแต่ละ branch พร้อมภาพหน้าจอก่อน-หลังการสร้างและข้อความที่ผู้ใช้เห็นจริง

### E2 · เดินตาม UC-T02, T04, T15 ผ่านหน้าจอ (P0–P1)

- UC-T15: เข้าสู่ระบบ → บังคับเปลี่ยนรหัส (ลองรหัสสั้น < 12 ตัว ต้องมีข้อความบอกชัด) → รหัสผิด 5 ครั้งแล้วบัญชีถูกล็อก (ข้อความที่ผู้ใช้เห็น)
- UC-T02: สร้าง → แก้เป็นเวอร์ชันถัดไปพร้อมเหตุผล → แนบ PDF/รูปภาพสังเคราะห์ → ดาวน์โหลด · ค่าขอบ: ชื่อภาษาไทยยาว 200 ตัว, ข้อความมีเครื่องหมายคำพูด/ขึ้นบรรทัดใหม่/แท็ก HTML (ต้องแสดงเป็นข้อความธรรมดา ไม่ถูกตีความเป็นแท็ก)
- UC-T04: เปิดเบราว์เซอร์สองโปรไฟล์ (co-alpha และ co-beta) ตรวจว่า co-beta ไม่เห็นข้อมูลของ co-alpha ทั้งในรายการ การค้นหา และเปิดด้วย URL/id ตรง ๆ
- **เกณฑ์รับ:** ทุกขั้นมีภาพหน้าจอและข้อความจริงที่เห็น · ข้อความผิดพลาดต้องบอกว่าทำอะไรต่อ (หลักข้อ 5–7 ใน designspec G.1)

### E3 · หน้าจออื่นและปุ่มต่าง ๆ (P1–P2)

เปิดทุกหน้า (`index`, `admin`, `business`, `executive`, `me`) ตรวจ: โหลดได้ไม่มี error ในคอนโซลเบราว์เซอร์ · เมนู "กล่องงานตรวจทาน/อนุมัติ" และ "กล่องงานลงนาม" · หน้าย้ายระบบ (บน PR #12 ต้องเห็นป้ายข้อมูลสาธิต) · **งานที่ต้องมีผู้ให้บริการลงนามต้องแสดงสถานะที่เข้าใจได้เมื่อยังไม่ตั้งค่า** · บันทึกรายการคอนโซลที่มี error/warning

### E4 · ความเข้ากันได้ของเบราว์เซอร์และฟอนต์ไทย (P1)

- เบราว์เซอร์: **Edge และ Chrome** รุ่นปัจจุบันบน Windows (ถ้าไม่มี Windows ให้รายงานตรง ๆ ว่าทดสอบบนระบบใด) · ตัวเลือก Firefox/Safari รอ Lead ตัดสิน
- หน้า Help (เฉพาะเมื่อ Lead นำ patch `docs/patches/setbox-offline-help.patch` ไปใช้แล้ว): ปุ่ม Help ทุกหน้า, แผนภาพ 13 ภาพอ่านครบ **ไม่ถูกตัดขอบข้อความ** บนฟอนต์ไทยของ Windows, ปิดเครือข่ายแล้วยังแสดงครบ, หน้าจอ 390px ไม่เลื่อนแนวนอน
- **เกณฑ์รับ:** ตารางเบราว์เซอร์ × หน้า มีผ่าน/ไม่ผ่านและภาพประกอบเฉพาะข้อที่ไม่ผ่าน

### E5 · การเข้าถึง (accessibility) เบื้องต้น (P2)

1. **คำนวณคอนทราสต์จริง** ของโทเค็นสีใน designspec G.2 (ตัวอักษรหลัก/รอง บนพื้นหลัง/แผง, ปุ่มสี teal/ทอง/แดง/ฟ้า) รายงานอัตราส่วนจริงเทียบเกณฑ์ ≥ 4.5:1 (ผมยังไม่ได้คำนวณ)
2. ใช้แป้นพิมพ์ล้วน: เข้าสู่ระบบ → สร้างเอกสาร → ปิดหน้าต่าง Help (Esc) ได้ครบ และเห็นเส้นโฟกัสทุกจุด
3. ซูม 200% และเปิดโหมดลดการเคลื่อนไหว (`prefers-reduced-motion`)
4. ตรวจด้วยเครื่องมือตรวจสอบอัตโนมัติ (เช่น axe หรือ Lighthouse) และรายงานเฉพาะข้อค้นพบที่ยืนยันด้วยมือแล้ว
- **เกณฑ์รับ:** ตารางข้อค้นพบพร้อมระดับ (S1–S4 ตาม TestSpec 10.2) · มาตรฐานเป้าหมาย (เช่น WCAG 2.1 AA) **Lead ต้องตัดสิน** รายงานผลเทียบ AA โดยไม่ประกาศว่า "สอดคล้อง" ถ้าไม่ได้ตรวจครบ

## 5. กฎการทำงาน (ตามโปรโตคอลของโครงการ)

1. เช็กกล่องจดหมายก่อนเริ่ม ก่อนส่งรายงาน และเมื่อติดขัด · ถ้าไม่มีสิทธิ์หรือเครื่องมือ (เช่น ไม่มี Windows) ส่ง `type: blocker` ระบุว่าใครปลดล็อกได้และระหว่างรอจะทำอะไรต่อ
2. รายงานแยก **"ทดสอบแล้วในเบราว์เซอร์ (ระบุเบราว์เซอร์/รุ่น/ระบบปฏิบัติการ)"** ออกจาก **"อ่านโค้ด/เดา"** และเขียน **"สิ่งที่ไม่ได้ทดสอบ"** เสมอ · **อย่ารายงานว่าผ่านถ้าไม่ได้รันจริง**
3. ภาพหน้าจอต้องไม่มีรหัสผ่าน โทเคน หรือข้อมูลจริง (ข้อมูลทดสอบสังเคราะห์เท่านั้น)
4. พบข้อบกพร่อง: ใช้แม่แบบ E.2 ใน TestSpec (ขั้นตอนทำซ้ำที่ใครทำตามก็ได้ผลเดิม) และเสนอระดับความรุนแรง ให้ Lead ยืนยัน
5. ห้ามแก้ไฟล์ใด ๆ ใน repo ผลิตภัณฑ์ · ส่งผลเป็นไฟล์ `work-orders/reports/BROWSER-VERIFY-<วันที่>.md` (+ โฟลเดอร์ภาพ) ผ่าน PR แบบ draft เฉพาะเอกสาร
