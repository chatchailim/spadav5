# ใบงานร่าง: ตัวตรวจ actor assertion แบบ KeySign (PKT-v1) ฝั่ง SPADA

- **รหัสเอกสาร: SPD-WO-008** (ยังไม่มีเลขใบงานจริง ผู้ดูแล monorepo กำหนดตอนนำเข้า) · ร่างโดย Claude ตามที่ Lead อนุมัติให้ร่าง (2026-10-01) · **ร่าง Lead ยังไม่ได้ตรวจ ยังไม่มอบผู้ทำ**
- **Lead ตอบ Q1–Q5 ของ ADR แล้ว (ตามข้อเสนอเริ่มต้น: challenge สุ่มโดย host, algorithm `ed25519-pkt-v1`, อายุ assertion ใช้ค่าเดิม, ใบงานตรวจ migration ของ counter, ต้องมีผู้ตรวจอิสระ) · ยังห้ามเริ่มจนผู้ดูแลนำเข้าและรับ [SPD-ADR-D05](../decisions/ADR-NEXT-keysign-actor-assertion-bridge-draft.md)** และผู้ดูแลนำเข้า ADR สู่ monorepo
- ผู้ทำ: ผู้ดูแลมอบ · ผู้ตรวจ: Cowork + ผู้ตรวจความปลอดภัยอิสระ · ผู้ตัดสิน: Lead
- ขนาด: **กลางถึงใหญ่** (identity path) · แยกจาก spike POO-WO-005 ทั้งหมด · branch แยกใน `spada-monorepo`
- เป้าหมาย: ปิดช่วง "actor assertion ผ่าน SPADA node" ของ A6-full

## ขอบเขต

ทำ: ตัวตรวจ algorithm `ed25519-pkt-v1` · สถานะ counter ต่ออุปกรณ์ · ตัวประกอบ assertion/ข้อความ PKT-v1 ฝั่ง host (ไลบรารี ไม่ใช่ UI) · ชุดทดสอบ
ไม่ทำ: ไม่แก้เฟิร์มแวร์ · ไม่แก้ `encodeSPADAActorAssertion` หรือพฤติกรรม algorithm เดิม · ไม่แก้ Fact v0/C2 · ไม่ขยาย `deviceAssurance` เกิน `NATIVE` · ไม่มีการเขียน/อนุมัติอัตโนมัติ

## เกณฑ์รับงาน

1. ชุดทดสอบเดิมของ `packages/auth` และ device manager ผ่านเท่าเดิม (พิสูจน์ว่า additive)
2. **ลายเซ็นที่ถูกต้อง** ผ่าน: ใช้เวกเตอร์ทดสอบที่สร้างด้วยตัวจำลอง (`sim`) และทะเบียนแยก ไม่ใช้ทะเบียนจริง
3. **แก้ข้อมูลแล้วถูกปฏิเสธ** ทีละฟิลด์: actor, device, request, route, payload, issuedAt, nonce, algorithm (แต่ละฟิลด์มีเหตุผลปฏิเสธที่ระบุได้)
4. **ใช้ซ้ำถูกปฏิเสธ:** nonce เดิม · counter เท่าเดิมหรือต่ำกว่า · สองคำขอพร้อมกันด้วย counter เดียวกัน → รับได้อย่างมากหนึ่ง (บังคับจังหวะด้วยเทสต์ ไม่ใช่ทดลองซ้ำ)
5. **หมดอายุ** และ **นาฬิกาเลื่อน** ถูกปฏิเสธตามค่าที่ตั้ง
6. **เพิกถอนกุญแจ/อุปกรณ์:** assertion ใหม่หลังเพิกถอนถูกปฏิเสธทันที ไม่ cache
7. ลายเซ็นจากอุปกรณ์อื่น · algorithm ไม่ตรง device record · ฟิลด์ `pkt` ขาด/ผิดรูป/ความยาวผิด → ปฏิเสธแบบ fail-closed ไม่ถอยไปทางเดิม
8. **ข้อมูลลายเซ็นไม่รั่ว:** บันทึก audit ไม่เก็บ private key; ไม่ใส่ DID/token ID/uid จริงในเทสต์หรือรายงาน
9. **หลักฐานบนอุปกรณ์จริง (ขั้นสุดท้าย):** ลายเซ็นจริงหนึ่งรายการผ่านตัวตรวจใหม่ ผู้ใช้กดปุ่มเอง, counter ของอุปกรณ์เพิ่มก่อน/หลัง, ใช้ทะเบียนทดสอบ ป้าย "หน่วยจริง กุญแจจริง ทะเบียนทดสอบ บริบททดสอบ" เก็บใน repo private เท่านั้น · **การใช้หน่วยเดิมหรือบอร์ดตัวที่สองต้องให้ Lead ระบุก่อนเริ่มขั้นนี้**
10. ตัวตรวจผ่านการตรวจความปลอดภัยโดยผู้ตรวจอิสระก่อน merge
11. รายงานแยก "ลองแล้ว / อ่านแล้ว / ไม่ทราบ" พร้อมข้อจำกัด

## ข้อกำหนดสภาพแวดล้อม

ข้อ 1–8 รันบนข้อมูลสังเคราะห์และตัวจำลองได้ ไม่ต้องใช้อุปกรณ์ · ข้อ 9 ใช้ตามที่ Lead ระบุในใบงานนี้: หน่วย `[●ยังไม่ตัดสิน]` · ผู้กดปุ่ม `[●]` · ตั้ง `SPADA_PKT_REGISTRY` และ `SPADA_PKT_SIM_STATE` ไปยังโฟลเดอร์แยกเสมอ (ค่าเริ่มต้นของ `pktctl` คือทะเบียนจริง)

## ความเสี่ยง

เป็นการแตะ identity service จึงต้องไม่ผสมกับงานอื่น · ถ้าพบว่ากุญแจ KeySign กับ `signingPublicKey` ใน device record ไม่เข้ากัน ให้หยุดและรายงาน ไม่ปรับ ADR เอง
