# แคตตาล็อกแอป OnDemand สำหรับเมืองอัจฉริยะหาดใหญ่ (เทศบาล + ร้านค้า) บน OneManOS SetBox

**รหัสเอกสาร:** SPD-PLN-003 · **สถานะ:** ร่างเพื่อทบทวน v0.1 (ไอเดียและข้อกำหนดเบื้องต้น ยังไม่ใช่แอปที่สร้างแล้ว ยังไม่ผ่านที่ปรึกษากฎหมาย) · **วันที่:** 2026-10-02
**ต่อจาก:** SPD-PLN-001 (แผนนำร่องหาดใหญ่), SPD-PLN-002 (ข้อเสนอเทศบาล), SPD-MED-008 (คู่มือ Harness/App Catalog)
**อ้างอิง:** `onemanos-setbox/app-catalog.js` + `APP-CATALOG-REGISTRY-TH.md` (ตามที่ SPD-MED-008 ตรวจไว้), ADR 0014, 0016, 0017, 0018, 0022, 0026 (**Proposed**), PROP-0003, doc 263 (tier A/B/C)

> **ข้อควรรู้:** เอกสารนี้เป็น "แคตตาล็อกไอเดียพร้อมข้อกำหนดเบื้องต้น" ผู้ร่างไม่ได้เปิดโค้ดใน `services/`, `packages/`, `modules/` ใหม่ จึงไม่ยืนยันว่าสัญญา (contract) หรือบริการที่อ้างถึงมีครบแล้ว ชื่อสัญญาเป็นชื่อเสนอเพื่อออกแบบ ไม่ใช่ชื่อในโค้ด App Manifest 3 ชนิดและการแบ่งรายได้ยังเป็นข้อเสนอ (ADR 0026 Proposed) ช่อง **[●]** คือสิ่งที่ต้องกรอกหรือยืนยัน ไม่มีตัวเลขงบหรือผลตอบแทนในเอกสารนี้

## 1. วิธีใช้แคตตาล็อก

1. เลือกแอปจากรายการ (ข้อ 4–6) ด้วยเกณฑ์ในข้อ 3
2. ใช้บัตรแอปเป็นข้อมูลตั้งต้นของขั้น **C (ลงทะเบียน)** และ **I (ยื่นสัญญา)** ในวงจร CIDER
3. ผ่านประตูมนุษย์ 2 บานตามข้อ 2 ทุกแอป ไม่มีข้อยกเว้น
4. แอปที่มีข้อมูลอ่อนไหวต้องผ่านเช็กลิสต์ข้อ 7 ก่อนเปิดใช้จริง

## 2. กฎตายตัวจากวงจรชีวิตแอป (CIDER)

อ้างตาม SPD-MED-008 §3.2 ซึ่งบันทึกว่ามีโค้ดจริงใน `app-catalog.js`

```
C ลงทะเบียน ─▶ I ยื่นสัญญา ─▶ 🔒 คนอนุมัติสัญญา ─▶ D สร้าง ─▶ E ตรวจ ─▶ 🔒 คนยืนยันผล ─▶ R ใช้จริง
```

| กฎ | ผลต่อแคตตาล็อก |
|---|---|
| `register` ต้องมีชื่อคนรับผิดชอบ (`ownerName`) และเหตุผลที่ต้องมีแอป (`purpose`) | ทุกบัตรแอปมีช่อง "เจ้าของแอป" และ "ทำไมต้องมี" |
| `submitVersion` ต้องมี `integration.directStorageAccess = false` และประกาศ `producedContracts`/`consumedContracts` อย่างน้อยหนึ่ง | แอปเข้าคลังผ่าน API/สัญญาเท่านั้น ห้ามอ่านฐานข้อมูลตรง |
| `approveVersion` และ `activateVersion` ต้องใช้ชื่อ **คน** ชื่อบัญชี agent ถูกปฏิเสธ | Human Gate 2 บาน: อนุมัติสัญญา และยืนยันผลทดสอบ |
| `activateVersion` ต้องแนบผลทดสอบสัญญาครบ + ผลตรวจต้านไซโล และต้องผูกบัญชี SERVICE (`bindService`) | ทุกแอปมีผลทดสอบและบัญชี SERVICE ของตนเอง |
| บัญชี SERVICE ของแอปที่ไม่ลงทะเบียนหรือยังไม่ live ถูกปฏิเสธ (`APP_NOT_REGISTERED`, `APP_NOT_LIVE`) | แอปที่ยังไม่ผ่านวงจรเรียกคลังไม่ได้ |
| เปลี่ยนสัญญา = กลับเข้าขั้น I | แก้ฟีเจอร์ที่กระทบข้อมูลต้องผ่านการอนุมัติใหม่ |
| `retire` ต้องมีคนตัดสินและเหตุผล | ทุกแอปมีแผนเลิกใช้ |

**ข้อจำกัดที่ต้องไม่ลืม:** ด่านเรียกคลังกัน "แอป" ไม่กัน "คนที่เอาบัญชีตัวเองให้แอปใช้" ตามที่เอกสารทะเบียนระบุไว้เอง

## 3. เกณฑ์คัดเลือกและระดับความเสี่ยง

**ระดับความเสี่ยงของแอป (เสนอ ต้องให้ Lead ยืนยัน):** 
- **L (ต่ำ):** ไม่มีข้อมูลอ่อนไหว ไม่มีเงิน ไม่มีผลต่อชีวิต
- **M (กลาง):** ข้อมูลส่วนบุคคลหรือเงิน ต้องมี Human Gate ตอนทำรายการ
- **H (สูง):** ข้อมูลอ่อนไหว (สุขภาพ พิกัดบ้าน) หรือกระทบความปลอดภัย ต้องผ่านข้อ 7 ครบ

**Tier ของขั้นงานภายในแอป (ตาม doc 263):** A = MyAI/ระบบทำเองได้, B = ต้องคนอนุมัติ, C = ห้ามทำเองอัตโนมัติ
(ไม่ใช้ปนกับ L/M/H ซึ่งเป็นระดับของ "แอป" ทั้งตัว)

**ลำดับความสำคัญ (ให้ทีมกรอกคะแนน 1–5):** ผลกระทบต่อประชาชน · ความเสี่ยงต่ำ · ใช้ข้อมูลน้อย · ทำได้ใน ≤ 5 เดือน · ไม่ต้องพึ่งระบบรัฐ

## 5. แอปของหน่วยงานเทศบาล

### M1 แจ้งปัญหาเมือง (ร้องเรียน)
- **เจ้าของแอป:** [●] (เทศบาล) · **ทำไมต้องมี:** ประชาชนแจ้งเรื่องแล้วไม่รู้สถานะ ข้อมูลกระจัดกระจาย
- **Journey:** เลือกหมวด → ถ่ายรูป/ระบุจุด (พิกัดเฉพาะจุดที่แจ้ง ไม่ใช่พิกัดบ้าน) → เลือกว่าจะเปิดตัวตนหรือไม่ → ส่ง → ติดตามสถานะ → ปิดงานพร้อมรูปหลังแก้ไข
- **ข้อมูล/consent:** ตัวตนเป็นทางเลือก; รูปและตำแหน่งเฉพาะเรื่อง; เก็บเท่าที่จำเป็น [●] วัน
- **สัญญา (ชื่อเสนอ):** ผลิต `CitizenReport.v1`, `ReportStatus.v1` · ใช้ `ConsentGrant.v1`
- **ขั้นงานและ Tier:** รับเรื่อง/จัดหมวด (A) · มอบหมายผู้รับผิดชอบ (B) · ตอบกลับประชาชน (B) · ปิดเรื่อง (B) · เผยแพร่ภาพ/ชื่อผู้แจ้ง (C ห้ามอัตโนมัติ)
- **ความเสี่ยง:** L–M ภาพอาจติดคนหรือป้ายทะเบียน ต้องมีขั้นเบลอ/ตรวจก่อนเผยแพร่
- **KPI:** เวลาตอบรับเฉลี่ย, สัดส่วนเรื่องที่ปิด, ความพึงพอใจ (วัดฐานก่อนเริ่ม)
- **ต้องพึ่ง:** ผู้ประสานงานเทศบาล, กระบวนการภายในที่มีอยู่

### M2 นัดหมายและคิวบริการ
- **Journey:** เลือกบริการ → เลือกวัน/เวลา → รับยืนยันและแจ้งเตือน → เลื่อน/ยกเลิก → เช็กอินหน้าสำนักงาน
- **ข้อมูล:** ชื่อ ช่องทางติดต่อ (ขั้นต่ำ) · **ความเสี่ยง:** L
- **Tier:** จองและเตือน (A) · เปลี่ยนกติกาคิว (B) · ยกเลิกนัดแทนประชาชนโดยเจ้าหน้าที่ (B)
- **KPI:** อัตราไม่มาตามนัด, เวลารอเฉลี่ย

### M3 แจ้งข่าวตามความสนใจ
- **Journey:** เลือกหัวข้อ (ประกาศงานเทศบาล, ปิดถนน, ตลาดนัด) → รับข่าวตามที่เลือก → ปรับ/ยกเลิก
- **ข้อมูล:** ความสนใจเท่านั้น ไม่เก็บพิกัด · **ความเสี่ยง:** L
- **หมายเหตุ:** ไม่ใช่ช่องทางเตือนภัยทางการ

### M4 คำขอเอกสารง่ายๆ (หนังสือรับรอง/ใบอนุญาตบางประเภท)
- **Journey:** เลือกประเภท → ให้ consent แบ่งเอกสารที่เคยยืนยันไว้ (รายเรื่อง) → ส่งคำขอ → เจ้าหน้าที่ตรวจ → รับผล
- **ข้อมูล:** เอกสารตัวตนและที่อยู่ · **ความเสี่ยง:** M
- **Tier:** ตรวจครบถ้วนเบื้องต้น (A) · อนุมัติ/ออกเอกสาร (C ให้คนของเทศบาลตัดสินเสมอ) · แจ้งผล (A)
- **ต้องพึ่ง:** กระบวนการและกฎของเทศบาลจริง, การเชื่อม Digital ID (ดู U4 ใน SPD-PLN-001) เหมาะระยะ 2

### M5 ทะเบียนอาสาสมัครและศูนย์พักพิง
- **Journey:** ลงทะเบียนทักษะและช่วงว่าง → เทศบาลประกาศความต้องการ → อาสาสมัครตอบรับ → ลงเวลา
- **ข้อมูล:** ทักษะ ช่วงเวลา ช่องทางติดต่อ · **ความเสี่ยง:** M
- **หมายเหตุ:** จับคู่เป็นข้อเสนอ ไม่บังคับ (B)

### M6 รายงานคุณภาพเมืองแบบรวม
- **Journey:** แดชบอร์ดสรุปเรื่องร้องเรียน นัดหมาย ความพึงพอใจ แบบข้อมูลรวม
- **ข้อมูล:** ข้อมูลรวมที่ไม่ระบุตัว · **ความเสี่ยง:** L
- **ข้อกำหนด:** ไม่แสดงกลุ่มที่เล็กจนระบุตัวได้ (เช่น น้อยกว่า [●] ราย)

### M7 ทะเบียนความช่วยเหลือยามภัยพิบัติ (สมัครใจ) — **เตรียมแบบร่าง ไม่เปิดใช้จนผ่านข้อ 7**
- **เจ้าของแอป:** [●] ร่วมกับหน่วยงานที่มีอำนาจ · **ทำไมต้องมี:** ข้อมูลช่วยเหลือผู้ที่ต้องการความช่วยเหลือเป็นพิเศษกระจัดกระจายตามบริบทพื้นที่ (ต้องยืนยันจริง)
- **Journey:** ประชาชนสมัครใจลงทะเบียน → ให้ consent เปิดข้อมูลเฉพาะช่วงเหตุที่หน่วยงานมีอำนาจประกาศ → เหตุการณ์ → ผู้ประสานงานที่ผ่านการรับรองเห็นรายบุคคลตามขอบเขต พร้อมบันทึกการเข้าถึง → จบเหตุ → การเข้าถึงปิดอัตโนมัติ
- **ข้อมูล:** พิกัดบ้าน สุขภาพ/ความต้องการพิเศษ ผู้ติดต่อฉุกเฉิน · **ความเสี่ยง:** H
- **Tier:** ลงทะเบียนและเตือนผู้ใช้ให้อัปเดตข้อมูล (A) · เปิดข้อมูลรายบุคคลแก่ผู้ประสานงาน (B ต้องคนอนุมัติ) · ตัดสินว่าใครได้รับความช่วยเหลือ (C ห้ามอัตโนมัติ)
- **ข้อกำหนดเฉพาะ:**
  1. ไม่ใช่ระบบเตือนภัยทางการ และไม่รับประกันการช่วยเหลือ ต้องแสดงข้อความนี้ในแอปทุกหน้าจอสำคัญ
  2. ผู้ที่ไม่ตอบกลับหรือไม่มีสัญญาณห้ามตีความว่าปลอดภัย
  3. ออกแบบโหมดออฟไลน์/mesh (PROP-0009 ยังเป็นข้อเสนอ)
  4. ต้องผ่าน Gate 2 ของ SPD-PLN-001

## 6. แอปของร้านค้าและผู้ประกอบการ

### S1 ส่งเอกสารบัญชีให้สำนักงานบัญชี
- **ผู้ใช้:** ร้านค้า SME และสำนักงานบัญชี · **ทำไมต้องมี:** รวบรวมใบเสร็จ/ใบกำกับภาษีด้วยมือ ผิดพลาดและล่าช้า
- **Journey:** ร้านค้าถ่ายหรือส่งเอกสาร → MyAI จัดหมวด → ร้านค้าตรวจและให้ consent แบ่งเอกสารรอบเดือนแก่สำนักงานบัญชี → สำนักงานบัญชีตรวจ → ปิดงวดและภาษี → ร้านค้ารับรายงาน
- **ข้อมูล:** เอกสารการเงินของธุรกิจ · **ความเสี่ยง:** M
- **Tier:** อ่านและจัดหมวด (A) · ส่งเอกสารให้สำนักงานบัญชี (B ร้านค้าอนุมัติ) · ปิดงวดและยื่นภาษี (C ห้ามอัตโนมัติ)
- **สัญญา (ชื่อเสนอ):** ผลิต `AccountingDocBundle.v1` · ใช้ `ConsentGrant.v1`
- **ต่อยอดจาก:** โมดูลขาย ซื้อ บัญชี ภาษี ปิดงวด กระทบยอดธนาคาร ที่ SPD-MED-008 ระบุว่ามีโค้ดตาม APP-CATALOG (ยังไม่เคยส่งมอบลูกค้านอกกิจการผู้พัฒนา)
- **KPI:** เวลารวมต่อรอบ, อัตราเอกสารที่ต้องแก้, ความพึงพอใจ

### S2 สมาชิกและสะสมแต้มร้านค้า
- **Journey:** ลูกค้าเลือกว่าจะให้ร้านเห็นอะไร (ชื่อเล่น ช่องทางติดต่อ ประวัติซื้อ) → สะสมแต้ม → รับสิทธิ์ → ถอนได้ทุกเมื่อ
- **ความเสี่ยง:** L–M · **Tier:** นับแต้ม (A) · แจกรางวัลมูลค่าสูง (B) · นำข้อมูลลูกค้าไปใช้โฆษณาแทนร้านอื่น (C ห้าม)

### S3 จองคิว/จองโต๊ะ/นัดบริการ (ร้านอาหาร คลินิกความงาม อู่ซ่อมรถ)
- **Journey:** เลือกบริการ-เวลา → ร้านเห็นเฉพาะข้อมูลที่จำเป็น → เตือน → เช็กอิน
- **ความเสี่ยง:** L · **หมายเหตุ:** คลินิกที่เกี่ยวกับสุขภาพเข้าข้อมูลอ่อนไหว ใช้ข้อกำหนดข้อ 7

### S4 ใบรับประกันและประวัติซ่อมดิจิทัล
- **Journey:** ร้านออกใบรับประกันให้เจ้าของสินค้า → เจ้าของเก็บในแฟ้มส่วนตัว → ส่งต่อร้านเมื่อเคลม → ร้านบันทึกประวัติซ่อม
- **ความเสี่ยง:** L–M · **ข้อดี:** เจ้าของข้อมูลมีสำเนาของตนเอง

### S5 สั่งของและส่งของในย่าน
- **Journey:** ลูกค้าสั่ง → ร้านรับออเดอร์ → ผู้ส่งชั่วคราวเห็นพิกัดเมื่อรับงานเท่านั้น → ส่งสำเร็จ → การเข้าถึงพิกัดหมดอายุ
- **ความเสี่ยง:** M · **Tier:** จับคู่ผู้ส่ง (A) · ชำระเงิน/คืนเงิน (B หรือ C ตามกติกา) · **ต้องพึ่ง:** ผู้ให้บริการชำระเงิน ซึ่งผู้ร่างไม่ได้ตรวจ

### S6 บัญชีรายรับ-รายจ่ายของ SME
- **Journey:** บันทึกรายการ → MyAI จัดหมวดและสรุป → เจ้าของอนุมัติก่อนส่งสำนักงานบัญชี
- **ความเสี่ยง:** M · **หมายเหตุ:** ทับซ้อนกับ S1 ควรสร้างเป็นโมดูลร่วม

### S7 ทะเบียนผู้ค้าตลาดและตลาดนัดชุมชน
- **Journey:** ผู้ค้าลงทะเบียนแผง → ตรวจสิทธิ์โดยตลาด/เทศบาล → ชำระค่าที่ (ถ้ามี) → เช็กอินวันขาย
- **ความเสี่ยง:** L–M · **ต้องพึ่ง:** กติกาตลาดและเทศบาล

### S8 ใบสมัครงานและประวัติพนักงานชั่วคราว
- **Journey:** ผู้สมัครเลือกแบ่งประวัติเป็นส่วนๆ → ร้านเห็นเฉพาะส่วนที่อนุญาต → หมดอายุอัตโนมัติ
- **ความเสี่ยง:** M

## 9. เกณฑ์ขึ้นแอปสโตร์ (Node App / SetBox App / Hybrid)

| เรื่อง | สถานะ |
|---|---|
| App Manifest 3 ชนิด, `APP_REVIEWED`, `APP_INSTALLED`, metering ต่อแอป, แบ่งรายได้, อุทธรณ์ | **ข้อเสนอ (ADR 0026 Proposed)** ยังไม่พบโค้ดครบ ห้ามสัญญาผู้พัฒนาภายนอกว่าใช้ได้ |
| ทะเบียนแอปและวงจร CIDER | มีโค้ดตามที่ SPD-MED-008 บันทึก ให้ตรวจ ณ วันใช้จริงอีกครั้ง |
| ร้านค้าที่สร้างแอปเอง (Journey → แอป) | แนวคิดและภาพจำลอง (SPD-MED-008) ไม่ใช่ผลิตภัณฑ์ที่พร้อมใช้ |
| กฎของ App Store ภายนอก (Apple/Google) | **ผู้ร่างยังไม่ได้ตรวจเงื่อนไข** ต้องตรวจก่อนเสนอให้ประชาชนติดตั้งผ่านร้านค้าภายนอก ทางเลือก: Progressive Web App หรือกระจายผ่านช่องทางของโครงการเอง |

เกณฑ์รับแอปเข้าแคตตาล็อก (เสนอ):
1. มีเจ้าของแอปที่เป็นคน และเหตุผลที่ต้องมี
2. สัญญาครบและผ่านประตูอนุมัติ
3. ผ่านผลทดสอบสัญญาและต้านไซโล
4. มีประกาศความเป็นส่วนตัวภาษาไทย
5. มีช่องทางร้องเรียนและถอน consent
6. มี KPI และจุดวัดฐานก่อนเริ่ม

## 11. คำถามที่ต้องตัดสินก่อนสร้างจริง

1. ผู้ให้บริการแอปจริงคือใคร: เทศบาล, ทีมโครงการ หรือผู้พัฒนาท้องถิ่น และใครเป็น data controller ของแต่ละแอป (ต้องถามที่ปรึกษากฎหมาย)
2. ช่องทางกระจายแอป: App Store ภายนอก, PWA หรือช่องทางของโครงการเอง
3. สถานะ ADR 0026 (App Manifest, การแบ่งรายได้) ตัดสินเมื่อใด
4. ชื่อสัญญาที่เสนอในเอกสารนี้ตรงกับของที่มีในโค้ดหรือไม่ (ให้ทีมวิศวกรรมตรวจ)
5. เจ้าหน้าที่เทศบาลคนใดเป็นผู้ประสานและเจ้าของ M1/M2
