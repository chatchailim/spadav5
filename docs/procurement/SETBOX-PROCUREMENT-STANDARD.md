# มาตรฐานการจัดซื้อ OneManOS SetBox (ร่าง v0.1)

> สถานะ: **Lead อนุมัติเป็นมาตรฐาน 2026-09-29** ([APPROVAL-LOG](../decisions/APPROVAL-LOG-2026-09-29.md)) มีผลกับการซื้อหลังได้รับเงินระดมทุน · ยังต้องกรอกชื่อบทบาทและตัวเลข ณ วันซื้อ · ก่อนซื้อจริงให้ทบทวนหนึ่งรอบ (ข้อ 13) · วันที่ 2026-09-29
> ต่อยอดจาก ADR 0017 (การติดตั้ง SetBox), ADR 0020 (รับรองรุ่นฮาร์ดแวร์ ด้วย EK certificate), doc 342 (สเปก `SB-S1`/`SB-D2`), doc 344 (ทะเบียนฮาร์ดแวร์), doc 347 (KeySign provisioning) และ ROADMAP ของ `onemanos-setbox`
> **ตัวเลขและเงื่อนไขเชิงพาณิชย์ทั้งหมด (X) กำหนด ณ วันซื้อจริง ตามราคาและสภาพตลาดในวันนั้น หลังการระดมทุน** ไม่ใช่วันนี้ · ใช้ [PURCHASE-TIME-DECISION-SHEET](PURCHASE-TIME-DECISION-SHEET.md) เป็นแบบกรอกและอนุมัติ ณ วันซื้อ · ผมไม่ได้ให้คำแนะนำด้านกฎหมายจัดซื้อ ภาษี หรือศุลกากร ต้องตรวจกับผู้เชี่ยวชาญ

## 1. วัตถุประสงค์และหลักการ

กฎนี้ทำให้ทุกเครื่อง SetBox ที่ซื้อมา **เหมือนกัน ตรวจสอบได้ และไม่พลาดซ้ำ** ตั้งแต่เลือกรุ่นจนส่งมอบลูกค้า

| # | หลัก | ที่มา |
|---|---|---|
| P1 | **ไม่ผ่านการรับรอง ไม่ออกใบสั่งซื้อล็อต** | ADR 0020 §4 |
| P2 | **วัดจากเครื่องจริง ไม่เชื่อเอกสารผู้ขายอย่างเดียว** เอกสารผู้ขายใช้ตัดสินใจก่อนซื้อเท่านั้น | ADR 0020 §3 |
| P3 | **ตัวอย่างก่อนล็อต** ซื้อ 1–2 เครื่องรับรองรุ่นก่อน | ข้อเสนอนี้ |
| P4 | **หนึ่งรุ่น + BIOS/firmware หนึ่งเวอร์ชัน = หนึ่งรายการในทะเบียน** เปลี่ยนเวอร์ชัน = รับรองใหม่ | doc 344 §4 |
| P5 | **แยกหน้าที่**: คนขอซื้อ คนรับรอง คนอนุมัติจ่าย ต้องไม่ใช่คนเดียวกันในรายการเดียวกัน | หลักควบคุมภายใน |
| P6 | **ทะเบียนเป็น append-only** ถอนรุ่น = เพิ่มรายการใหม่ ห้ามลบ | doc 344 §4 |
| P7 | **ล้มเหลวแบบปิด (fail closed)** ข้อมูลไม่ครบ = ไม่ผ่าน ไม่ใช่ "น่าจะผ่าน" | ADR 0015 §4 |
| P8 | **ไม่มีข้อยกเว้นแบบปากเปล่า** ข้อยกเว้นต้องบันทึกในทะเบียนข้อยกเว้นพร้อมผู้อนุมัติและวันหมดอายุ | ข้อเสนอนี้ |

## 4. ขั้นตอน (ด่านที่ต้องผ่านตามลำดับ)

```
D0 กำหนดสเปกขั้นต่ำ
 → D1 ส่ง RFQ + คำถามบังคับ (ลายลักษณ์อักษร)
 → D2 ประเมินคำตอบ (ผ่าน/ไม่ผ่านตามเกณฑ์ข้อ 5)
 → D3 ซื้อตัวอย่าง 1–2 เครื่อง
 → D4 วัดและรับรองรุ่นจากเครื่องจริง → Steward บันทึกทะเบียน (APPLIANCE-CANDIDATE / NATIVE-ELIGIBLE / REJECTED)
 → D5 ออก PO ล็อต พร้อมเงื่อนไขความสอดคล้องกับตัวอย่าง
 → D6 ตรวจรับของ (ทุกเครื่อง + สุ่มวัดซ้ำ)
 → D7 provision + ติดตั้ง + ตรวจก่อนส่งมอบ H1–H7
 → D8 ดูแลหลังขาย (อัปเดต BIOS = รับรองใหม่, เพิกถอนเมื่อจำเป็น)
```

### D0 สเปกขั้นต่ำ (ต้องผ่านทุกข้อ ก่อนขอราคา)

- TPM 2.0 บนฮาร์ดแวร์จริง (dTPM/fTPM/iTPM ยอมรับได้เชิงเกณฑ์ขั้นต่ำ **vTPM ห้าม**)
- Secure Boot เปิดได้และตั้งเป็น user mode ได้
- ปิดช่องดีบัก (DCI/JTAG) ถาวรได้
- PCR bank SHA-256 ครบ และอ่าน event log ได้
- ตัวแปรที่ผู้ขายต้องระบุ: รุ่น/SKU, เวอร์ชัน BIOS ที่จัดส่ง, ผู้ผลิตและ firmware ของ TPM
- **ที่ควรมี (ไม่บังคับ)**: TPM ชนิด dTPM ที่มี EK certificate ที่ chain ถึง vendor root · จะเปิดทาง `APPLIANCE` ในอนาคต แต่ตอนนี้เพดานระบบยังเป็น `NATIVE` ตาม ADR 0017 §7.5

### D1 คำถามบังคับใน RFQ

ใช้ 6 ข้อของ doc 344 §5 และข้อเพิ่มใน [RFQ-VENDOR-LETTER-TH](RFQ-VENDOR-LETTER-TH.md) **คำตอบต้องเป็นลายลักษณ์อักษรเท่านั้น** (อีเมลหรือหนังสือ ไม่รับโทรศัพท์หรือแชต) และเก็บไว้เป็นหลักฐานเข้าแฟ้มจัดซื้อ

### D2 เกณฑ์ประเมินคำตอบ

| ผล | เงื่อนไข | การดำเนินการ |
|---|---|---|
| ❌ **ตกทันที** | ไม่ตอบข้อใดข้อหนึ่งเป็นลายลักษณ์อักษร · เป็น vTPM · ปิดดีบักไม่ได้ · ไม่ยืนยัน Secure Boot user mode · ปฏิเสธไม่ระบุเวอร์ชัน BIOS | ไม่ซื้อ |
| 🟡 **ผ่านแบบมีเงื่อนไข** | เป็น fTPM และไม่ยืนยัน EK certificate | ซื้อตัวอย่างเพื่อวัดเอง ห้ามอ้าง `APPLIANCE` |
| 🟢 **ผ่าน** | ตอบครบ และยืนยัน EK certificate พร้อมรากที่ chain | ซื้อตัวอย่างเพื่อวัดยืนยัน |

### D3–D4 ตัวอย่างและการรับรอง

- ซื้อตัวอย่าง 1–2 เครื่อง จากล็อตหรือช่องทางเดียวกับที่จะใช้สั่งจริง
- วัด 10 ข้อตาม doc 344 §3 ด้วยเครื่องมือของทีม (สคริปต์รับรองยังไม่มี ต้องมี WO) บันทึก hash ของ evidence log
- Steward เท่านั้นที่เพิ่มรายการ ห้ามรับรองจากเอกสารผู้ขาย
- ผลไม่ตรงกับคำตอบผู้ขาย = บันทึกความคลาดเคลื่อน และประเมินผู้ขายใหม่

### D5 เงื่อนไขขั้นต่ำในใบสั่งซื้อล็อต

1. ทุกเครื่องในล็อตต้องมีรุ่น, BIOS/firmware, ผู้ผลิตและ firmware ของ TPM **เหมือนตัวอย่างที่ผ่านการรับรอง**
2. ผู้ขายต้องแจ้งล่วงหน้าเป็นลายลักษณ์อักษรหากจะเปลี่ยนชิ้นส่วนหรือ firmware (X วัน)
3. สิทธิ์ปฏิเสธรับและคืนเงินหากตรวจรับพบไม่ตรงตัวอย่าง
4. ห้ามส่งของที่ผ่านการใช้งานหรือ refurbished เว้นแต่ระบุไว้และผ่านการรับรองเป็นรายเครื่อง
5. การรับประกัน (X ปี) เงื่อนไขซ่อม/เปลี่ยน และข้อกำหนดกรณีต้องเปลี่ยนเมนบอร์ดหรือ TPM (ต้องรับรองใหม่ทันที)
6. ที่มาของสินค้า (ช่องทางนำเข้า/ตัวแทนจำหน่ายที่ได้รับอนุญาต)
7. ไม่มีการติดตั้งซอฟต์แวร์หรือบัญชีของผู้ขายที่ลบไม่ได้

### D6 ตรวจรับของ

| รายการตรวจ | วิธี | เกณฑ์ |
|---|---|---|
| ซีลและสภาพภายนอก | ตรวจด้วยตา ถ่ายรูป | ไม่มีร่องรอยเปิด/เปลี่ยน |
| Serial และรุ่น | เทียบกับใบส่งของและ PO | ตรง 100% |
| BIOS/TPM firmware | อ่านจากเครื่อง | เท่ากับตัวอย่างที่รับรอง **ทุกเครื่อง** |
| สุ่มวัดซ้ำ 10 ข้อ | ตามข้อ D4 | จำนวนสุ่ม X% ของล็อต (อย่างน้อย 1 เครื่อง) · พบความคลาดเคลื่อน 1 เครื่อง = ตรวจทั้งล็อต |
| ไม่มีซอฟต์แวร์/บัญชีแฝง | ติดตั้งระบบใหม่จาก image ที่เซ็นแล้ว | เครื่องต้องล้างและติดตั้งใหม่ก่อนใช้ |

เครื่องที่ไม่ผ่าน = แยกกัก (quarantine) ไม่ติดตั้ง และเปิดเรื่องกับผู้ขาย

### D7 provision และส่งมอบ

- ใช้ `ProvisioningClaim` (ต้องออนไลน์ ตาม ADR 0017 §7.4) และติดตั้งด้วยชุดที่เซ็นแล้ว
- **ห้ามแจกรหัสติดตั้งล่วงหน้าตอนผลิตหรือพิมพ์ติดกล่อง** (ADR 0017 §7.4)
- ก่อนส่งมอบรันตรวจ H1–H7 ของ SetBox (`setup/onemanos-handover.js`) เครื่องต้องไม่มีข้อมูลหรือโทเคนของลูกค้ารายก่อนและบัญชีทางลัดของผู้พัฒนา
- **ผลตรวจความพร้อม SetBox 2026-09-06 ยังเป็น CONDITIONAL** ให้ปิด P1 ทั้ง 4 ข้อก่อนส่งมอบลูกค้าจริง

### D8 หลังขาย

- อัปเดต BIOS/firmware ที่เปลี่ยนสถานะ TPM = **รับรองใหม่เป็นรายการใหม่** (doc 344 §4)
- ถอนรุ่นออกจากทะเบียน = เพิ่มรายการใหม่ที่อ้างอิงของเดิมพร้อมเหตุผล และวางแผนเปลี่ยนเครื่องที่ติดตั้งแล้ว ไม่ใช่ปิดตาต่อ
- เพิกถอน host: ผู้มีอำนาจคือ Approver ของ WorkSpace เจ้าของกล่อง (ADR 0017 §7.3) อุปกรณ์ของทุกคนบนกล่องตกชั้นทันที
- กล่องเปลี่ยนมือ: เจ้าของเดิมเพิกถอน host ก่อนส่งมอบ เจ้าของใหม่ provision ใหม่ทั้งกล่อง

## 5. ธงแดง (Red Flags): พบข้อใดให้หยุดและรายงาน Steward

- ผู้ขายลังเลหรือปฏิเสธตอบเป็นลายลักษณ์อักษร หรือตอบเลี่ยงคำถามเรื่อง EK certificate
- ราคาต่ำผิดปกติ หรือสินค้า "มือสองเหมือนใหม่" ไม่ระบุที่มา
- BIOS ที่จัดส่งไม่ตรงกับตัวอย่าง หรือผู้ขายอ้างว่า "อัปเดตให้ทีหลัง"
- ซีลถูกเปิด ซอฟต์แวร์แปลกปลอมมาในเครื่อง หรือมีบัญชีผู้ดูแลของผู้ขาย
- แรงกดดันให้ข้ามการรับรองเพราะ "เร่งส่งมอบ" หรือ "ลูกค้ามีเครื่องอยู่แล้ว" (ADR 0020 ห้ามไม่มีข้อยกเว้น)
- ผู้จัดซื้อและผู้รับรองเป็นคนเดียวกัน หรือมีความสัมพันธ์ส่วนตัวกับผู้ขายที่ไม่ได้แจ้ง

## 6. เอกสารที่ต้องเก็บต่อรายการซื้อ (แฟ้มจัดซื้อ)

1. สเปกที่ขอ (D0) 2. RFQ และคำตอบเป็นลายลักษณ์อักษร (D1) 3. บันทึกการประเมินคำตอบ (D2) 4. หลักฐานการซื้อตัวอย่าง 5. รายงานการวัดและ hash ของ evidence log (D4) 6. รายการในทะเบียน (doc 344) 7. PO ล็อตและเงื่อนไข (D5) 8. บันทึกตรวจรับและการสุ่มวัด (D6) 9. ผลตรวจ H1–H7 (D7) 10. ทะเบียนข้อยกเว้น (ถ้ามี) พร้อมผู้อนุมัติและวันหมดอายุ

## 7. อุปกรณ์ KeySign (RP2350) ระหว่างยังเป็นต้นแบบ

- ซื้อจากตัวแทนจำหน่ายที่ได้รับอนุญาตเท่านั้น บันทึก chip ID และ revision ต่อชิ้น (ต้องเป็น A4 ตาม doc 345) เปรียบเทียบกับหลักฐานอุปกรณ์ตัวแรก
- **ซื้อชิ้นทดลองที่ยอมทิ้งได้ แยกจากชิ้นใช้งาน** ก่อนทดสอบการเขียน OTP/ล็อก (ย้อนไม่ได้ ดูบันทึกข้อเสนอคำตัดสินข้อ 3)
- เตรียมเครื่องตาม runbook doc 347 (7 ขั้น มี 3 จุดที่ต้องให้มนุษย์กดปุ่ม) และลงทะเบียนแบบ append-only
- ห้ามเรียกอุปกรณ์ว่า FIDO2 และห้ามอ้างกับลูกค้าว่ากันการขโมยระดับฮาร์ดแวร์ (ดู doc 346 §9)

## 8. เครือข่ายและ NAS/สำรองข้อมูล

- switch ต้องรองรับ VLAN ตาม doc 342 (Management / SetBox / Evidence-Backup / Member / Guest-IoT) และ firewall ต้องตั้ง egress แบบ deny เป็นค่าเริ่มต้น
- ห้ามซื้ออุปกรณ์ที่ต้องพึ่งบริการคลาวด์ของผู้ขายเพื่อทำงานพื้นฐาน (SetBox ต้องทำงานแม้ SPADA/อินเทอร์เน็ตล่ม)
- NAS/สำรองข้อมูลต้องรองรับการเข้ารหัสและอยู่คนละ security zone · **ต้องซ้อมกู้คืนจริงก่อนส่งมอบ** (ตามหลัก `onemanos-care.js`)

## 9. การทบทวนมาตรฐานนี้

- ทบทวนทุกครั้งที่ ADR 0017/0020, doc 342 หรือ doc 344 เปลี่ยน และอย่างน้อยปีละครั้ง
- เมื่อรับรองรุ่นแรกได้ ให้ปรับข้อ D0–D6 จากบทเรียนจริง

## 10. รายการที่ตัดสิน ณ วันซื้อ (ไม่กำหนดล่วงหน้า)

รายการเหล่านี้ **จงใจเว้นไว้** เพราะราคา ความพร้อมของสินค้า และเงื่อนไขตลาดในวันซื้อจริง (หลังระดมทุน) จะต่างจากวันนี้ ให้กรอกใน [PURCHASE-TIME-DECISION-SHEET](PURCHASE-TIME-DECISION-SHEET.md) และให้ผู้อนุมัติจ่ายลงนาม

| รายการ | ตัดสินอย่างไร ณ วันซื้อ |
|---|---|
| ผู้ขาย รุ่น SKU และราคา | ขอใบเสนอราคาอย่างน้อย 3 ราย (ถ้าตลาดมี) เทียบราคาเต็มรวมประกัน/ขนส่ง/ภาษี |
| งบประมาณและวงเงินที่ต้องอนุมัติเพิ่ม | ตามงวดเงินที่ระดมได้ (ข้อ 11) และสถานะงบ ณ วันนั้น |
| จำนวนตัวอย่างและเปอร์เซ็นต์สุ่มวัด (X%) | ตามขนาดล็อตและราคาต่อเครื่อง ณ วันซื้อ (เครื่องแพง/ล็อตเล็ก = สุ่มมากขึ้น) |
| ระยะรับประกัน (X ปี) เงื่อนไขซ่อมและเวลาส่งมอบ | ตามที่ตลาดให้ในวันนั้น ห้ามต่ำกว่าเกณฑ์ขั้นต่ำที่กำหนดในแบบกรอก |
| กฎหมายจัดซื้อ ภาษี ศุลกากร | ตรวจกับผู้เชี่ยวชาญตามกฎหมายที่ใช้บังคับ ณ วันซื้อ |
| รายชื่อบุคคลตามบทบาท (ข้อ 3) | ระบุก่อนออก RFQ และไม่ซ้ำบทบาท |
| เวอร์ชัน BIOS/TPM firmware ที่รับได้ | ตรวจประกาศช่องโหว่และรายการแก้ไขล่าสุดของผู้ผลิตในวันซื้อ แล้วล็อกเวอร์ชันที่ผ่านการรับรอง |
| Track ของล็อต (S หรือ C หรือผสม) | ตามสัญญาลูกค้าที่จะส่งมอบ (ข้อ 12) |

**สิ่งที่ตัดสินล่วงหน้าแล้วและไม่เปลี่ยนตามตลาด**: หลัก P1–P8, เกณฑ์ตกทันที (vTPM, ปิดดีบักไม่ได้, ไม่ตอบเป็นลายลักษณ์อักษร ฯลฯ), ขั้นตอนตัวอย่างก่อนล็อต และการรับรองรุ่นจากการวัดจริง

## 11. การจัดซื้อที่ผูกกับการได้รับเงินระดมทุน (Funding-gated)

ไอเดียเพื่อกันพลาดเมื่อเงินเข้าแล้ว จึงอยากรีบสั่งทีเดียว:

| # | แนวทาง | เหตุผล |
|---|---|---|
| F1 | **ทำสิ่งที่ไม่ต้องใช้เงินมากล่วงหน้า**: จดหมาย RFQ, เตรียมสคริปต์รับรองฮาร์ดแวร์, เตรียมแบบกรอก, ซ้อมขั้นตอนกับอุปกรณ์เดิม | วันที่เงินเข้าจะได้เดินได้เร็วโดยไม่ข้ามด่าน |
| F2 | **แบ่งงวดการซื้อ**: งวด 1 = ตัวอย่างเพื่อรับรอง (ยอดน้อย) · งวด 2 = ล็อตนำร่อง · งวด 3 = ล็อตขยาย เมื่อผลนำร่องผ่านเกณฑ์ | จำกัดความเสียหายถ้ารุ่นที่เลือกผิด |
| F3 | **ห้ามสั่งล็อตใหญ่ก่อนรุ่นอยู่ในทะเบียน** แม้มีเงินแล้วหรือมีแรงกดดันจากลูกค้า/นักลงทุน | ตรงกับ ADR 0020 และธงแดง "เร่งส่งมอบ" |
| F4 | **คัดผู้ขายสำรองอย่างน้อย 1 ราย/1 รุ่น** ผ่านการรับรองไว้คู่กัน | กันสินค้าขาดตลาดหรือผู้ขายผิดสัญญา |
| F5 | **จ่ายตามหลักไมล์สโตน** เช่น มัดจำน้อยตอนสั่ง ส่วนที่เหลือจ่ายหลังตรวจรับและสุ่มวัดผ่าน (เจรจาตามที่ตลาดยอมในวันนั้น) | มีอำนาจต่อรองถ้าสินค้าไม่ตรงคำตอบ |
| F6 | **เผื่อเครื่องสำรอง/อะไหล่** (X% ตามอัตราเสียของตลาด) และเครื่องสำหรับทดสอบ/รับรองซ้ำ | เปลี่ยน BIOS หรือเปลี่ยนชิ้นส่วนแล้วต้องรับรองใหม่ |
| F7 | **ตรวจวงจรชีวิตสินค้า** (รุ่นเลิกผลิต/EOL, การรับประกันการมีอะไหล่) ก่อนตัดสินใจล็อต | หลีกเลี่ยงล็อตที่ตามซื้อเพิ่มไม่ได้ในรุ่นเดียวกัน |
| F8 | **ตรวจอัตราแลกเปลี่ยนและเวลาส่งมอบ** ถ้านำเข้า และกำหนดอายุใบเสนอราคาให้ครอบคลุมช่วงตัดสินใจภายใน | ราคาในวันนี้อาจไม่ใช่ราคาวันสั่ง |
| F9 | **ทางเลือกเช่า/ลีสเครื่อง** สำหรับลูกค้าหรือช่วงนำร่อง (ถ้าตลาดมี) | ลดเงินสดจม แต่ต้องตรวจว่ายังรับรองรุ่นและควบคุม BIOS ได้ |
| F10 | **ทะเบียนทรัพย์สิน**: บันทึก serial, รุ่น, BIOS, ผู้รับผิดชอบ, ลูกค้าปลายทาง ตั้งแต่ตรวจรับ | ใช้เพิกถอน/เรียกคืน/รับรองใหม่เมื่อจำเป็น |
| F11 | **ตรวจประวัติการเรียกคืนสินค้าและช่องโหว่ TPM/BIOS ของรุ่นนั้นในวันซื้อ** | ข้อมูลเปลี่ยนตลอดเวลา ต้องดูในวันนั้น |

## 12. สองเส้นทางการติดตั้ง: Track S และ Track C

ทั้งสองเส้นทางเป็นไปได้จริงและมีเหตุผลต่างกัน (ADR 0014: OneManOS อยู่นอก SPADA) รายละเอียดเชิงหลักการอยู่ในร่าง [ADR-DRAFT-hardware-qualification-scope](../decisions/ADR-DRAFT-hardware-qualification-scope.md) สรุปผลต่อการจัดซื้อ:

| หัวข้อ | **Track S** ไม่เชื่อม SPADA | **Track C** เชื่อม SPADA |
|---|---|---|
| เหตุที่ต้องมีเกณฑ์ฮาร์ดแวร์ | ปกป้องข้อมูลและความต่อเนื่องของลูกค้ารายนั้น (เก็บกุญแจเข้ารหัสดิสก์, กันเครื่องถูกแก้ไขแฝง) | SPADA ไว้วางใจตัวตนอุปกรณ์เพื่อทำธุรกรรมของสมาชิก ความผิดพลาดกระทบผู้อื่นในเครือข่าย |
| ผู้กำกับเกณฑ์ | ฝั่ง OneManOS (Technical Owner ของ SetBox Factory WorkSpace) | Attestation Policy Steward ตาม ADR 0020 |
| ทะเบียนที่ใช้ | **ทะเบียนแบบเดี่ยว** (ฝั่ง OneManOS แยกชุด) วัดด้วยขั้นตอนเดียวกัน เกณฑ์ฐาน = NATIVE-ELIGIBLE | **ทะเบียน doc 344** (ฝั่ง SPADA) **บังคับ** ห้ามติดตั้งถ้าไม่อยู่ในทะเบียน |
| ผู้ลงนามรับรองรุ่น | ฉัตรชัย (ชั่วคราว ตามทิศทางของ Lead) | Attestation Policy Steward (ปัจจุบัน: ฉัตรชัย) |
| เครื่องที่ลูกค้ามีอยู่แล้ว | อนุมัติเป็นรายกรณีหลังวัดจริง (ขั้นตอน 7 ข้อในร่าง ADR) | ห้าม (ADR 0020) |
| EK certificate | ไม่บังคับ | จำเป็นเมื่อจะขยับไป `APPLIANCE` (ตอนนี้ยังบล็อก) |
| `ProvisioningClaim`/ออนไลน์ตอนติดตั้ง | ไม่ต้อง | ต้อง (ADR 0017 §7.4) |
| ส่งมอบ | H1–H7 | H1–H7 + ตรวจ Trusted Service Gate |
| อัปเกรดไปเชื่อม SPADA ภายหลัง | ทำได้เมื่อลูกค้าลงทะเบียนเป็นสมาชิก SPADA และเครื่องผ่านการวัด/ทบทวน evidence โดย Steward ได้ระดับ ≥ NATIVE-ELIGIBLE แล้วเพิ่มรายการใหม่ในทะเบียน doc 344 และ provision ใหม่ | ไม่เกี่ยว |

**คำแนะนำเชิงจัดซื้อ**: ซื้อและรับรองด้วย **เกณฑ์ฐานเดียวกัน** ทุกเครื่อง เพื่อให้เครื่องที่ขายแบบ Track S เชื่อม SPADA ได้ภายหลังโดยไม่ต้องเปลี่ยนเครื่อง ส่วนเอกสารสัญญากับลูกค้าต้องระบุ Track ให้ชัดว่ายังไม่ได้รับสิทธิ์/การรับรองใดจาก SPADA เมื่อเป็น Track S

## 13. การทบทวนรอบถัดไป

เมื่อเงินระดมทุนเข้าและก่อนออก RFQ ให้ทบทวนมาตรฐานนี้หนึ่งรอบ พร้อมตรวจว่า ADR 0017/0020, doc 342 และ doc 344 ยังไม่เปลี่ยนและสถานะ SetBox (ผลตรวจ 2026-09-06, GAP-01..08) ถูกปิดหรือยัง
