# เศรษฐกิจดิจิทัลที่สมาชิกได้ประโยชน์สูงสุด: ข้อเสนอบนสถาปัตยกรรมจริงของ SPADA Node/Network + OneManOS SetBox

> สถานะ: **ข้อเสนอ v0.1** (ยังไม่ผ่านการตัดสินใจของ Lead) · วันที่ 2026-09-29
> ทุกข้อเสนอผูกกับส่วนที่มีอยู่จริงใน monorepo/SetBox และระบุสิ่งที่ต้องตัดสินใจ ตัวเลขเปอร์เซ็นต์และราคาที่ยังไม่มีฐานข้อมูลจริงเว้นเป็น "X" เพื่อไม่ให้เดา
> อ่านคู่กับ [GAP-ANALYSIS v0.3](GAP-ANALYSIS.md) ข้อ 3 ซึ่งพบว่า doc 100 (โมเดลรายได้เดิม) ขัดกับ ADR 0012

## 1. บทนำ: ทำไมต้องคิดใหม่

ระบบจริงวางรากฐานไว้ดีแล้วว่า **สมาชิกเป็นเจ้าของตัวตน ข้อมูล และ AI** (doc 247) และ node เป็นผู้ให้บริการ ไม่ใช่เจ้าของสมาชิก (ADR 0005) แต่โมเดลรายได้เดิม (doc 100) เน้น **การเก็บค่าธรรมเนียม 40% ให้ node, โทเคน, staking และการขายข้อมูลแบบ anonymized** ซึ่ง

1. ขัดกับ ADR 0012 (โทเคน/chain ไม่อยู่ใน Core และยังไม่มีโค้ด)
2. ให้แรงจูงใจแก่ผู้ให้บริการในการเก็บค่าธรรมเนียมสูงสุด ไม่ใช่สร้างมูลค่าสุทธิให้สมาชิก
3. ตั้งอยู่บนตัวเลขผู้ใช้ที่ยังไม่มี (doc 189: user/LOI = 0)

ข้อเสนอนี้กลับลำดับ: **เริ่มจากมูลค่าสุทธิที่สมาชิกได้ แล้วค่อยออกแบบว่าใครจ่ายอะไร**

## 2. หลักการ 6 ข้อของเศรษฐกิจที่ให้ประโยชน์สมาชิก

1. **สิทธิ์ต้องฟรี บริการคิดเงินได้**: สิ่งที่เป็นสิทธิ์พื้นฐานของสมาชิกไม่มีค่าธรรมเนียม (ดูข้อ 4)
2. **มูลค่าสุทธิของสมาชิกต้องเป็นบวก**: วัดจาก (มูลค่าที่ได้รับ − ที่จ่าย) ไม่ใช่จำนวนธุรกรรม
3. **ราคาโปร่งใสและล็อกด้วยหลักฐาน**: ตารางค่าธรรมเนียมมี hash ใน ServiceBook เหมือน manifest ของแอป แก้ = รุ่นใหม่ที่สมาชิกต้องยอมรับใหม่
4. **ข้อมูลขายได้เฉพาะที่เจ้าของสั่งเอง ต่อครั้ง และไม่ถูกคัดลอกถาวร**
5. **ออกได้เสมอ**: ลูกค้าเลิกใช้แล้วได้ข้อมูลและหลักฐานคืน (ADR 0026 `export`)
6. **ทดลองจริงก่อนขยาย**: ทุกโมเดลผ่านนำร่องกับสมาชิกกลุ่มเล็กก่อน ตามเป้า M2 ของระบบ

## 4. "สิทธิ์ที่ต้องฟรี" (Rights-are-Free Schedule) ข้อเสนอ

ไม่คิดค่าธรรมเนียมใดกับ: (1) สร้าง/ผูก/หมุนกุญแจตัวตนและ SPADA ID (2) การกู้กุญแจและ emergency freeze (ADR 0005 §9) (3) ขอคืนและส่งออกข้อมูลของตนเอง รวม Reclaim/DSAR (4) การเพิกถอน consent (5) PersonSpace พื้นฐานตามโควตาที่กำหนด (6) ช่องทางอุทธรณ์การตัดสินของนโยบาย (ADR 0005 §7) (7) assisted access สำหรับผู้ไม่มีอุปกรณ์ (ADR 0005 §11) (8) การย้ายไป node หรือแอปอื่น

เหตุผล: เป็นการเก็บค่าธรรมเนียมจากสิทธิ์จะทำให้ node มีแรงจูงใจขัดกับสมาชิก และขัดหลัก ADR 0005 §15 (ห้าม bypass consent/appeal/portability)

## 5. ข้อเสนอ 10 ข้อ

### M1. ใบแจ้งมูลค่าสมาชิกรายเดือน (Member Value Statement)
- **คืออะไร**: รายงานส่วนตัวเดือนละครั้ง แสดงค่าบริการที่จ่าย, บริการที่ใช้, ข้อมูลที่ถูกขอใช้ (จาก consent ledger), เงินที่ได้รับจากการอนุญาตใช้ข้อมูล, ค่าธรรมเนียมที่ถูกยกเว้น
- **ประโยชน์**: สมาชิกเห็นมูลค่าสุทธิของตนเอง สร้างความไว้วางใจ ตรวจสอบ node ได้
- **ต่อยอดจาก**: `metering-service`, consent-service, ServiceBook/EWalletBook
- **ข้อควรระวัง**: สร้างบน device/บริการของสมาชิก ไม่ส่งข้อมูลดิบออกนอกเครื่อง

### M2. ขายข้อมูลแบบ "เจ้าของสั่งเอง ต่อครั้ง" แทนตลาดข้อมูลรวม
- **คืออะไร**: ผู้ขอ (บริษัท นักวิจัย) ส่งคำขอผ่าน broker ระบุวัตถุประสงค์ ขอบเขต ระยะเวลา และราคา เจ้าของเลือกอนุมัติ ปฏิเสธ หรือเสนอราคาสวน ชำระผ่าน `finance-service` ได้สิทธิ์เข้าถึงชั่วคราวโดยไม่คัดลอกถาวร
- **ประโยชน์**: เจ้าของได้รายได้จากข้อมูลตนเองจริง ราคาถูกกำหนดโดยเจ้าของ ไม่ใช่การขายข้อมูลรวมที่คนอื่นได้กำไร
- **ต่อยอดจาก**: `data-share-broker-service` (default-deny, scoped, time-boxed, revocable, TrustScore gate ของผู้ขอ ≥ 500 สำหรับข้อมูลอ่อนไหว)
- **แทนที่**: ตลาดข้อมูล anonymized 15% ของ doc 100
- **ต้องทำก่อน**: DPIA + legal review (broker กำหนดเป็น launch gate) · ค่าธรรมเนียมบริการของ broker ให้เป็นอัตราคงที่ต่ำและเปิดเผย (X) · ห้ามข้อมูลอ่อนไหวเด็ก/ผู้ไร้ความสามารถเพื่อการค้า (ADR 0005 §10)
- **ความเสี่ยง**: ผู้ขอกดดันสมาชิกที่ขัดสน ต้องมีเพดานข้อมูลต่อคน/ต่อเดือนและ cooling-off

### M3. ตารางค่าธรรมเนียมที่ล็อกด้วยหลักฐาน (Fee Constitution)
- **คืออะไร**: ทุก node/แอป/broker ต้องประกาศตารางค่าธรรมเนียมที่ hash ลง ServiceBook เปลี่ยนได้ต้องแจ้งล่วงหน้า (X วัน) และสมาชิกยอมรับรุ่นใหม่ · กำหนดเพดานรวมของค่าธรรมเนียม (แพลตฟอร์ม + node + ผู้เผยแพร่) ต่อธุรกรรม (X%) · ค่าธรรมเนียมบริการห้ามเกินเพดานโดยไม่ผ่านกระบวนการ RFC ของชุมชน (ADR 0005 §14)
- **ประโยชน์**: ป้องกันการขึ้นราคาหลังผูกมัด ตรวจสอบได้โดยสมาชิก
- **ต่อยอดจาก**: กลไก hash manifest (ADR 0026 §2–3), ADR 0021 (canonical hash)
- **แทนที่**: "Operator ได้ 40% ทุกประเภท" ใน doc 100

### M4. ตัวเลือกส่วนแบ่งแบบสหกรณ์ (Patronage) แทนโทเคน/staking
- **คืออะไร**: node ชุมชนดำเนินการแบบสมาคม/สหกรณ์ (มีกรณีสมาคมศิษย์เก่าใน doc 133 เป็นตัวอย่างชุมชน ผมยังไม่ได้อ่านรายละเอียดว่าเข้ากับโมเดลนี้เพียงใด) ส่วนเกินหลังหักต้นทุนคืนให้สมาชิกตามสัดส่วนการใช้ (patronage) ผ่านกระเป๋าเงินบาท ไม่ต้องมีโทเคน
- **ประโยชน์**: สมาชิกได้ผลประโยชน์ตามการมีส่วนร่วมจริง หลีกเลี่ยงความเสี่ยงด้านการลงทุนแบบโทเคน และสอดคล้อง ADR 0012
- **ต่อยอดจาก**: `finance-service`, metering, ADR 0005 §2 (ประเภทเจ้าของ node)
- **ต้องทำก่อน**: ปรึกษากฎหมายเรื่องรูปแบบนิติบุคคลและภาษี

### M5. เครดิตพกพาที่สมาชิกเป็นผู้เปิดเผยเอง (Trust-backed Credit Evidence)
- **คืออะไร**: สมาชิกเลือกเปิดเผยหลักฐานที่ตรวจสอบได้ (ประวัติชำระ ประวัติส่งมอบงาน ความสม่ำเสมอของรายได้จากบัญชีใน SetBox) ให้สถาบันการเงินพิจารณาสินเชื่อรายย่อย โดยไม่ส่งข้อมูลดิบ
- **ประโยชน์**: SME/OPB ที่ไม่มีประวัติในระบบเดิมเข้าถึงเงินทุนได้
- **ต่อยอดจาก**: Reclaim "D3 Credit signal" (รอไฟเขียวตาม README), TrustScore, SetBox `ledger.js`/`bank-reconciliation.js`
- **ข้อจำกัดที่ต้องรักษา**: TrustScore ไม่ใช่อำนาจสากล มีสิทธิ์อุทธรณ์ (ADR 0005 §6–§7) ผู้ให้สินเชื่อเป็นผู้ตัดสินใจ ไม่ใช่ SPADA · ต้องผ่านการตรวจกฎหมายเครดิตและ PDPA

### M6. SetBox แพ็กเกจ OPB (One Person Business) ราคาคงที่ + ค้ำประกันการออก
- **คืออะไร**: ชุดสำเร็จ (บัญชี ภาษี VAT หัก ณ ที่จ่าย เงินเดือน เอกสาร) สำหรับธุรกิจคนเดียวหรือทีมเล็ก ราคาคงที่ต่อเดือน (X) พร้อมข้อตกลงว่าเลิกใช้ได้ทุกเมื่อและได้ข้อมูลครบ (ผ่านเกณฑ์ H1–H7)
- **ประโยชน์**: ต้นทุนการทำบัญชี/ภาษีของ OPB ลดลง ไม่ผูกมัดผู้ขาย
- **ต่อยอดจาก**: SetBox modules + `docs/commercial/` (แม่แบบ scope/ราคา/SLA) + doc 263 (OPB OS spec)
- **ข้อเท็จจริงที่ต้องยอมรับ**: ROADMAP ระบุว่ายังไม่ส่งมอบลูกค้านอกกิจการผู้พัฒนา และตัวเลขราคาจริงต้องตั้งจากเวลาที่ใช้จริงในงานแรก · ผลตรวจ 2026-09-06 ยังเป็น CONDITIONAL ต้องปิด P1 ก่อนขายจริง
- **ตัวอย่างเพิ่มมูลค่า**: เชื่อมเครื่องคำนวณค่าธรรมเนียมธนาคารตามเกณฑ์ใหม่ของ ธปท. (มี skill `bot-bank-fee-2569` ในสภาพแวดล้อมของคุณ) เข้ากับ `cash-bank`/`bank-reconciliation` เพื่อบอกสมาชิกว่าประหยัดได้เท่าใด (รายละเอียดต้องอ้างประกาศ ธปท. จริง ผมไม่ได้อ่านเนื้อหา skill นี้)

### M7. ตลาดแอปที่ผู้ใช้เห็นราคาและสิทธิ์ก่อนติดตั้ง และส่วนแบ่งชัดเจน
- **คืออะไร**: App Catalog ตาม ADR 0026 แสดง `dataScopes` + `purpose`, ราคา, SLA, ช่องทางส่งออกข้อมูล ผู้เผยแพร่ได้ส่วนแบ่งเป็นค่าคงที่ที่ประกาศไว้ (X%) และค่าคอมมิชชันแพลตฟอร์มมีเพดาน
- **ประโยชน์**: ผู้พัฒนารายย่อยและเจ้าของ node ขายแอปได้ ผู้ใช้ไม่ถูกหลอกเรื่องสิทธิ์ข้อมูล
- **ต่อยอดจาก**: ADR 0026 (Proposed), ADR 0014 (SetBox อยู่นอก SPADA), ADR 0017
- **ต้องทำก่อน**: ADR 0026 อนุมัติ · implement การแบ่งรายได้ (ยังไม่พบโค้ด) · เกณฑ์ตรวจแอปที่แตะเงินหรือข้อมูลอ่อนไหวโดยมนุษย์

### M8. ชั้นคุ้มครองสมาชิกจากการฉ้อโกง (Member Protection Layer)
- **คืออะไร**: ใช้ผลวิเคราะห์ใน doc 335 เป็นบริการที่สมาชิกสัมผัสได้: ธุรกรรมที่ย้อนไม่ได้ต้องยืนยันด้วยมนุษย์ทุกระดับ, ตรวจความผิดปกติของ velocity (G4), เวลารอสำหรับการโอนมูลค่าสูงหรือการเปลี่ยนกุญแจ, ช่องทาง emergency freeze
- **ประโยชน์**: ลดความเสียหายจากการหลอกลวงด้วย AI/deepfake ซึ่งเป็นภัยที่ doc 335 ระบุว่าโตขึ้น
- **ต่อยอดจาก**: doc 335 D2/D2.1, ADR 0005 §9, `human-gate.js`
- **สถานะ**: doc 335 ยัง Proposed ต้องให้ Lead ตัดสินก่อน · กองทุนชดเชยหรือประกัน (ถ้ามี) ต้องออกแบบและตรวจกฎหมายแยก

### M9. งานชุมชนที่มีรายได้: Steward และ assisted access
- **คืออะไร**: บุคคลที่ผ่านเกณฑ์ (TrustScore, อบรม) ช่วยผู้ไม่มีอุปกรณ์หรือผู้สูงอายุเข้าใช้ ผ่าน community terminal ตามกติกา ADR 0005 §11 (ผู้รับรองโอนความเป็นเจ้าของให้ตนไม่ได้, แสดง actor/purpose/expiry ทุกการกระทำ) และได้ค่าตอบแทนจากกองทุนหรือค่าบริการที่ประกาศ
- **ประโยชน์**: สร้างรายได้ท้องถิ่นและขยายการเข้าถึงกลุ่มที่ถูกทิ้งไว้ข้างหลัง
- **ต้องทำก่อน**: กำหนดแหล่งเงินและมาตรฐานการรับรอง · กันผลประโยชน์ทับซ้อน

### M10. กองทุนสาธารณะเล็กๆ (Public Goods & Hardship Fund)
- **คืออะไร**: หักส่วนเล็ก (X) ของค่าบริการที่ node ชุมชนเก็บเข้ากองทุน ใช้จ่ายค่าเปลี่ยนอุปกรณ์ KeySign ที่สูญหายของผู้มีรายได้น้อย, assisted recovery, การอบรม และซอฟต์แวร์เปิด บริหารโดยชุมชนตามกติกา governance (ADR 0005 §14)
- **ความเสี่ยง**: การบริหารเงินกองทุนต้องโปร่งใสและตรวจสอบได้ มีกฎหมายควบคุม

## 8. ตัวชี้วัดความสำเร็จ (วัดที่สมาชิก)

- สัดส่วนสมาชิกที่มูลค่าสุทธิเป็นบวก (มูลค่าที่ได้ − ที่จ่าย)
- เวลาที่ใช้ส่งออกข้อมูลและกู้คืนสมบูรณ์เมื่อออกจากบริการ
- ความหน่วงของการเพิกถอน consent จนตัดสิทธิ์จริง
- จำนวนธุรกรรมฉ้อโกงที่ถูกหยุดก่อนเสียหาย และเวลาตอบสนอง emergency freeze
- รายได้ที่สมาชิกได้รับจากข้อมูลและแอป (มัธยฐาน ไม่ใช่ค่าเฉลี่ย)
- สัดส่วนสมาชิกกลุ่มเข้าถึงยาก (assisted access) ที่ใช้งานต่อเนื่อง
- ไม่ใช้จำนวน node, จำนวนธุรกรรม หรือจำนวนผู้ใช้รวมเป็นตัวชี้วัดหลัก

## 9. ความเสี่ยงและข้อควรระวัง

| ความเสี่ยง | แนวทาง |
|---|---|
| กฎหมาย: โทเคน/staking, ตลาดข้อมูล, เครดิต, กองทุน, นิติบุคคลแบบสหกรณ์ | ปรึกษาผู้เชี่ยวชาญก่อน E2/E4 ผมไม่ได้ให้คำแนะนำทางกฎหมาย |
| ผู้ขอข้อมูลกดดันสมาชิกที่ขัดสน | เพดานต่อคน/เดือน, cooling-off, ห้ามข้อมูลเด็ก/ผู้ไร้ความสามารถเพื่อการค้า |
| ตัวเลขประมาณการไม่มีฐาน (doc 189: user/LOI = 0) | ใช้ผลนำร่องจริง ไม่อ้างตัวเลข doc 100 |
| ADR 0024–0026 ยัง Proposed | ข้อเสนอที่พึ่งพา (M2 ราคา, M7) ต้องรอ Lead |
| SetBox ยัง CONDITIONAL | ปิด P1 ก่อนขายจริง (ข้อ M6) |
| การแบ่งรายได้ยังไม่ implement | ต้องมี WO สำหรับ finance/metering ก่อน E3 |
| ความซับซ้อน | ทำทีละระยะตามตาราง ไม่ทำพร้อมกัน |

## 10. สิ่งที่ต้องขอให้ Lead ตัดสิน

1. ยืนยัน Rights-are-Free Schedule (ข้อ 4) และเพดานค่าธรรมเนียมรวม (X)
2. ยกเลิกหรือคงกลไกโทเคน/staking/ตลาดข้อมูล anonymized ใน doc 100 (แนะนำให้ supersede ตาม ADR 0012)
3. เลือกระหว่างผลตอบแทนแบบ patronage (M4) และแบบอื่น หลังปรึกษากฎหมาย
4. ตัดสิน ADR 0024–0026 และข้อ D1/D2 ของ doc 335 ที่เกี่ยวข้องกับ M2, M7, M8
5. กำหนดผู้รับผิดชอบเศรษฐกิจของสมาชิกและช่องทางรับเรื่องอุทธรณ์ด้านค่าธรรมเนียม
